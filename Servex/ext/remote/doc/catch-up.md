# Catch-up: the voice agent hears what changed (built 2026-10-20: the `updates` tool)

**The problem.** The voice agent (`voice-app`, a claude.ai session using this remote MCP) only exists when an owner prompt arrives or a tool result comes back. Nothing reaches it in between, so it misses agent replies, `/live` changes and its children's progress.

**The ask (the owner, via voice-app, 2026-10-16):**
1. Every tool result carries "what changed since your last call" for this voice session, or nothing when nothing changed.
2. Ideally, a hook runs the same catch-up on every owner prompt.

Logged in [core/Page/task.jsonl](../../../../public/framework/core/Page/task.jsonl).

## What is possible today

- **No per-prompt hook exists for claude.ai connectors.** Hooks such as `UserPromptSubmit` are a Claude Code feature and run on the user's own machine. A claude.ai chat runs in Anthropic's cloud, and its model decides when to call a tool.
- **No push either.** Claude's MCP client "doesn't yet support resource subscriptions" or sampling ([Build an MCP server for Claude](https://claude.com/docs/connectors/building)).
- **The only channel is the tool result.** In practice that already covers every prompt, because `RemoteMCP.INSTRUCTIONS` tells the voice agent to call `ask_mastermind` before it says anything.


## What is built

- **`updates`** (`External.updates()`, registered by `External.tool()`, so it is on the whole registry and the remote door): returns everything that arrived for THIS caller/conversation since its own cursor, oldest first, at most 50, and moves the cursor. `peek: true` reads without moving it.
- **One place per conversation (2026-11-09, the owner).** The cursor key is `conversation` (pass your claude.ai conversation id) or, with none given, the caller's own voice session id that `RemoteMCP` already resolved for this call (`ctx.session.id` — the dated `cloud-voice-<name>` record), or finally the bare caller — today's original behaviour. Every key's place is one entry in `logs/inbox/<caller>.cursors.json` (`{key: {offset, at, follows}}`); the old single `<caller>.cursor` file is still read as the caller-key's own entry, so an upgrade never jumps anyone's place. **A BRAND NEW key starts at "now"** (the inbox's current end), not the backlog — so a second mastermind that only just started talking to a voice session is never handed a wall of lines meant for someone else's conversation. Its first answer carries `missed`: a digest (below) of what happened between the shared cursor and now, capped to the last 24h.
- **Digest by default.** `updates` returns `{count, more, updates, digest}`: `count` is every raw event read (so paging with `more` stays exact), `digest` is one row per sender — `{from, count, latest}` — and (unless `raw: true`) `updates` itself holds only the newest line per sender, so a caller reading `updates[].text` the old way still works, just compacted. `raw: true` returns every line, as before 2026-11-09.
- **Follows are read here, not pushed to the inbox (step 2).** `follow({path, agent: "voice-app"})` ([follow.md](../../../doc/follow.md)) still records the subscription, but for an external caller `Follow.flush` no longer delivers a `.jsonl` file's lines as an inbox message (a non-jsonl change still gets today's one-line note — there is no line for `updates` to read instead). Instead, `updates` reads each followed file itself, from THIS key's own byte offset (`External.followed_lines`, independent of `Follow`'s own change-detection offsets), and returns each line as `{agent, session, path, line}`. Like the inbox itself, a key's first read of a followed file starts at that file's current end, not its backlog. A directory follow reuses the `.jsonl` files `Follow` itself already tracks (`follow.offsets`) instead of walking the tree again on every `updates` call (`External.followed_files`) — a module with thousands of files costs one lookup, not a recursive directory scan, per call. The followed line is tagged `agent: sub.of ?? line.by ?? null` — the CHILD being tailed, or who wrote the line, never the follower's own id — and passes the same `skip_by`/`heard`/`worth_waking` filters the pushed-message path uses (`Follow.without`, `Follow.worth_waking`), so a parent-tailing-a-child follow still hears only state/pointer lines through `updates` too.
- **No line is ever dropped by a budget (fix, 2026-11-09).** `followed_lines(id, state, budget)` takes the CAP remaining after the inbox's own share and stops reading a file at a line boundary once that budget is spent — the per-file offset only ever advances past lines actually returned. A 60-line burst with a 50-line budget comes back as 50 now, `more: true`, then the other 10 on the next call; nothing is skipped, nothing repeats.
- **The hint (item 1):** `RemoteMCP.hint()` adds one text item, "N new updates for you: call updates.", to every other remote tool result while THIS call's own key is behind (resolved the same way `updates` resolves it, so the hint never disagrees with what a later `updates` call finds), and nothing otherwise.
- **No duplicate "done" at the sender (step 4).** `Agents.wake_parent`, when the parent is a registered external agent and the report carries no "Next:" note, compares it against the same child's last one to that parent after stripping timestamps and ids (`Servex/agents/mark-strip.js`'s `strip_marks`). An identical report skips only the MESSAGE to the parent — the task-dir `inbox.jsonl` line still writes, same as any other "done" — and is counted on the host (`this._dup_done_skips`), never logged per occurrence. **Measured against the real inbox (2026-11-09, read-only, `voice-app.jsonl`, 727 lines):** 398 lines were a "done" report; of those, only 4 (1.0%) were a byte-for-byte repeat of the SAME sender's previous one after stripping. The inbox's earlier bulk — the 369 "done:"-prefixed and 188 raw `follow` lines noted below — were mostly each other's near-neighbors in TEXT, not literal duplicates; the digest (above) and the follow-via-updates change (step 2) are what actually shrink that volume, not this dedup, which catches a smaller, narrower case (the exact same report sent twice).
- **Rotation (step 5).** Every `deliver()` first checks just the inbox's first line (`External.first_line`, a small bounded read, not the whole file) before deciding whether a rotation is even due — only once it is (once a month) does it read the whole file. When due, the part every cursor has already read moves to `logs/inbox/archive/<caller>-<YYYY-MM>.jsonl` (appended, never overwritten); the live file keeps only what some cursor has not read yet, and every cursor is rebased to the shorter file. **A STALE cursor does not pin it**: a conversation key `updates()` has not touched in 7+ days (or the legacy single cursor, by its file's own mtime) no longer holds back the rotation — its offset rebases to 0 instead of to its true remaining distance. Whatever it had not read yet is still in the archive, not lost, just no longer live in the inbox; a conversation nobody resumes in a week cannot hold the whole file hostage.
- **The directive:** one sentence in `RemoteMCP.INSTRUCTIONS`: call `updates` at the start of nearly every turn, and pass `conversation`.

## Not built

- `/live/` and the children's logs still arrive only if an agent calls `follow` on them; nothing subscribes automatically.
- `missed`'s digest covers only the caller's shared inbox backlog, not a brand-new key's followed files (those simply start at "now" too, with nothing to report missing — there was never a subscription for them before).
- The noise this was built to fix (measured 2026-11-09, before this change): `voice-app.jsonl` held 668 lines since October, about 261 unread; 369 began "done:" (finished agents re-reporting "nothing running") and 188 were raw `follow` deltas. Not yet re-measured against a live restart with all five steps in effect.
