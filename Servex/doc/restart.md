# `--restart` runs outside Servex's own process tree

**The bug (09-28, 09-29):** an agent ran `--restart` from inside Servex's own tree (`Servex →
claude → bash → node sustain`). `--restart`'s `taskkill /t /f` is a *tree* kill, so it killed the
caller before the caller finished restarting anything — Servex kept running the old code.
`spawn(..., {detached:true})` does not fix this: Windows records a child's parent once, at
creation, and `taskkill /t` still finds it by that recorded lineage even after the real parent
is gone.

**The fix:** on win32, `--restart` relaunches itself as `--restart-detached` through WMI
(`Invoke-CimMethod Win32_Process.Create`), which parents the new process to `WmiPrvSE.exe`, never
to the caller. The in-tree hop only launches that copy and exits; the detached copy does the
actual kill/wait/confirm. `ops.js`'s `restart_servex` needs no change — it already just runs
`sustain.mjs --restart`.

**The trap for the next test of this:** `Win32_Process.Create` hands the new process WmiPrvSE's
own environment, not the caller's, so `SERVEX_HOME` (and a test's `SERVEX_API_PORT`) would
otherwise vanish — the relaunch pins both explicitly on the command line
(`cmd.exe /c set "SERVEX_HOME=..."&& ...`). Found the hard way: an early version of this fix's own
private-Servex proof leaked past its sandbox and restarted the real Servex, before the pinning
was added.

`kill()` also no longer trusts `taskkill`'s exit code alone: it polls for up to 5s afterward and,
if the pid is still alive, logs loudly and retries with a plain (non-tree) kill.

Proved on a private stand-in Servex (own `SERVEX_HOME`, stub entry script, own API port): a
caller nested inside that fake Servex's own tree asked for a restart, and its pid changed even
though the caller died along with the rest of that tree. No window ever appeared.

**The revive sweep skips an agent with nothing to resume** (2026-10-18): at boot `Agents.revive()` leaves alone, and does not tell "Servex restarted mid-turn", any agent that started after this boot, or has no completed turn and no session file (`Agents.revive_skip`, test `agents/revive-skip.test.mjs`, proof `public/framework/ai/sessions/2026/10/13/session-730e8a7b/mastermind-repo-slim/restart-sweep/proof-fixed.txt`). Such an agent is marked gone and logged once (`revive-skip` in `servex.jsonl`); a second restart seconds after a spawn used to resume a session that did not exist yet and kill the agent at $0, so respawn it.

**A "second boot" seconds after a restart is the keeper, not a second Servex** (2026-10-18): on the 17:32 restart the new Servex (pid 32996) died with exit 3221226505 (0xC0000409, a native fast-fail; 53 such exits sit in `sustain.log`) at 17:33:56, and `sustain.mjs` restarted it as pid 35816 a second later; that boot's `revive()` then swept an agent spawned seconds earlier. `revive()` now runs once per process (`Agents.revived`), and `index.js` calls `Servex.only_one()` first, so a second Servex on the same port prints one line and exits before it touches the shared registry. The crash itself has no report and is not fixed here.

**A native crash now leaves evidence** (2026-10-19): exit 3221226505 is a Windows fast-fail that skips every JS handler and writes no node report (the report flags were already on and never fired in 53 crashes; stderr was already kept in `sustain.log` and is empty before each one). So `sustain.mjs` loads `Crumbs.js` (a breadcrumb line before each child process and file watcher, a heartbeat every 5 s, in `logs/crumbs.log`) and on any signal or `0xC...` exit writes `logs/crashes.jsonl` (crumbs, stderr, the last 5 `servex.jsonl` lines), prints `CRASH` lines beside the `exited` line, and after the 3rd in an hour prints `CRASH-LOOP` and posts a `risk` owner note once Servex answers. The 53 and their numbers: `public/framework/ai/sessions/2026/10/13/session-730e8a7b/mastermind-repo-slim/servex-crash/crashes.json`. The cause itself is still unknown; the next crash's last crumb is the first clue. The 135 `exit 1` boots on 2026-10-01 were a missing `express` in the main tree (4 more a missing agent SDK), already guarded by `ensure-deps.mjs`.

## Why so many restarts, and the fix not built (2026-10-20)

Servex loads its code once at start, so every change under `Servex/` (a new tool, the remote door, an agent class) is live only after a restart; there is no scheduled restart. Each restart ends every agent session (they go dormant and resume on the next message) and drops a cloud call mid-flight, so restarts are held until no agent is working and landings are batched behind one. Next improvement: reload a changed tool module in place (the registry re-imports it on change) so agents keep running; not built.

## Restarts that lose nothing (the owner, 2026-10-22)

**What a restart now keeps.** Before `sustain.mjs --restart` kills Servex, it asks Servex to write down who is alive (`POST /api/before-restart` → `Agents.snapshot()`): every live agent with its state (working, idle, starting), and every agent a pending wake-up waits on, dormant ones included. The list goes to `restart-snapshot.json` beside the registry and one `restart-snapshot` line in `servex.jsonl`; `restart_servex` names its caller in it.

**What the next boot does with it.** `Agents.revive()` reads the snapshot once (then moves it aside to `restart-snapshot.used.json`) and resumes exactly the agents it lists, however long they had been idle; without a snapshot (a crash) the old 30-minute window applies. **Every agent that comes back is told:** one that was mid-turn checks its last tool call; an idle one learns its session was resumed and that any background shell or sleep it had is gone. That note costs each idle agent one short turn.

**Wake-ups node keeps** (`Servex/agents/Wakeups.js`): an agent that wants to be woken later calls `wake_me({in_min | at, why})` instead of sleeping or leaving a background shell running, both of which a restart kills. Node writes `{type:"set"|"fired"|"cancel", id, agent, due, why}` lines to `logs/wakeups.jsonl`, keeps one timer per pending wake-up, and fires it by sending the agent `why` (with `revive: true`, so a dormant agent is reopened). At boot every pending wake-up is armed again; one that came due while Servex was down fires at once and says it is late. `cancel_wake` and `list_wakes` complete the set. Test: `node Servex/agents/wakeups.test.mjs` (9 checks). Off: `SERVEX_NO_WAKEUPS=1`.

## Rule: every agent that was open at a restart comes back (2026-10-22)

The boot sweep (`Agents.revive()`) never refuses on `landed` (a long-lived mastermind lands its first task and keeps working; `mastermind-figma-cards`, `mastermind-test` and `mastermind-item` were buried "landed" that way, item in the 21:11 sweep) and restarts a never-started agent fresh from its spec when it has a task folder (its brief is the prompt; the registry keeps no prompt), else buries it with the reason. A held resume in the gate queue (`Servex.stale`) skips the landing check for the same reason; it refuses only for a deleted cwd, a stop on purpose, or code-carrying spawns, and writes the reason on the row's `ended`. Test: `node Servex/agents/revive-sweep.test.mjs`.

**A `Crumbs.js` wrapper must keep `util.promisify.custom`** (2026-11-05): `promisify(execFile)` needs that hook to resolve `{stdout, stderr}`; without it `.stdout` is undefined and the process list is empty inside Servex (`node Servex/Crumbs.test.mjs`).

**Lag watchdog (2026-10-25).** `Crumbs.js` also starts a worker thread (`CrumbsWatch.js`) that watches a tick the main thread bumps every second. If the main thread is silent for more than 5 s it appends `LAG 5+ s: the main thread has not run since its last operation: <the last child process or watcher it began>` to `logs/crumbs.log` while the stall is still going (only another thread can), and `LAG over: the main thread was stuck N s` when it ends. A freeze like the 2-hour one on 2026-10-25 (a synchronous `git show` per file) now names itself. Test: `node Servex/pool-restore.test.mjs`.

## When Servex crashes: what comes back, why, and what to watch (2026-11-02)

**Two kinds of crash, two causes.** The boot-time record is `logs/crashes.jsonl` (exit code, uptime, the last crumbs, any node report), made by `sustain.mjs`.

1. **A JavaScript error ends the process** (exit `0xC0000374` at 00:31). The node report names it: an unhandled promise rejection. `VoicePage.write()` (`ext/refine/VoicePage.js`) returned a promise nobody awaits (LiveRefine calls it fire-and-forget); the Dictate browser scripts drove a made-up session through the live `/api/session/say`, the page tools refused ("no session …"), the rejection was unhandled and node ended Servex. Fixed three ways: `write()` now catches and logs its own failure (test `ext/refine/voice-page-refused.test.mjs`); `Servex.js` has an `unhandledRejection` handler that logs `unhandled_rejection` to `servex.jsonl` and keeps running; and the browser scripts can no longer reach the live Servex (below).
2. **A native fast-fail** (exit `3221226505` = `0xC0000409`, 74 of them in `sustain.log`, the latest 07:24 on 2026-11-02 after 3143 s). It skips every JavaScript handler and writes no node report, so there is no stack. What the crumbs show across eight of them: heap and handles were ordinary (rss 300–480 MB, heap 130–310 MB, 53–258 handles), and the last lines are always a burst of child-process work (`spawn claude.exe`, `taskkill`, `execFileSync git`) or `/mcp` posts; uptime is random (9 s to 40 h). Not proved to be our code (a Node 24 / libuv Windows crash is as likely). **What to watch:** the `LAG 5+ s` lines just before it (a synchronous `taskkill`/`git` call held the main thread 5 s before the 00:31 crash); a crash within seconds of a boot burst of agent spawns; and `crashes.jsonl` having no report. **To get a real stack** someone with admin must turn on Windows Error Reporting local dumps for `node.exe` (`HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps`, `DumpFolder`, `DumpType=2`); nothing else can see inside a fast-fail.

**Is memory the trigger?** Not proved, a plausible contributor. The monitor logs `ram_free_gb` once a minute (`system.jsonl`, `type: "minute"`). Joined to the 19 crashes in `crashes.jsonl` (2026-10-20 to 11-02): free RAM at the crash had a median near 5.3 GB against a baseline median of 7.6 GB; the first three crashes had 15–16 GB free, so physical RAM alone is not enough; only one (10-25 06:32) was near exhaustion (0.5 GB); the two on 11-02 had about 2.5 GB. The node process count at the crash rose from 14–20 (10-21) to about 165 (11-02), mostly leaked worktree dev servers (`node Server/worktree-servers.mjs list`). Commit charge (the 93% reading) is not sampled, so it cannot be tested from the logs; adding `commit_pct` to the minute line in `Servex/Monitor.js` is the one change that would settle it.

**Do concurrent `/mcp` posts trigger the native fast-fail? Not shown (2026-11-02, 20 trails in `crashes.jsonl`, tested against the 43,000 ten-second windows in `crumbs.log`).** The 09:47 crash (62 s after a boot that revived 6 agents) and the 07:24 one both ended on `/mcp` posts, but: (1) the request crumbs only exist from 10-25, and of the 13 crashes since then 4 had no `/mcp` or child-process traffic at all in their last 10 s (idle, last op a 60 s `Get-CimInstance` poll); (2) boots that revived 17 agents at once peaked at 38 and 31 `/mcp` posts in 2 s and ran 6406 s and 2135 s afterwards; (3) the 10 s windows before the busy crashes sit at the 91st to 99th percentile of child-process and `/mcp` rates, which is enriched, but 9 of 20 crashes were within 1 s of a child-process spawn and about 4 in 10 random instants are that close to one. Read it as "load may make it likelier, no single trail shows it". The only way to know is the stack: Windows Error Reporting local dumps (admin), above.

**Revives are staggered** (`Agents.revive`, `SERVEX_REVIVE_GAP_S`, default 3; 0 = all at once). Mid-turn agents are reopened first, then the rest, one every gap, so 17 agents no longer start 17 `claude.exe` in the same two seconds. `out.revived`/`out.told` list everyone at once; an agent whose session cannot be reopened later is marked `gone` (`revive-failed` in `servex.jsonl`), and one a message woke first is just told. A cheap mitigation, **not a proven fix**: if crashes within a few minutes of a revive boot keep happening at the same rate, set the gap back to 0 and drop it. The `revive` line in `servex.jsonl` therefore counts the queued agents as revived before they start, so count real starts from the agents' own `spawn` lines. A second crash during the wait loses nobody: the queued rows are re-stamped with the new boot and `snapshot()` lists them. Check: `node Servex/agents/crash-revive.test.mjs`.

**Why 00:31 revived nobody, and 01:24 revived eight.** At 00:31 the `exit` handler ran (the JavaScript-error kind lets handlers run), and `Servex.shutdown()` answered it by stopping every live agent, so every registry row read `stopped`, and the boot sweep leaves a stopped row alone (a stop on purpose). The fast-fail at 01:24 ran no handler, so the rows still read working or idle and the 30-minute window brought them back.

**What the code does now** (`Servex/Servex.js` `shutdown()`, `Servex/agents/Agents.js`):
- `down(how)` first writes the restart snapshot (`Agents.snapshot({by:"shutdown", how})`), then stops the agents. `how` is `signal` (SIGINT/SIGTERM), `exit` (clean exit) or `crash` (a non-zero exit code). If a shutdown snapshot is written during a planned restart it would replace the `sustain --restart` one and lose the "(asked by X)" note; that cannot happen today because `sustain.mjs` force-kills Servex and no handler runs. Watch `servex.jsonl` for `unhandled_rejection` events piling up: the guard logs them instead of crashing. A row stopped by that shutdown has `stopped_by: null`, so a snapshot with `how` revives a listed row even though it reads `stopped`; a row someone stopped (`stopped_by` set) stays stopped.
- With **no snapshot at all** (a native crash, or a `kill`), `revive()` rebuilds the list from the registry: every row from the previous boot, working or idle, `revivable`, with a session and a task that has not landed. Each is told `Servex crashed at <time>; resume` (a planned restart still says `restarted … (asked by X)`). Test: `node Servex/agents/crash-revive.test.mjs` (a registry with no snapshot, plus the staggered revive).

**Tests must not hit the live Servex.** `Server/ServexFence.mjs` answers every request to `127.0.0.1:8090`, `localhost:8090` and `servex.localhost` from a Playwright context with `{ok:true, fenced:true}` (an empty event stream for `/stream`), and prints `servex fence: kept off the live Servex: …` at exit. It is a context route, so a script's own `page.route()` stubs win; inside them use `route.fallback()`, never `route.continue()` (continue goes to the network). On when `FENCE_SERVEX=1`: `TestRunner.browser()` sets it and points `PWENTRY` at `core/Test/playwright-fenced.mjs` (a wrapper over the real Playwright, real path in `PW_REAL`); `Server/Browser.mjs` honours the same switch. Test: `node Server/ServexFence.test.mjs`. A private Servex per test was the alternative: heavier, and the scripts only ever want stubs. `Servex/test` has no such stand-in.
