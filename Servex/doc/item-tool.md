# The item tool

`item({path, delta})` in `Servex/agents/page_tools.js`: `page_set` generalised to any Item class. `delta` is one log line, the object `Item.set()` takes. A key naming a method calls it, a key naming a child walks into it, anything else assigns (`set_one` in `core/Item/Item.js`; there is no second apply).

- **Which log:** a url's folder holds `task.jsonl` (Task), else `session.jsonl` (Session, `core/Session/Session.js`), else `page.jsonl` (Page). `task.jsonl` beside a `page.jsonl` means a task folder. A `class` key on line 1 wins when `Item.types` registers that name (`class_for`); an unknown name falls back to the file's own class.
- **One live root per file, for any class** (2026-10-28, build I): every file is replayed once into `Item.Store.for(url)`, and each write is one line applied to that live root (`try_line`), then appended. A page write no longer replays the whole page: `page_set`, `page_add`, `page_call` and `page_log` all go through `run_item`, and a page's answer is drawn from the live `Page` (`page_picture`). Measured on the 1167 `page.jsonl` files in git: 1137 draw exactly as the old text replay, 19 differ cosmetically (an untyped item, a nested data card flattened, a title a line set now shows, one order), 11 need a browser to replay (their writes were already refused; reads fall back to the text replay). At most 1000 live roots are kept (`LIVE_CAP`; the least recently used go cold and replay on their next call). A browser's raw page line (`record_lines`) advances a warm page the same way; one node's Page cannot apply is still written and the warm root dropped (a task line is refused instead).
- **`improvements.jsonl`** (2026-10-22): a url naming `<folder>/improvements.jsonl` is class `Improvements` (`core/Task/Improvements.js`, a Task); `tasks.add` always nests there (no folder). The same title proposed again is merged by the class's own list (its `add` reinforces the existing task, on write and on replay), so the tool writes the add as sent; the answer says `merged: [{title, into, weight}]`. The rule for writing one is in `Servex/agents/roles/mastermind.md`, "Improvements".
- **Item vs log, settled 2026-10-22** ([code-shape.md](/framework/ai/doc/code-shape.md)): `item` is for files a class reads (Task, Session, Process, Page, improvements): node replays the class, checks the delta or method against it, writes, and answers with what it wrote (`{ok, ids, line, size, now: {state, completion}}` for a Task, Session or Process; a Page write still answers its page). The full computed state is a read, with no delta. `log` (the Servex MCP `log` tool) is the plainly named raw append for any other JSONL record: node adds time, author and session and checks the line against the log's schema. Neither makes the model write bookkeeping.
- **No delta** returns the state; Task: `{class, state, completion, data, tasks}` from `Task.replay`.
- **Dot paths:** `"now.preview": x` becomes `{now: {preview: x}}`, and `"tasks.a.tasks.b.title": x` sets three levels down; the line is written nested, never dotted. `target` takes the same path (`"tasks.a.tasks.b"`, or a list of hops) and is walked level by level through each level's own `get` (a property, a named List, a List's member), so it reaches any list, not only `tasks` ([ids-and-paths.md](/framework/core/Session/tasks/data-shapes/ids-and-paths.md), DECIDED).
- **Ids** (2026-10-28): an id the tool makes is `Item.short_id()`, 8 random letters and digits with a letter first, redrawn on a clash among siblings; never a slug of the title. An explicit `id` is kept; one a sibling already has, or one holding a dot, is refused. The same title twice under one parent is refused as the same ask (the answer names it as `existing`), except where the class merges it (Improvements). A task with its own folder still gets a readable folder name from its title (`<module>/tasks/<slug>/`): that is a path on disk, not an id.
- **Verdicts:** `{"approve":"ok"}` is written as sent; `Task.replay_line` passes the string to the verb.
- **Refusals (Task):** `_` keys and keys that are no method, field or child return `{ok:false, why, exists}`.
- **Instructions:** first call per caller and class returns `Item.describe()` (plus first comment lines); `{"help":{}}` repeats them.
- **Decision:** the `jsonl-schema.mjs` check is skipped for Task lines (the tool validates them; the schema forbids `by`/`ts`).
- Test: `node Servex/agents/item_tool.test.mjs`. Servex must restart to load the tool.
- **In-process (step 12):** Servex-spawned agents also get this tool as `mcp__local__item` (same function, no HTTP; the `mcp__servex__` twin is disallowed). Off with `SERVEX_LOCAL_TOOLS=0`; test `Servex/agents/item-local.test.mjs`.
- **Step 3c supersedes the folder-by-default below:** `tasks.add` NESTS in the parent's file (`{"tasks":{"add":{…,"id"}}}`, later `{"<child id>":{…}}`); a folder is made only with a real module home, then listed in the module's `files.jsonl`. `{"folder":"<child id>"}` moves a nested child out. A module folder that already exists is refused with `suggest: "<slug>-2"`; nested ids are random (above). One cached root per file (`Item.Store.for`), re-read when the file changes on disk; `page_set/call/add/log` on a task folder take the same path.
- **Task homes (step 14a; changed 2026-10-26):** a task stays in the session that files it: `{"tasks":{"add":{title, module?, home?, …}}}` nests in the parent's log. `module` is a tag for the module page; only an explicit `home: "<module>"` makes a child folder (`<module>/tasks/<slug>/` if the module folder exists, `-2`, `-3` on a repeat; the call's path never picks one) with its app path on line 1, and writes only `{"task": path}` on the parent. The answer lists `homes`. Replay resolves references (`Task.from_ref`, `link_refs`). Tests: `item_tool.test.mjs`.
- **Filing (step 16):** every `tasks.add` also appends the same `{"task": path}` line to the caller's own task log (`ctx.caller_log`, or `resolve_log(caller)` from `page_tools(resolve_log)`; skipped with no caller, no task dir, or when that log is the parent). There is no default module home any more (it used to be the nearest folder with a readme).
- **Grouping rules** (returned as `rules` beside `describe()` on the first call; `RULES` in `page_tools.js`):
  - A refinement of an existing task goes into that task (add to its `tasks`, or set its fields). It does not become a new task.
  - New tasks are only for new asks.
  - A task stays in the session that files it; `module` tags it, `home` (only when the owner asked) moves it into the module's folder.
  - An idea to keep beside a module while designing is a note, not a task.
  - The tool files the session reference; never write it by hand.

## Queries: ask without writing (2026-10-23)

A **query** is a method or getter that only reads. A class lists them in `static queries` (`core/Item/Item.js`; `Item.describe()` returns them). A delta whose keys are ALL queries is answered at once and **writes no line**: `{ok, answer:{<key>:value}}`. The grammar is the same one ("a key naming a method calls it"): there is no `get` key. `target` walks into a child first (`target:["a"]`), then asks. A delta that mixes a query with a change (`{"cost":{},"title":"x"}`) is refused with `{ok:false, why}` and writes nothing: send two calls. The item tool holds one live replayed instance per file, so a query is a method call on memory (a 132-task session answers in about 135 ms).

```
item({path:"/framework/ai/sessions/2026/10/20/session-e00f55c9/", delta:{"summary":{}}})
item({path, delta:{"progress":{}, "cost":{}}})            // several queries in one call
item({path, target:["a"], delta:{"progress":{}}})          // the same, on the child "a"
```

`Task.queries` = `progress`, `cost` (this folder's agents, USD), `total_cost` (plus every child that has a folder), `duration` (ms, from the start/stop lines), `children` (child **sessions**: tasks whose `path` folder holds a session record), `summary` (id, title, state, completion, progress, counts by state, the open tasks only as id/title/state, cost, duration, children). Cost is computed by `Task.cost_resolver`, which `Agents.js` wires; with no Agents instance (a plain script) it reads 0.

**Session or Task? A session folder stays a Task with queries (decided 2026-10-23).** `core/Session` is the page-level view of a run (menu, settings, `AISession` cost and transcript), and `Session.completion` and `Task.completion` count the same thing with the same code. `class_of` already replays a session folder as a Task (`SessionRecord.log_file`), because the log holds task lines, `start`/`stop` spans and verbs that only Task understands. Switching to `Session` would lose those and need a second copy of `duration`, `cost` and `summary`. So `summary` and `children` live on Task and answer for a session's `session.jsonl` too (line 1's `{"session":{id,kind,…}}` is kept as `record`, so the summary reports the session id and kind). The alternative, a `Session` loader that extends Task, stays open if the view needs menu or settings through the tool.

Tests: `item_tool.test.mjs` (a query writes no line, a mixed delta is refused, the session summary with inline and referenced children, an array `tasks.add` is two tasks).

## A real Page, and lines refused before they are written (2026-10-23)

- **Page files** (`page.jsonl`): `page_tools.js` `page_class()` loads the real `core/Page/Page.class.js` in node, once. `Servex/agents/site-hooks.mjs` is a node resolve hook that maps site-absolute imports (`/framework/…`) to `public/`, so no DOM stub is needed; the few import-time browser touches (`location`, `document`, `Element`) are guarded in `Reader.js`, `View.js`. `Page.replay(lines)` replays a log (its `replay_new` marks the page as replaying, so a `file` line only records itself).
- **One list of part types:** `core/Page/parts/kinds.js` imports every part class and exports `PART_TYPES`. The browser (`Parts.js`, `ai/AISession/AISessionDetail.js`), the tool and `Page.test.mjs` all import it. A new part type is one import and one name there.
- **Refused before the write** (`page_refusal`, then `try_line` on the live page, for every page write): a key starting `_` (or `constructor`, `prototype`) anywhere in the delta; a `part-*` type that is not registered (the answer lists the real ones); a line the live page cannot apply. Only `part-*` types are checked: pages also hold plain data typed `card`, `note`, `request`, `task`, `question` that no class claims (the alternative, checking every type, would refuse all of those).
- **Any task line that would break replay is refused too** (`try_line`, `Refused`): the line is replayed on the live root BEFORE it is appended. A throw (for example `commits` in a child add: the getter has no setter) returns `{ok:false, why:"this line would not replay (…). Nothing was written."}` and the cached root is dropped. A `tasks.add` array is checked member by member on an empty root before any member is written.
- **A query key given a value is refused:** `{"summary":"text"}` is not an ask and cannot set; the answer says `summary is a query: it only reads and cannot be set`. `{}`, `true`, `null`, an array or an object are arguments.
- Tests: `node public/framework/core/Page/Page.test.mjs` (replay, unknown type reported, the tool refuses), `node Servex/agents/item_tool.test.mjs`, `node Servex/agents/page_tools.test.mjs`.
- **Subpage parent (kept from before):** a `page.js` parent is never edited; `Subpages.js` notes the child in the parent's `page.jsonl` and `Page.child` reads it (17c696fa6, 645ccbe33). The old test that expected a `children:` edit in `page.js` was stale and now asserts this.

## Special cases still in the tool (2026-10-28, build I)

Moved into classes so far: verdict strings (`Task.replay_line`) and improvements reinforce (`Improvements`). Still in `run_item_now`, each with where it should go:

1. **`tasks.add` with `home` or `process`** makes a folder on disk (`task_home`, `make_child`, `process_home`). Goes to a Task verb whose disk half is a node seam the tool sets (`Task.homes`, wired like `Task.resolver`); the line it leaves, `{"task": url}`, already replays.
2. **`move`** (`{"<id>":{"move":{"to"}}}`) calls `move_item` instead of writing a line. Goes to an effect verb the class declares (`static effects = ["move"]`) that the tool calls instead of writing, with the disk half in the same node seam. It must not be a plain method `set()` can reach, or a replay would move folders.
3. **`folder`** (`give_folder`): the same shape as `move`.
4. **`pages`** (`apply_pages`: subpage folders through `Subpages`, `Promote`): Page verbs with a node seam.
5. **The same-title refusal** on `tasks.add`: `Task.List.add`, once a browser add should refuse a repeat too (Improvements already merges in its own list).
6. **Request stamping** (`from` on an add to another agent's task) and the **`sessions` line**: node-side, they need the caller; a Task hook on add if a class should own them.
7. **`type` defaulting** (`task_type`: an unknown type becomes `Task`): `Task.List.make`.
8. **Session url routing** (a query on a session's page url reads its `session.jsonl`): a path rule in `resolve`, not a delta rewrite; it stays.

Test: `node Servex/agents/item-generic.test.mjs` (page writes through the live root with zero replays, a task added by verb, a dotted set three levels deep, random ids).
