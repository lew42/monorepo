- **The layer trap takes MARGINS too, not just `display`** (board-declutter, 2026-09-22). Rule 3 names the direction — a `@layer util` class beats a module's `@layer theme` rule at any specificity — but only shows it costing a `display`. `framework.css`'s `.flex > * { margin: 0 }` silently zeroed a `margin-inline-start: auto` on a head-row button, so the button sat mid-row at x=710 in a 1039px flex row and read as clutter, with the rule right there in the sheet and `getComputedStyle` reporting `0px`. Twenty minutes of hunting. Worth one clause in rule 3: the utility classes that set `display` also reset their CHILDREN's margins, so any auto margin, any negative margin, any spacing you write on a direct child of `.flex`/`.grid`/`.wall` is gone — drop the utility from the markup and own the display in the sheet, which is the fix the rule already prescribes.
2026-09-22 (dictate-silence) . the skill says to read framework.css before writing a declaration; it should also say WHY in the one sentence that would have saved this: an unknown custom property makes the whole declaration invalid, so `background: var(--accent)` — there is no `--accent` token in this framework — painted the level meter's fill TRANSPARENT with no error, no warning and no failing assertion. The numbers beside the bars updated correctly the entire time, four headless width checks passed, an overflow check passed, and only opening the screenshot showed the bars were never there. Two lines worth adding: (1) a var() you did not read out of framework.css is a silent no-paint, not a fallback — give every `var(--x)` in a background/color a second argument or verify the token exists; (2) the colour tokens that DO exist are `--ink --paper --lighten-1/2/3 --darken-1/2/3 --error --ok --warn --hot --radius`, and the ramp for a meter or a gauge is `--ok → --warn → --hot → --error`.
- **A custom property holding a PERCENTAGE cannot be handed to a child and still mean the same length** (layout-analysis, 2026-09-22). `--gutter-x: clamp(2em, 4%, 5em)` on `.page` resolves to 41.6px there and to 38.2px on a child using it for a negative margin, because a percentage resolves against each element's own containing block — and the page's content box is already two gutters narrower. Nothing throws; a full-bleed band just sits 3px in at 1280 and 5px at 1920 and reads as a hairline of the wrong colour. `core/Page/Page.css` already writes this down for the columns host ("`cqi`, never `%` … the inversion stays exact") but the css skill does not, and rule 4 ("prefer a token to a rule") actively encourages handing a token down. One clause: a token a CHILD will invert or subtract must be percentage-free. `@property` does not rescue it — `syntax: "<length>"` rejects a clamp containing a percentage, so the declaration is dropped and the initial value wins.
- **`getComputedStyle().getPropertyValue("--x")` hands back the TOKEN TEXT, never a length** (layout-analysis, 2026-09-22). Rule 6 says to smoke-test and read a computed style back; rule 1's last line says to verify a word by reading a computed style rather than inferring it. Neither says that an unregistered custom property has no computed length, so `parseFloat(getPropertyValue("--gutter-x"))` is `NaN` → 0, and a probe reports every page's gutter as zero while looking like it worked. The ways out, in order: read the page's own resolved `gridTemplateColumns` (its px numbers are ground truth — but strip the LINE NAMES first, `[bleed-start] 41.6px …`, or the first "word" parses to 0); or size a scratch element with `width: var(--x)` and read its rect back — which is exact only for a percentage-free token, for the reason in the line above.
2026-09-22 (ai2-master-detail round 2) . the skill's rule for a util-layer collision is "drop the utility from the markup, never fight it in the sheet" — and that advice is unavailable when the markup belongs to ANOTHER MODULE. I moved `ux/Dictate`'s info block (its own `div.c("ux-dictate-info flex v")`) into my composer as a popover and hid it with `display: none` in `@layer theme`; `.flex { display: flex }` in `@layer util` won, so the popover stayed laid out and invisible, `position: absolute` over the row below it, and swallowed every click on two buttons. The symptom is the expensive part: both buttons reported `checkVisibility() === true`, looked perfect in the screenshot, and `elementFromPoint` at their own centres returned `SPAN.ux-dictate-engine`; Playwright resolved the right element and then timed out after 30 s "attempting click action". Worth one line beside the existing util-layer warning: when you cannot edit the markup, hide with `visibility: hidden` + `pointer-events: none` instead — neither is a property any utility sets — and after hiding anything that overlaps, hit-test it (`document.elementFromPoint` at the centre of whatever is underneath), because `display` is the only one of the three that also stops taking clicks.
