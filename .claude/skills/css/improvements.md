# css — improvements

Any agent may append. One line each: `YYYY-MM-DD · what should change · why (the evidence)`.
A recurring line is a rule waiting to be written; the owner promotes.

- 2026-08-18 (panel-document): the skill sends you to read what CASCADES onto the element, but the thing that cost the hour was a property already on it — `container-type: size` on an ancestor. A size container may not be sized by its own contents: a flex column with `container-type: size` measured **0px while holding 963px** of children, which the parent's `overflow: hidden` then clipped away — nothing thrown, nothing to see, and every specificity check said the new rules were winning. Worth a caveat line: before making any box content-sized, read its own `container-type` back from the computed style.
- 2026-08-19 (ui-tree) · any new `<button>` needs the theme file read regardless of whether you touch color/type · `styles/layers/theme/lew42/lew42.css` styles every `button, .btn` in `@layer site` (CTA padding 0.7em 1.4em, uppercase, bold) — beats a component's `@layer theme` rule at ANY specificity, by layer order alone. A tree-view toggle glyph silently got 33-38px of padding and misaligned every sibling row; fix was to not use `<button>` at all (a plain clickable span). The skills ladder step 4 gates the theme-file read on "colour or type is in play" — a bare `<button>` IS in play even with no color/font-size written, because the site layer supplies both unconditionally.
- 2026-08-19 (playground-3-grid-toolbar) · a flex row of buttons squeezed below its content width does NOT overflow first — a button's own multi-word label ("+ grid") wraps onto a second line before the row does, since browser default flex-shrink lets an item shrink to its min-content, and wrapping text lowers min-content further than the label's rendered width. Silent, no error: 6 toolbar buttons at a fixed 540px column went from one 40px line to a two-line 76px mess just by adding 3 more buttons, nothing else changed. `white-space: nowrap; flex: none` on the item + `overflow-x: auto` on the container is "constrain the container, not the items" (§4) — but that rule doesn't name this specific failure mode, so it read as a wrap/overflow bug, not a shrink bug, until measured.
