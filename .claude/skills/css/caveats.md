# CSS caveats — what has bitten

One line each. Read the one that seems to apply; the detail is where the link points.

- **An unlayered rule beats every layer** at any specificity. Everything goes in a layer.
- **A layer name outside `base theme site util`** is appended last, past `util`, silently. `styles/readme.md`.
- **Overriding a `framework.css` rule is a bug report about `framework.css`** — de-escalate upstream (flatter selector, `:where()`, a token); never `!important` downstream. `styles/readme.md`.
- **Base-theme selectors stay flat** (one element, no descendant combinators) or a theme's `h2` can never win. `framework.css` header comment.
- **`page-<slug>` is stamped on every page**, so a module class `page-<x>` collides with any route slug `<x>` — `.page-catalog` broke the catalog Doc page. Guard every rule, not one. `ext/catalog/catalog.css`.
- **`.page.full` zeroes `--measure` and `--page-pad`**, and the title renders outside `content()`. `layout/caveats.md`.
- **A container query cannot restyle its own container**; the rule goes on a child. `layout`.
- **A `@container` (or `@media`) block is still ORDINARY CSS** — specificity and layer decide inside it; it is not an override. `.sections-hold { position: static }` inside a `@container` lost to `.sections-stuck .sections-hold` (0,2,0) outside it and a sidebar stayed sticky at 400, nothing thrown. Write the query's rules with the SAME selectors the unqueried words use (2026-09-05).
- **Load order inside `@layer theme` follows the IMPORT graph, not the file you are editing** — `blog.css` is appended by `View.stylesheet` when `Post.js` is imported, which is AFTER the importing module's own sheet, so `.templates-blog-hero { align-self: stretch }` at (0,1,0) lost to `.blog-hero` at (0,1,0). A fix aimed at another module's rule must OUT-SPECIFY it, not merely be written later: `.templates-blog > .blog-hero` (0,2,0) was the fix (2026-09-05).
- **framework.css's `max-width: 100%` on media** clamps an iframe you meant to be wider (it clamped `frame()` at 3440). `ext/DesignTool/readme.md`.
- **A util-layer `:first-child { margin-top: 0 }`** beats a component's top margin — it is the highest layer. Live collision worth knowing: it kills the BLOCK half of every bled block in a column, because `Page.css`'s theme-layer `.page-column-prose > .bleed:first-child { margin-block-start: -pad-y }` loses to it — measured, the `margin-inline: -30.72px` applied and the `margin-top` did not, while the losing rule still matches and looks correct in devtools (2026-09-05). **The `:last-child` half reaches just as far** — it cancelled `ext/tabs`'s `.tab { margin-bottom: -1px }` on the last tab of every strip, and because a `.tab-bar` stretches its items that one low tab made every sibling a pixel taller (37.09 vs 36.09px, both rules looking correct in devtools). It reaches a COMPONENT'S OWN CHILDREN, not just page-level blocks — restate the margin in `util`, since `util` is the layer that took it away (ui-theme, 2026-09-06).
- **A utility class on a box you also want to HIDE is the same trap in a worse costume.** `.omnibox-chips` styled with the `flex` utility (`@layer util`) plus a module rule `.omnibox:not(.open) .omnibox-chips { display: none }` (`@layer theme`) left the chips on screen permanently — `display` loses exactly like a sizing property does, but the failure is invisible rather than merely wrong, since nothing looks broken until you notice the thing never hides. Drop the utility from the markup and declare the three lines yourself (omnibox-search, 2026-09-06).
- **`el.hidden` loses to any `display` your own rule sets.** The browser's `[hidden] { display: none }` is a UA rule at the bottom of the cascade, so `.ai-chat-rail { display: flex }` in `@layer theme` beat it and the "hidden" rail measured 54px tall with `hidden` true in the DOM — nothing thrown, reads like a JS bug. Any box you give a `display` needs its own `.thing[hidden] { display: none }` (asks-critic, 2026-09-17).
- **A `var()` that resolves to an INVALID value does not fall back and does not throw** — the whole declaration computes to its INITIAL value instead. `ext/tabs` sets `.tab-panel { --measure: none }`, so `max-width: var(--measure, 40em)` inside a tab panel became `max-width: none` — the fallback never fires (the variable IS defined), and `getComputedStyle` just reports `none`. Before reading a token in a component, read it back on the ELEMENT itself, not the container you declared it on — anything in between may have redeclared it (ai-log-asks, 2026-09-17).
- **`--measure` is `40em`, and an `em` is the ELEMENT'S OWN font-size** — so a box with a bigger font than its siblings silently widens its measure too: `.color-takeaway { font-size: 1.15em; max-width: var(--measure) }` resolved to 622px where a `1em` sibling resolved the same token to 542px, 100px apart on a page about things lining up. A length token in `em` is not one number, it is one number per font-size — name the scale and divide it back out (`--takeaway-scale: 1.15; max-width: calc(var(--measure) / var(--takeaway-scale))`) (polish-critic, 2026-09-17).
- **Every measure cap on this site is a DIRECT-child selector, so anything nested inside a wrapper escapes all of them.** A `<details>` fold's paragraphs (`details.md-details > div.md-details-body > .md > p`) sit two levels past what `.page-column-prose > :is(p, h1…)` matches, so `max-width` computed to `none` and one ran 3,342px wide at 3440. After wrapping prose in ANY box, read `max-width` back off a paragraph inside it (polish-critic, 2026-09-17).
- **`--wash` IS the page ground, so a `--wash` box on the page paints nothing.** `.app { background: var(--wash) }` is the page itself, so three cards built with `background: var(--wash)` measured identically to the page behind them — invisible, no error. A token only means something RELATIVE TO THE GROUND IT LANDS ON; a box that must read as a box takes `--surface` plus a real border (what `.surface` does), and the check is to read back both the box's AND its parent's computed `backgroundColor` (decisions-system, 2026-09-17).
- **A relative `font-size` REPLACES the cascade's answer, and then is itself relative to the PARENT, not to what the element already was.** `font-size: 1.3em` in `@layer theme` did nothing at all against the skin's heading rule (lost the cascade); moved to `@layer util` (won the cascade) it made the heading SMALLER — 34.9px to 20.2px — because `1.3em` means 1.3× the parent, not 1.3× whatever the theme had already sized the element to. CSS cannot scale an element's own computed font-size; `zoom` can (`ext/Panel/tools.js` already explains why `zoom`, never `transform: scale()`) (editor-select, 2026-09-18).
- **On this site `rem` and `em` are NOT "both roughly 16px" — `rem` is a CONSTANT and `em` is the one unit that tracks the viewport.** `framework.css` puts the site's entire fluid type clamp on `body`, while `html` stays the browser's fixed 16px — so anything sized in `rem` (always relative to `html`) is flat at every width, and only `em` (inherited down from `body`) is fluid here. A `--sidebar-w: 18rem` default, copied from a lab page that never inherits the body clamp, measured a dead-flat 288px at 400, 1280 AND 3440 alike; `20em` (matching the sidebar's older token) gave 241/256/288px. Before choosing `rem` for anything meant to scale with the page, check what element the site's own fluid clamp actually sits on (site-sidebar-tree, 2026-09-18).
- **A component that ALSO scales its own font-size by `var(--size)` double-multiplies every framework CONTROL nested inside it.** `framework.css` already gives every button/input/select/textarea its own `font-size: calc(1em * var(--size))` — the size standard's whole point — so a board that sets `.my-board { font-size: calc(1rem * var(--size)) }` for its own density switch feeds `--size` into every nested control a SECOND time. Measured: a reply textarea and its Send button rendered at 9px (0.75 × 0.75 = 0.5625) beside text correctly floored at 12px right next to them. "Put `.size-small` on a toolbar and every control inside it is 0.75×" is true only ONCE per subtree — reset `--size` back to 1 on any subtree that holds real framework controls before adding a second `--size`-reading `font-size` rule above it (ai-v2, 2026-09-19).
- **A backtick anywhere inside `` css(`…`) `` kills every page** — and where it sneaks in is a `/* */` comment naming a class in backticks, the way every other comment in the repo does; inside a `css()` template, comments use plain quotes. You cannot see it: every page renders blank and the console holds one `SyntaxError` naming no file. `.claude/hooks/syntax-guard.mjs` now blocks any `.js` write that stops parsing — believe it over your eyes (it happened twice in fifteen minutes on the live site, 2026-09-19).
- **`**/` closes a block comment** in a `.css` file too.
- **A stylesheet loaded before framework.css** in a hand-written html file: link `/framework/framework.css` first (`fly/index.html`).
- **A `background:` SHORTHAND on a `select` wipes the arrow** — it is a background-image; recolour with `background-color` only. The arrow sits `right 0.5em center` from the padding box (never `100%` + content-box origin, which walked it onto the text of every shrink-to-fit select). `framework.css`, at the rule (2026-08-28).
- **A `<select>` in a flex row is a flex item** — it shrinks below its own content, and writing `padding: 0.2em 0.4em` on it also removes the end reserve the browser draws its arrow in. Both make a control that was sized to fit clip its longest value ("Top tabs" reading "Top tab") with nothing in the CSS that looks like a width. `flex: none` and *no* width, font-size or padding shorthand — let the browser size it (2026-09-05).
- **An icon font's line box is its own `font-size`, not the surrounding prose's** — so in an `align-items: flex-start` row an icon beside a line of text sits ~5px above it. `line-height: inherit` on the icon is the fix; a margin nudge is not (it breaks at the next type scale) (2026-09-05).
- **A reset rule only resets what it names.** `pre > code { padding: 0; background: none }` did not reset the `box-shadow` later added to `code {}`, so the inline hairline drew a light rectangle inside every dark code block — for four hours, on every page with a sample. **Adding a property to a base rule? Grep for the rules that reset it.** One element can live in several very different contexts; see the CSSDoc work, `ai/2026-08-18/cssdoc/`.
- **Paint order is not the cascade — a positioned element beats a static sibling wherever they overlap**, whatever the source order; and a block-level child is full width even when it only declares `min-width`. `position: relative; z-index: 2` on an in-flow `+` turned a 24px glyph into a full-width bar covering both sibling chips; class list and computed `display` looked fine. Diagnose with `elementFromPoint(centre)`, not the cascade. `ext/Playground` `.pg-add`, 2026-08-27.
- **A `position: sticky` GRID ITEM is constrained by the grid CONTAINER, not by its own grid area** (Chromium) — a capped, sticky middle column still painted over the file and code boxes below it, because those were rows of the same grid; `max-height` fixed the overhang and not the covering. The fix is structural: make the boxes siblings under the card, so the card ends where its columns end. Nothing in the sheet looks wrong (measured at 3440, 2026-09-05).
- **Never split a `selectorText` on `,`** — `:is()`, `:where()`, `:not()` and `:has()` contain commas. `:where(p, li, td, th, dd, blockquote, .md) a:visited` shreds into seven fragments, nothing throws, and the output looks plausible. Split at paren depth 0; strip `::pseudo` after, not before.
- **A block box with `aspect-ratio` AND `max-height` transfers the height cap to its WIDTH** — a 16/9 canvas capped at 62vh sized itself 992px inside a 1279px row, grey beside it. Before giving a box a ratio, ask what caps its other axis (2026-08-29).
- **Two adjacent line-name groups in a track list (`[a-end] [b-start]`, or `[a] [b] 2em`) are a parse error** — the whole track list is dropped, named placements fall through to implicit lines, nothing is logged; track 1 measured 0px. A child's `grid-column: a` then computes back as the literal STRING `"a"` (browsers echo an unresolved custom-ident), which looks like it worked until you check the layout. Multiple names on one line are written `[a b]`, never `[a] [b]`. After any multi-value track list, bisect with `CSS.supports("grid-template-columns", value)` (strip `var()` out first — it always reports supported) before trusting `getComputedStyle` on a live element, and count the tracks you got back (2026-08-30, recurred 2026-09-18 on `core/Page/Page.css`'s RELATED block).
- **`em` inside a container query resolves against the CONTAINER's font size** (16px at 1920, 18px at 3440 here) — a threshold picked by dividing viewport widths lands wrong; one box read 96.4em and 165.9em. Measure the container with `getComputedStyle`, or write the breakpoint in `px` (2026-08-30).
- **`light-dark()` resolves where the value is USED**, reading that element's `color-scheme`, not where the custom property was declared — one `--x: light-dark(a, b)` on a wrapper gives two answers in two children, and a box that is dark in both modes fixes every token inside it with one `color-scheme: dark`. Verified: `--fill-a08` read `rgba(0,0,0,0.08)` and `rgba(255,255,255,0.08)` at once (2026-08-30).
- **Spacing is a clamp × one knob, never a constant** — `:where(*)` sets `--pad` / `--gap` / `--flow` directly from framework.css's clamps × `--size` (`.size-small` 0.75 · `.size-regular` 1 · `.size-large` 1.5). Every `var(--pad, …)` / `var(--gap, …)` fallback reads that value, since `:where(*)` gives every element its own; a THEME retunes the clamp itself, never a per-element override. Never a new `var(--gap, 1em)` literal; a component's own constant converts as `calc(var(--gap) * <the old em number>)`; never a `%` inside a GAP token (percentage row-gap is undefined against auto height — `vw` there, `%` only in padding). The clamps and the ladder: [/framework/styles/system/studies/size/](/framework/styles/system/studies/size/).
- **`--pad` is a PERCENTAGE of the containing block, so it sits pinned at its `1em` floor until that block is about 1292px wide** — `clamp(1em, 2.6% - 1.1em, 4em)`. Measured 2026-09-19 at 400/1280/1920/3440: a `.pad` box is **14 / 15 / 16 / 18px** inside a card, a rail or a column, and **14 / 16.7 / 32.3 / 69.6px** in a full-width page region — the same word, a 4.3× spread, nothing in the CSS to show it. Padding that must grow with a NARROW box does not come from `--pad`.
- **A `%` inside `calc()` stays a `%` in the COMPUTED value only on a box with no layout yet** (zero size — an inactive nested `.page` is the common case), so `getComputedStyle(el).paddingLeft` there reads back as a `calc(…)` string and `parseFloat` gives `NaN`. Refined 2026-09-19 (`card-word`): on a box that IS actually painted (`getBoundingClientRect().width/height > 0`), `getComputedStyle` DOES resolve `--pad`/`--pad-card` to a real px number — CSSOM's "resolved value" rule for padding returns the USED value when one exists. Measure geometrically (an inner marker's left edge minus the box's) when the box might not be laid out, or when you want one method that is never wrong; `getComputedStyle` is fine, and simpler, once you've already filtered to real painted boxes.
- **`--muted` is a PERCENTAGE, not a colour** — framework.css defines only `.muted { color: color-mix(in srgb, currentColor var(--muted, 75%), transparent) }`, so `color: var(--muted)` is silently invalid and the text renders at full strength; ask for the CLASS. `--text` does not exist at all (2026-09-04).
- `.h4` (and the heading utility classes) are uppercase and letter-spaced in this theme: `span.c("h4", "core/Layout")` printed CORE/LAYOUT. A path or a code name never takes a heading class; use `.small.muted` or a `code` element (layout-study, 2026-09-06).
