2026-09-17 (pages-in-d1) . add to the "Never edit outside your fence" guidance: a site-wide error found while proving your OWN page may not be your bug. Every page on the shared dev harness threw `SyntaxError: Invalid left-hand side expression in postfix operation` mid-task; bisecting with `node --check` across all of `public/` traced it to `public/framework/ui/decision/decision.js`, an untracked file belonging to a concurrent sibling task (`decisions-system`), imported unconditionally by `ui/ui.js` -> `app.js` so it broke every route, not just mine. 2026-09-18 (imagine-move-3) . two traps worth naming for any "rewrite N links across the repo" brief, found the expensive way. (1) A scoped `sed` regex meant to collapse a deleted url's deep sub-paths used a character class that excluded only quote/paren/space — backtick, comma and period were NOT excluded, so it silently ate through markdown inline-code backticks and even whole `[text](url)` link syntax on ~22 files, corrupting prose that had nothing wrong with it. `rg -n` for a truncated-backtick signature (a stray `` `/newpath/ `` with no closing backtick before end of line) after ANY sed that touches markdown/JS-with-template-literals, before moving on - one of the mangled lines was inside a `` md(`...`) `` JS template literal, where an unescaped stray backtick would have broken that whole module, not just the prose. (2) A directory move that adds ONE MORE level of nesting (e.g. `imagine/sections/stack/` at depth 2 becomes `layouts/labs/sections/stack/` at depth 3) silently breaks any RELATIVE import inside the moved tree that reaches OUTSIDE it (`../../paging/presets.js` pointed at the right place before, the wrong place after) - same-realm relative imports (`../Blog.js`) stay correct because both ends moved together, but a cross-realm relative import does not. `grep -rn 'from "\.\./\.\.' <moved-tree> --include="*.js"` catches it in seconds; a same-realm single `../` is fine, anything with two or more `../` crossing into a different top-level realm needs checking by hand. Both bugs were invisible to a plain `rg -c` link recount (the count looked complete) and only surfaced under an actual headless crawl - crawl before declaring a move done, not just recount.
2026-09-18 (reply-in-place) . add to the headless-proof guidance: with other agents working, a headless proof that spans more than a few seconds WILL be interrupted, and the failure does not look like one. Any agent creating a task dir rebuilds `directory.json`, which the dev server treats as a site change and full-reloads every open tab - nine reloads inside one 150s window, measured. Each reload destroys the page's JS context, so an in-flight browser-side operation (here, a `claude -p` turn whose answer the browser was going to file) is simply lost; the turn itself completes on the server and costs real money, and Playwright reports only a `waitFor` timeout with a quiet "navigated to ..." buried in its call log. Three real turns burned before I spotted it. The fix is one line in the probe, after load: `page.evaluate(async () => { const S = (await import("/framework/dev/Socket/Socket.js")).default; S.prototype.reload = () => {}; })` - it suppresses live reload in the probe's own tab only, touches no server and no other tab. Also worth the skill saying: `page.on("framenavigated", ...)` as a counter turns this from a mystery into a number.
2026-09-18 (imagine-move-2) . two more findings for any "delete/move a directory, keep the old address alive" brief. (1) A directory being deleted (not just moved) can be the SOLE definition site of a CSS class every one of its own children's `preview()` overrides depends on for their thumbnail rendering, imported nowhere explicitly - it worked before only because the deleted parent page's own `View.stylesheet()` call happened to load it once for the whole subtree. Deleting the directory would have broken every sibling's card thumbnail sitewide with zero console error and zero 404 (a plain `<img>` just doesn't crop/fill its box) - nothing in a headless crawl catches a wrong-but-present image. Caught only by grepping the class name itself (`grep -rn "the-class-name" public --include=page.js`) across the WHOLE repo before deleting the file that defines it, not just inside the directory being moved. Moved the one rule to the nearest true shared ancestor (`core/Page/Page.css`, beside the box class it decorates) since the children now live in five unrelated trees. (2) The brief's own suggested link-count command (`rg -c "old/url/"`, trailing slash required) undercounted real links by ~40% against a rewrite script's own boundary check (next-char-not-a-word-char, so it also catches a bare mention with no trailing slash) - a JSON `"source"` field and a few `css-scopes.txt` lines had no trailing slash and were invisible to the suggested count but were still live, working references. Recount with the same boundary logic the rewrite uses, not the simpler suggested pattern, before declaring the two numbers agree.
2026-09-19 (blunder-critic) . the "never kill or restart the owner's/mastermind's server, your own private server is yours to run" guidance is missing what happens when your OWN private server dies on its own, mid-task, from a SIBLING agent's edit: a supervisor here restarts the whole Server/ child process on any change under `Server/`, and a concurrent agent's in-flight fix to `Server/plugins/SocketServer/LiveReload.js` left it briefly crash-looping (`this.socket_server.sockets is not iterable`) - my private :8133 died with no action from me, `curl` returned nothing, `netstat` showed no listener. The right read, in order: tail your own server's log file first (it names the exact crash and often a self-documenting comment explaining it, as this one did), confirm the cause is a shared file outside your fence rather than anything you wrote, wait/re-check rather than "fix" someone else's in-flight edit, then once the log shows the fix landed, start a FRESH `PORT=<port> node server.js` yourself and note the new real PID - this is not "restarting the server" in the forbidden sense (that rule is about the owner's :80 and the mastermind's :8123), it is relaunching your own private one after it died for a reason outside your control. Also: the same supervisor pattern means the owner's and mastermind's server PIDs can legitimately CHANGE mid-session for the same reason (their child got auto-restarted too) - check the PORT is still answering before assuming a PID mismatch means something broke.

2026-09-19 (dashboard-next) . the "reload hold... take it before your first write, load the page headless before releasing" guidance is missing the one fact that actually matters here: THE HOLD DOES NOT STOP THE SITE'S OWN PAGE-HEALTH CRAWLER FROM RE-LOADING A PAGE. It only suppresses the LiveReload signal to browser tabs that are already open. A new shared module (`ai/v/3/compose.js`) shipped with a relative import one `../` short; it parsed fine (`node --check` cannot catch a wrong import path, only a syntax error) and I did not load a page headless before moving on to the next file in the same batch — the health crawler found the 404 and blanked the owner's whole live site for about 80 seconds before the mastermind fixed it. The actual guard is doing the headless load YOURSELF, every batch, not trusting the hold or `node --check` to have covered it — `node --check` proves a file PARSES, never that its imports RESOLVE. Second, sharper lesson: a file the DEV BAR imports (anything reachable from `DevBar.js`/`tools.js`) is loaded on EVERY page of the site the instant the rail opens, not just the one page you are building for — treat any such import of code built for one page as lazy-load-behind-a-try (`await import(...)`, captured host box first per the "no DOM after an await" rule) rather than a static top-level import, and prefer root-absolute paths (`/framework/...`) over relative depth for anything reused across more than one directory, so a miscounted `../` cannot happen at all.
2026-09-19 (v3-timeline) . the reload-hold guidance says the hold "expires by itself after five minutes if you forget" as reassurance, but says nothing about what happens when a batch legitimately runs LONGER than that (debugging a live behavior, not just writing files) - it expired silently mid-batch twice in one continuation here (once during a ~10-minute dual-mount investigation, once during a resurfacing proof), with `hold.mjs off` later reporting "nothing removed" as the only signal it had lapsed. No damage happened either time only because I re-verified the real site by hand after each expiry, not because anything in the skill told me to. Also found the harder way: forgetting to take a NEW hold at the start of a follow-on batch (treating "I already held earlier in this session" as still covering a later, separate round of edits) let one real edit through unheld - the owner's site 404'd on a newly-imported file for ~14 seconds before the health-guard hook caught it. Worth a line: treat the hold as needing a fresh `on` call at the START of every distinct batch of writes (never assumed to carry over from an earlier one), and re-issue `hold.mjs on` partway through any batch expected to run past a few minutes (it is idempotent - "Holders now: 1" either way) rather than trusting the 300s window to outlast real investigation work.
2026-09-19 (health-revive) . the skill is silent on how to leave a process running past the end of YOUR OWN task (not the owner's or mastermind's server - a supervisor a brief explicitly asks to survive being killed and outlive the session). A plain `node x.mjs &` via the Bash tool is tracked as a background task tied to this tool session and got reported "failed" the moment I killed it on purpose partway through testing - not proof it would die with the session, but suspicious enough not to trust for the real, final launch. What worked, verified: `PowerShell Start-Process -FilePath node -ArgumentList "<script>" -WorkingDirectory <repo> -WindowStyle Hidden -PassThru` - confirmed alive (via its own heartbeat file and `tasklist` by the real PID) well after the tool call that started it returned and after unrelated later tool calls ran. Worth a line in the skill: use `Start-Process -WindowStyle Hidden` (or the bash-tool equivalent, `disown`) for anything a brief says must outlive the task, never the run_in_background Bash flag alone.
