2026-09-18 (imagine-move-3) . two traps worth naming for any "rewrite N links across the repo" brief, found the expensive way. (1) A scoped `sed` regex meant to collapse a deleted url's deep sub-paths used a character class that excluded only quote/paren/space — backtick, comma and period were NOT excluded, so it silently ate through markdown inline-code backticks and even whole `[text](url)` link syntax on ~22 files, corrupting prose that had nothing wrong with it. `rg -n` for a truncated-backtick signature (a stray `` `/newpath/ `` with no closing backtick before end of line) after ANY sed that touches markdown/JS-with-template-literals, before moving on - one of the mangled lines was inside a `` md(`...`) `` JS template literal, where an unescaped stray backtick would have broken that whole module, not just the prose. (2) A directory move that adds ONE MORE level of nesting (e.g. `imagine/sections/stack/` at depth 2 becomes `layouts/labs/sections/stack/` at depth 3) silently breaks any RELATIVE import inside the moved tree that reaches OUTSIDE it (`../../paging/presets.js` pointed at the right place before, the wrong place after) - same-realm relative imports (`../Blog.js`) stay correct because both ends moved together, but a cross-realm relative import does not. `grep -rn 'from "\.\./\.\.' <moved-tree> --include="*.js"` catches it in seconds; a same-realm single `../` is fine, anything with two or more `../` crossing into a different top-level realm needs checking by hand. Both bugs were invisible to a plain `rg -c` link recount (the count looked complete) and only surfaced under an actual headless crawl - crawl before declaring a move done, not just recount.
2026-09-18 (reply-in-place) . add to the headless-proof guidance: with other agents working, a headless proof that spans more than a few seconds WILL be interrupted, and the failure does not look like one. Any agent creating a task dir rebuilds `directory.json`, which the dev server treats as a site change and full-reloads every open tab - nine reloads inside one 150s window, measured. Each reload destroys the page's JS context, so an in-flight browser-side operation (here, a `claude -p` turn whose answer the browser was going to file) is simply lost; the turn itself completes on the server and costs real money, and Playwright reports only a `waitFor` timeout with a quiet "navigated to ..." buried in its call log. Three real turns burned before I spotted it. The fix is one line in the probe, after load: `page.evaluate(async () => { const S = (await import("/framework/dev/Socket/Socket.js")).default; S.prototype.reload = () => {}; })` - it suppresses live reload in the probe's own tab only, touches no server and no other tab. Also worth the skill saying: `page.on("framenavigated", ...)` as a counter turns this from a mystery into a number.

2026-09-22 (worktree-design) . the never-list warns hard about `git stash`, `checkout --` and `reset`, but says nothing about `git worktree remove`, which turns out to be just as destructive here for a reason no one would guess: `Server/worktree-up.mjs` links the new worktree's `node_modules` to the MAIN checkout's real one with a Windows junction, and `git worktree remove` walks THROUGH that junction and deletes the target. Running the repo's own supported script and then its own supported teardown emptied the main tree's `node_modules` - 68 packages, express among them - with no error, no warning and nothing in `git status` (node_modules is gitignored). The five dev servers running off that tree did not fall over, because they already had their modules in memory; the damage would only have surfaced at the NEXT restart, which any sibling agent saving a file under `Server/` triggers, as `Cannot find package 'express'` on the owner's live site. Repaired in one second with `npm install` from the package-lock.json already in the tree (`git diff package-lock.json` empty afterwards). The 2026-09-19 worktree-study log had already recorded this exact failure and the script shipped the junction anyway, so the lesson is not "the script has a bug" but two things worth a line each in the skill: (1) before running ANY repo script that creates or removes a git worktree, check whether it symlinks or junctions anything out of the main tree, and if it does, prefer `npm install` in the worktree (measured 1.0 s here, 871 ms in the prior study) - a link into a tree you are about to delete is never worth the second it saves; (2) after any command that removes a directory tree on Windows, verify the things that tree LINKED TO are still there, not just the things it contained - `ls node_modules | wc -l` before and after would have caught this instantly, and I only found it because I happened to re-read an unrelated prior study minutes later.

2026-09-22 (reuse-audit) . the "kill your private server by its real PID from netstat" rule is right but incomplete, and following it exactly LOOKS like it failed. The root server.js is a SUPERVISOR: the PID listening on your port is a forked Server/run.js child, and killing that child makes the supervisor immediately respawn a new one on the SAME port, so the netstat check straight afterwards still shows a listener (a different PID) and reads as "the kill silently missed", which is the exact failure this skill's own parenthetical warns about. Kill the PARENT. `powershell -NoProfile -Command "Get-CimInstance Win32_Process -Filter \"Name='node.exe'\" | Select-Object ProcessId, ParentProcessId, CommandLine | Format-Table -AutoSize -Wrap"` shows the whole tree: find the `Server/run.js` row whose ProcessId is your netstat PID, kill its ParentProcessId (the `server.js` row) FIRST, then the child. Measured: killed child 37352, port still listening as 26856 two seconds later; killed parent 41552 then child 26856 and the port went free. Worth a clause on the never-list's kill guidance, because the machine currently runs ~10 of these supervisor/child pairs at once and picking the wrong parent kills a sibling agent's server.

- **Landing a worktree: `carry-in` is a TAG as well as your branch's commit, and the tag wins.** The brief says `git diff --binary carry-in`, but `refs/tags/carry-in` was left by an earlier worktree and points somewhere else entirely — `git diff carry-in` built a 77-file, 12,592-line patch carrying six other agents' work, where `git diff HEAD` built my 9 files. Run `git rev-parse HEAD carry-in` first; if they differ, diff against HEAD. Second half, same landing: `git apply --3way` reads the INDEX, and everything in the main tree is uncommitted, so it fails `does not exist in index` / `does not match index` on any file a sibling has touched. What works is to split the patch — a plain `git apply` for the files you CREATED, and the files you MODIFIED edited by hand against the main tree's own current text (a sibling had already renamed the function my one Edit sat in).
