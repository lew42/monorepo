# The LAN rule: a phone gets push traffic, never commands

The dev socket carries `rpc:cmd` (runs a shell command) and file writes, so it must never be open to the network. A phone on the home Wi-Fi still needs reload and live updates, so the server splits the two:

- **Loopback** (this machine) keeps everything.
- **A private LAN address** (`10.*`, `192.168.*`, `172.16`–`172.31`) may connect, but `Server/plugins/SocketServer/Socket.js` only lets it send what is in its one list, `LAN_OK`: `hello`, `subscribe`, `unsubscribe` and `query`, and a `query` only for a source in `LAN_QUERY` (`sessions`, `tasks`). Every other message (`cmd`, `write`, `append`, `ask`, `rm`, `move`, a `query` of any other source…) is refused, logged as `socket: REFUSED …`, and answered with a `refused` reply so a waiting `send()` does not hang.
- **Anything else** (a public address, a forged origin) is refused at the upgrade, as before.

**The site tier (through the gateway).** `Server/SiteGateway.mjs` dials the dev server at this PC's own LAN address and marks every request `x-lew42-remote`. `Socket.js` believes that header only from one of this PC's own addresses, so a phone on the Wi-Fi cannot send it to gain anything. Such a socket gets the LAN list plus one more method, `append` (one JSONL line, only to a `.jsonl` under `public/`, schema-checked by `Append.js`), so page edits and dictation work from `https://monorepo.lew42.com`. `write`, `rm`, `move`, `cmd` and `ask` stay refused. It may append to any `.jsonl` under `public/`, so the key cookie (or Cloudflare Access later) is what guards it. The test is `Server/plugins/SocketServer/Socket.test.mjs`. The server also sends a protocol ping every 25 s so Cloudflare does not drop a silent socket (about 100 s idle).

**The rule (2026-10-17): the client tries everywhere; the server decides.** `Socket.js` connects on every host (`wss:` on https) and has no allow-list. A peer the server refuses (a static host, a tunnel, a forged origin) backs off to a minute, says so once on the console, stays quiet, and gives up after about five minutes; `send()` and `request()` return at once where there is no socket, so nothing parks. Reload, CSS swaps and JSONL tails go server to client, so the phone gets them without a poll. Widening what a LAN peer may *send* is a security change: add only read-only methods that return data from files under `public/` and never run or write anything. `query` is one: it reads an in-memory index (`ext/Query`), which is the same data the phone can already fetch as `index.json`; a new query source stays closed to the LAN until it is added to `LAN_QUERY`. Proof, 2026-10-17, headless from `http://10.0.0.135`: a `tasks` query returned rows, `/live/now/` showed Last landed, `cmd` and a query of an unknown source were both `refused`.

**https too.** A phone needs https for the mic, so the dev server also attaches the socket to its https listener (`Server/plugins/HttpsLan.js` emits `https`, `SocketServer.attach()` adds a second `WebSocketServer` behind the same `local_only` gate). Before that, `wss://<lan-ip>:<port+10000>` got a plain 200 and never connected. Proof, 2026-10-17, headless over `https://10.0.0.135:<port+10000>`: connected on `wss`, `cmd` answered `refused`, a JSONL tail arrived in 9 ms, the `/live/now/` view redrew 1.3 s after a session folder's `cache.jsonl` grew; a forged `https://evil.example` origin got 401.
