# Recite: decisions

Built 2026-11-01 in the voice-recite task ([requirements](/framework/ai/sessions/2026/10/20/session-e00f55c9/voice-recite/requirements.md), [plan](/framework/ai/sessions/2026/10/20/session-e00f55c9/voice-recite/plan.md)).

- **Kokoro-82M on the CPU, not a GPU model.** It reads 6x faster than real time on this CPU (11 s of speech in 1.7 s), so it takes no VRAM from Whisper (2 GB) or the local LLMs. Rejected for now: Piper (more robotic), Chatterbox or XTTS (3–4 GB of VRAM, about real time; the option if a cloned voice is wanted). The server's `/speak` route would stay the same.
- **The names are the owner's:** `Voice` is one voice or persona, `Recite` is the overall control. `Voice` already existed (the browser's speechSynthesis), so it was extended, not duplicated (law 6).
- **One `<audio>` element, not Web Audio.** The element keeps its place when paused, keeps playing with the screen locked, and gives Android's lock-screen and headphone controls (Media Session). Web Audio gives none of those.
- **Sentence by sentence, two ahead.** The first sentence is kept short, so the first sound comes in about 0.4 s. Each sentence's length comes back in the `X-Recite-Seconds` header, which builds the timeline for back 10 s.
- **Barge-in in two steps.** A level alone pauses for wind or a truck, so a loud moment pauses at once and Whisper decides. Whisper's silero VAD returns no text for noise (tested with `silence.wav` and a fake wind clip), and reading resumes. After a noise verdict the trigger level rises to that noise and fades over about 10 s, so steady wind stops pausing it.
- **Echo is checked by words.** If most of what Whisper heard is in the sentence being read, it was the speaker, and reading resumes.
- **The chat's wire, not a chat view.** Recite hears replies from the session's live wire (`Session.stream`), which feeds all three chat views, so it works whichever view is on. Advised by the dictation-map task ([dictation-notes.md](/framework/ai/sessions/2026/10/20/session-e00f55c9/voice-recite/dictation-notes.md)).
- **Never two mics.** With the chat's own mic on, barge-in listens to that mic's level, and the owner's line arriving on the wire is the check (no line in 5 s means noise).
- **Read new replies is on by default, on a phone and a PC alike** (the owner, 2026-11-01). The 🗣 button turns it off, and that choice is remembered on that browser. The first tap anywhere on the page unlocks sound.
- **The karaoke playhead marks text, it does not rebuild it** (2026-11-01). `Recite.Highlight` lights the sentence and word with `CSS.highlights`, so a chat that redraws a bubble is never fought over, and nothing is written into the page. The word is estimated (each word's share of the sentence's seconds, by length), because Kokoro returns no word timings. *Alternative:* wrap each word in a span (works in every browser, but every chat view would need to cooperate); exact timings from an engine that gives them (a later engine can supply `c.words` and `fraction()` reads it).
- **Turn-taking: `chunks` is one running queue across replies, not reset per reply** (dictation-v3, 2026-11-01). A reply that arrives while another is playing (or waiting) is appended with `queue()` and never cuts it off; only `read()` (the public "start over now" call) empties the whole queue — a dropped barge-in question cuts out just the one reply it interrupted (`drop_heard()`, below). A freshly queued reply never starts over the owner's own voice: `queue()` checks `barge.speaking()` and, if true, `start_or_hold()`/`check_wait()` poll (about every 80 ms) until `turn_wait_ms` (1.5 s) of quiet, then plays. The poll is a local mic-level timer read straight off `BargeIn.level`, not a network fetch, so "stream, don't poll" does not apply to it. *Known limit, not fixed here:* `chunks` (and its rendered audio blobs) only shrinks on a full `stop()`, so a very long session without an interruption holds every reply's audio in memory; deferred as low-risk (a session is bounded by a page reload in practice) rather than adding chunk-eviction now.
- **A barge-in interruption pauses; a question drops only the reply it interrupted, never what is queued behind it.** `BargeIn.heard_speech(text)` is the one place real speech (not noise, not echo) is decided: text ending in `?` means a new answer is coming, so the interrupted reply is dropped (`recite.drop_heard()`) rather than resumed into the new one; anything else schedules an auto-resume (`schedule_resume()`/`try_resume()`) once about `quiet_ms` (1.5 s) of silence passes — reset on every further loud frame while the chat's own mic is open, so a long aside does not get cut back in on. The resume itself restarts the cut sentence from its start (`resume(true)`), not mid-word, since the owner likely did not hear the first part either; a manual tap (the bar's Play button) still continues from exactly where it paused (`resume()`, no argument).
- **"Or a reply to it is coming" does not depend on the "?" ever arriving.** The trailing-"?" check is a fast, immediate signal from the owner's own line; `Recite.drop_heard()` is the general one — called from `partial()`/`final()` whenever a *fresh* reply starts arriving while the old one still sits paused (`state === "heard"`). A reply arriving IS the proof an answer is coming, so a spoken question Whisper happens to punctuate with a full stop is still covered, with no text heuristics on the owner's words. Both paths funnel through `BargeIn.cancel_resume()` (clears the quiet timer, drops `state` back to `"off"`) before `recite.drop_heard()`, so the mic resyncs cleanly either way.
- **`drop_heard()` cuts out one reply's chunks, not the whole queue.** Every chunk carries the `reply` id of the `queue()` call that pushed it (a `take()` continuation keeps its live reply's id, so a streamed-so-far reply still drops as one unit); `drop_heard()` widens out from `chunks[this.at]` to the full run sharing that id, splices just that span, and shifts `pending_ids` down to match. Anything already queued behind the dropped reply shifts into its place and keeps playing (`start_or_hold()`), or the state goes back to `"idle"` if nothing is left. `stop()` is the wrong tool for dropping one reply: it empties `chunks` outright, losing anything queued behind the one being dropped, even a reply that had not started yet.
- **A session switch drops the old session's queue.** `Sheet.js` `read_aloud()`'s `listen(session, why)` calls `recite.stop()` before following a *different* session (never on the very first follow, when nothing was queued yet) — a different voice session's replies are not this one's to read. `READ_ALOUD_V` bumped to `"2026-11-01f"`.
- **Played ids survive a reload** (owner item 20, folded in 2026-11-01 21:08). `Recite.mark_played(id)`/`was_played(id)` persist to `localStorage` (`lew42.recite.played`, capped at 200 ids). Marked only once the reply's LAST chunk actually finishes playing (`Recite.pending_ids`, settled in `ended()`/`speak_browser()`), never at queue time: a reply dropped by a barge-in question, a session switch or a reload before it played must stay unmarked, the exact skip item 20 forbids. `stop()` clears `pending_ids` along with `chunks`, so a dropped reply is never marked. The id itself: a Prompt `replies.add` line already carries one (`add.id`); the plain `{chat}` line shape has none, so its own `at` timestamp stands in (one per line, stable across a reload).
- **A second owner line while already paused (`BargeIn.state === "heard"`) still gets a question check.** `owner_spoke()` calls `heard_speech()` whenever `recite.state` is `"playing"`, `"loading"`, or already `"heard"` — not only the first two — without re-pausing when it is already paused. So "wait… / what about the other one?", a second line heard while the first interruption is still being waited out, still gets its trailing-"?" check: a question drops the old reply instead of letting it resume a moment later and talk over the new answer. An ordinary (non-question) second line just pushes the resume timer out further, the same as a held mic staying loud.
- **`close()` resets `level` to 0, so `speaking()` cannot stick true after the mic closes.** `BargeIn.speaking()` reads `this.level`, set only by `hear()` frames; once the mic closes (`heard_speech(text, {close_mic: true})`, the own-mic path, after a real check) no more frames arrive to correct a loud reading from just before close. Without the reset, a reply held by `start_or_hold()`/`check_wait()` (turn-taking) would wait for quiet that could never arrive.
- **`queue()` only starts or holds when `wait_at == null`,** so a second reply queued while the first is still held for quiet never skips the first. Starting or holding on every queue while idle, with no guard, would move `wait_at` to the new, later chunk whenever a second reply arrived mid-hold, and the chunks held between the old `wait_at` and the new one would never play. A reply queued behind an already-held one simply waits in `chunks` and plays in its turn once the hold resolves.
- **Echo: the read-aloud voice leaking into the chat's own mic must never pause itself** (dictation-v3 echo, 2026-11-01). Three independent guards, since the chat's own mic (not Recite's own Whisper check) is the normal path on a phone:
  - `MicStream.constraint()` turns on `echoCancellation`/`noiseSuppression` in every `getUserMedia` call, so the browser itself fights the leak first.
  - `Recite.echo_active()` is true while `state === "playing"`, and for `echo_guard_ms` (1500) after — `set()` stamps `echo_guard_until` the moment "playing" ends. While it is true, `BargeIn.owner_spoke()` runs `echo(text)` (word overlap ≥ 60% against the chunk being read, one either side) before anything else; a match is traced (`"barge: echo dropped"`) and dropped — never pauses, never a barge-in. An unrelated line is unaffected, question or not. `effective_threshold()` also raises `speaking()`'s and the fast-trigger's loudness floor by `echo_threshold_mult` (1.6) during the same window, so a stray loud moment of the voice itself (or a cough right after) doesn't hold a freshly queued reply or fire the fast trigger either.
  - `BargeIn.noise(text)` is a blocklist of common Whisper hallucinations ("thank you.", "thanks for watching", "you") heard alone; `owner_spoke()` checks it first, unconditionally (not gated by `echo_active()` — a phantom is a phantom whenever it arrives). Near-silence is checked unconditionally too, in both paths: `trigger()`'s own mic reads `this.peak` (reset and tracked only while that path is listening); `owner_spoke()`'s chat-mic path reads `recent_peak`, a decaying max `hear()` keeps on every frame it sees, since `owner_spoke()` only learns of a line after the mic has gone quiet again. Either below `near_silent` (0.045) is dropped as hallucinated text out of near-silence, logged as `"barge: near-silent dropped"`. `recent_peak` starts (and resets, on `close()`) at `1`, not `0` — "no mic info yet" — so a line arriving before any frames, or after the mic has fully closed, is never mistaken for silence.
  - *Known trade-off, not fixed here:* `echo_active()`'s guard window also starts when playback pauses for an ordinary barge-in (`set("heard")`), not only when a chunk finishes — so the owner's own genuine speech right after interrupting Recite is briefly judged against the raised `echo_threshold_mult` floor too. Harmless for the fuzzy echo match (real words rarely score ≥ 60% against the sentence just cut off) and bounded to `echo_guard_ms` (1500 ms), but it can delay `schedule_resume()`'s quiet-window push by that long. Left as is rather than tracking "ended by chunk" vs. "ended by pause" separately, since the bound is small and the behavior (reading resumes a little later, never earlier) already errs the safe way.
  - *Open item, not built here:* every guard above only stops BargeIn acting on a phantom/echo line — it still reaches the chat as a sent message, since posting the owner's transcribed line is `ux/Dictate/`'s send path, a file this task never touches. Filed as a task on the session record (owner `mastermind-ink-check`, who owns `ux/Dictate/`), not built here: gate the send on the same `BargeIn.noise(text)` / `echo(text)` checks this file already exports.
  - *Scope note:* `recent_peak` decays continuously (×0.995 per `hear()` frame) including mid-transcription, so a long Whisper transcription could in principle decay it under `near_silent` for a real but quiet line. Not reproduced; a real-phone check beats a synthetic one here.
- **The thinking cue is driven by the wire, not the mic.** The owner's own line landing on `from_wire` (any non-assistant `chat.text`, typed or spoken) is "a reply should be coming": `expect_reply()` sets `cue_pending` right away — no-flood's `agent_update()` reads that flag to decide whether to hold an update behind the coming answer, whatever `thinking_cue` is set to — and, only when `thinking_cue` is also on, plays a short generated tone (`play_cue()`, a plain Web Audio oscillator — never Kokoro, never an asset file) right away, and once more `cue_repeat_ms` (2000) later if `cue_pending` is still true. `partial()`/`final()` call `cancel_cue()` the moment real reply text arrives. `play_cue()` is skipped (but still traced) while `state === "playing"`; `thinking_cue = false` turns the tone off, never the holding (fixed, read-aloud-b 2026-11-02: `cue_pending` used to only ever be set while scheduling the tone, so no-flood silently did nothing with the cue off).
  - *Why "any non-assistant `chat.text`" is close enough:* `ext/Chat`'s own wire only ever stamps `from.kind` `"owner"` or `"assistant"` (grepped across every `.js` there) — no third role to slip through. Deliberately NOT gated on `barge.on` (the mic-listening toggle is a different question from "chime once a line was sent"); gated on `auto` alone.
- **Highlight dropout: `find()` was a strict positional match, so markdown noise broke it outright.** Raw, not-yet-rendered markdown (a link's bracket text followed by its own literal URL) interposes extra words the spoken text never had; once `find()` returned null, nothing retried it until the next sentence's key arrived, so the highlight stayed dark. Two fixes: `find()` now matches `want` as a **subsequence** (`ReciteHighlight.subsequence()`, bounded to `want.length * 2 + 20` positions) instead of requiring an unbroken run, and a genuine miss (`ranges === null`) now retries every `RETRY_MS` (300 ms) in `draw()`, tracing `"highlight: not found"` once per distinct miss (`logged_key`) rather than once per retry. A candidate start must still match the first TWO words contiguously (`find()`), not just the first, so a common word ("the") can't anchor the match somewhere wrong. Proved by 4 tests: markdown noise skipped, a miss retried and found, a re-render reconnects with zero dropout, a mention chip's own icon word doesn't break the match.
- **Lit words (item 24), same file, same merge:** `draw()` sets three disjoint CSS Custom Highlights instead of one wash over the whole sentence — `recite-unread` (not reached yet, muted), `recite-read` (already said, stays lit as later words play), `recite-word` (current, brightest) — the same `.is-said`/`.is-now` scheme `ReciteBar.js`'s karaoke line already used. *Scope:* "muted until read" is per-sentence (the word playhead within the sentence Recite is on), not the whole reply dimming until Recite reaches it — that would need a signal into the bubble's own base styling, which this DOM-free `CSS.highlights` approach cannot give; a whole-reply dim is a bubble-level change (`ext/Chat`), not this file. Shown at 400 and 1200 in `shots/piece-highlight-sheet-*.png` (at 1200 the AI surface is a docked panel, not an overlay sheet — the framework's own ≥52em breakpoint, same feature either way).
- A console race in `core/Test`'s `TestBlocks.js` (concurrent `test()` calls sharing one global captor) used to throw `Recite: a listener failed TypeError: fn is not a function` from `Recite.changed()` during a `play()` call — caught, never failed a test, but failed smoke. `changed()` now skips a non-function listener instead of calling and catching it, which is strictly safer regardless of cause; `on()`/`set()` are unchanged.
- **No flood, piece 1: the quiet window is 2.5 s, not unified into one field.** `Recite.turn_wait_ms` and `BargeIn.quiet_ms` both moved from 1500 to 2500 (within the owner's 2–3 s ask), but stay two separate fields rather than one shared setting: several existing tests set `r.barge.quiet_ms` directly to speed themselves up, and the two timers gate different moments (starting a fresh reply that would talk over the owner, vs. resuming one already cut off by a barge-in) — unifying them is a real simplification, still open, not done in this merge.
- **No flood, piece 2: an agent update is never read in full — it collapses to one line, and the direct answer plays first.** `from_wire()` used to drop any assistant reply whose `from.id` wasn't `"smart"` entirely; now `Recite.agent_update(text, id, from_id)` reads it instead — but only when `from_id` matches `Recite.AGENT_ID` (`mastermind-`/`minion-`/`reviewer-`/`clarity-`), not for every non-"smart" id. `"fast"` (the fast seat), `"revise"` (every voice revision of the owner's own sentence) and `"card"` (card conversations) post an assistant chat line too, but are not agent updates — they still fall through to the old drop, exactly as before this task (review finding, read-aloud-b 2026-11-02: `revise` fires on every dictated sentence, so collapsing it to a spoken line would have added the very flood this task was meant to stop). Collapsed, as `"I have an update on {label}, tap to hear it."` (`Recite.agent_label()`: the `mastermind-`/`minion-`/`reviewer-`/`clarity-` prefix off, dashes and underscores to spaces — a rough heuristic, not a lookup of the agent's own title). While `cue_pending` is true (the owner's own line landed and the direct "smart" answer hasn't arrived yet), the update waits in `pending_updates` instead of queuing, so it can never play ahead of — or instead of — the answer the owner is actually waiting for; `flush_updates()` releases it, behind whatever just queued, the moment that answer's own `final()`/`partial()` call returns (both `from_wire()` call sites call it right after), or after `update_hold_ms` (4 s) regardless, so a held update is never lost if the owner's line turns out not to need a direct reply at all. With no answer pending, an update just queues immediately like any other reply — there is nothing to hold it behind. `stop()` clears `pending_updates` and the hold timer along with the rest of the queue.
- **Tap to pause: one global toggle, not a per-bubble control.** `Recite.Tap` (`ReciteTap.js`) is a single document-level click listener that calls `recite.toggle()` — the same play/pause the bar's own button does. Five pieces:
  - **The toggle itself.** A tap lands inside a chat bubble (`ReciteHighlight.ROOTS`) and not on a link, a mention chip, a button, or the bar's own copy (`ReciteHighlight.SKIP`): `recite.toggle()`. `ROOTS` is the whole thread container (`.chat-v3`, etc. — the same selector `Highlight` already uses), not one bubble each, so a tap anywhere in the thread toggles, the owner's own sent lines included; narrowing it to assistant bubbles only is for the per-bubble control the bubble-toolbar piece plans, not this one. Deliberately NOT a per-bubble resume either — tapping an already-finished OLD bubble today just toggles whatever Recite is doing right now (or does nothing if nothing is queued); replaying an arbitrary past bubble from its own place is "resumable bubbles" (readme.md's Open list), the next piece, not this one.
  - **The drag guard.** A drag to select a word still fires a native `click` on mouseup, and that is never a tap: `click()` backs off whenever `getSelection()` has text anchored inside the tapped bubble (review finding, 2026-11-02) — narrowed to that one bubble, so a selection left over elsewhere on the page never blocks every other tap.
  - **"Tap to hear it" is not true yet.** The collapsed agent-update line (no-flood, piece 2, above) promises a tap will play that update; tapping right now only pauses or resumes whatever is already playing, never replays that specific update. Resumable bubbles is the piece that makes the promise true — until it lands the phrase is aspirational, matching the owner's own wording for the feature.
  - **The listener is never removed**, same as the rest of `Recite`: nothing in this class (or `BargeIn`, or `Highlight`) has a teardown path, since `Recite.shared` is a page-lifetime singleton — only the test file makes many short-lived instances, each leaving its own listener behind harmlessly (an empty `chunks` guard makes every stale one a no-op). `ReciteTap` is `track()`ed (same opt-in as `Recite` itself), so its live instances show wherever that is read back.
  - **The demo's own bubble has a hover affordance** — `.audio-recite-demo-bubble`'s `cursor: pointer` (Recite.css) — scoped to the demo, since a real chat bubble's look stays `ext/Chat`'s; a real per-bubble hover affordance is left for the bubble-toolbar piece, which already plans per-bubble controls.
