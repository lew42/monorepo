# Chat v2: a session's chat, drawn from its `tasks` list

- ⬜ **Goal:** the owner calls the whole experience "chat": the first view ([`ux/Dictate`](/framework/ux/Dictate/readme.md)) and Chat v2 become one chat, no renames yet. How a chat is made today, and where the two views differ: [`ux/Dictate/doc/pipeline.md`](/framework/ux/Dictate/doc/pipeline.md).

Read-only step 1 of the new chat (the owner's decision, [chat-shape.md](/framework/ai/sessions/2026/10/20/session-e00f55c9/sessions-and-tasks/dictation-debug/chat-shape.md)): a session's conversation is its `tasks` list in `session.jsonl`. Each Prompt sits at the root of the chat (a card each, no bubbles) as the smart assistant's refined version; its replies, questions and child tasks nest under it, marked 🧠. The raw Whisper text and the fast assistant's cleaned paragraphs are one click down, "show raw", never dropped. The old chat ([Chat.js](../Chat.js), `ux/Dictate/chat.js`) is untouched until v2 replaces it.

Try it: [/framework/ext/Chat/v2/](/framework/ext/Chat/v2/) draws [fixture/session.jsonl](fixture/session.jsonl); `?src=<url of any session.jsonl>` draws that session, live.

## Classes

- `ChatV2.js`: `class ChatV2 extends JSONL`. `read()` draws everything on the first load, then patches in place: each later line updates only the element(s) `ChatV2Model.apply(line)` says it touched (`apply_one`, `patch`, `insert_reply`, `move_anchored`). A root Task or Question added live goes to the root, or into its prompt's nest when its `from` names one; "show raw" or a first title moves only the anchored replies between the nest and their sentences; `reset()` (the file was rewritten) drops the model so the replay draws whole. Parts are its methods: `prompt` (+ `prompt_head`, `prompt_raw_wrap`, `prompt_nest`), `sentences`, `reply` (+ `reply_body`), `child` (+ `child_body`).
  - **The sent/working marks (2026-10-25, round 3):** two fixed-width marks move to sit after the newest Prompt only, never one per message or per sentence — `place_cursors()`, called after every patch. `.chat-v2-cursor` (✓): gray, green once `sent.fast`. `.chat-v2-smart-cursor` (🧠): gray once `sent.smart`, the smart-reply colour once `working` is also clear. `.chat-v2-smart-dots` at the bottom is a fallback only, hidden once any Prompt exists to carry the smart cursor. Both are per-PROMPT signals (`Sessions.mark_sent` fires once per Prompt, not per sentence) — a true per-sentence mark needs a new Servex line, named in the `chat-live` task's `proposal.md`.
- `ChatV2Model.js`: folds the lines into plain objects and holds every field read (`title`, `raw`, `paragraphs`, `replies`, `answer`), the computed `sentences(prompt)` and `phase(question)`. `apply(line)` also says what the line touched, for `ChatV2`'s in-place patch (see Decisions).
- `ChatV2.css`: the `chat-v2-` classes, all in `@layer site`. Column max 46rem.
- `ChatV2.test.mjs`: headless Playwright, 47 checks (order, nesting, show raw, live append, in-place patch with the chat's own scroller held, `paragraphs.replace`/dedupe-by-id/`raw.push` array): `node ChatV2.test.mjs [base-url] [shots-dir]`. The live checks write a per-run copy of the fixture, `fixture/live-<pid>.jsonl`, into the tree the site at `base-url` serves (with no url, the main tree, even when the test runs from a worktree or merge.mjs's base checkout), and delete it at the end; a killed run leaves it behind, and `.gitignore` covers it.

## The shape it reads (one line each in `session.jsonl`)

```js
{tasks:{add:{type:"Prompt", id:"p-<ms>", title, text,          // the smart assistant's version; may be absent early
  raw:["whisper text", …], paragraphs:[{id:"a", text}],        // one raw per utterance; the fast assistant's cleaned text
  replies:[{id:"r-<ms>", text, by, ts, anchor?:{sentence:"a1", words?:[start,end]} | {sentence:"a1", from, to}}],   // end exclusive, either shape
  tasks:[ …child Task / Question entries… ]}}}
{tasks:{add:{type:"Question", id:"q-<ms>", text, from:"p-<ms>", answer?:{text, by, ts}}}}
{"<id>":{answer:{…}}}  {"<id>":{complete:{}}}  {"<id>":{replies:{add:{…}}}}   // later lines edit by id
{"<prompt id>":{"<task id>":{complete:{…}}}}   // or through the parent, as the item tool writes it: the change is the child's
```

Sentences are computed, not stored: a sentence id is its paragraph id plus a 1-based index (`a1`, `a2`, `b1`). A Question is open (no answer), answered (answer, not complete) or complete. A prompt's children are its own `tasks` plus any root Question or Task whose `from` is its id. A prompt with no title or text draws its paragraphs; an anchored reply sits beside its sentence (below on a phone) with the words marked.

## Who writes the data

Step 3 landed, round 2 (chat-v2-writers): a Prompt starts the moment the owner starts speaking — any seat, voice or not. `Servex/agents/Sessions.js`'s `say()` opens it (`assign_prompt`) on the first line of a thought, pushes raw words and grows the one paragraph "a" on every later line of the same thought, through the one small writer `Servex/agents/PromptLines.js` (every function it exports matches a line shape above). The Prompt closes the moment its thought is handed to a seat (`release_thought`, or a standalone line with nothing held) — `s.prompt` is cleared there, so the next line always starts fresh, and a fallback respawn (`woken()`, re-sending the last owner line) never writes a second one. The smart seat writes the refined title/text, replies, questions and their answers through the `item` tool directly (it is an LLM, not code); its instructions are the "Chat v2" section of `Servex/agents/session-smart.md`. **Both seats are told the Prompt's id**: every message either gets, as a trailing `(prompt p-…)` line (`voice_say`, `release_thought`, `feed_smart`) — there is no other way for either seat to learn an id `say()` just minted. Needs a Servex restart to take effect (dev-server-only code).

**The page's own reports** (errors, opt-in clicks, context) reach the assistants down the REAL dictation path, `POST /api/session/say` (`Servex/agents/Sessions.js`'s `say()`), tagged `kind`: `speech` (the default, an owner utterance, unchanged) or `error`/`click`/`context`. `public/framework/ext/Chat/v2/report.js`: `init(session)` once, then `window.onerror`/`unhandledrejection` post themselves; `click(label)`/`context(text)` are opt-in calls. A non-speech `say()` call never wakes a seat and never touches a Prompt: `error` is filed as a `log` line on that session, `click`/`context` are queued for the smart seat's next turn. Wired into `ux/Dictate/chat.js`, which calls `init(session)` each time its voice session changes.

**Checked once:** the smart seat's `item` tool writes land in a session folder's `session.jsonl`, not a stray `page.jsonl` beside it. `Servex/agents/page_tools.js`'s own file-resolution rule (`resolve_file`, item-tool mode) run against a real voice session folder with no `page.jsonl` (`public/framework/ai/sessions/2026/10/01/v-6jvcrk2/`) resolved to that folder's `session.jsonl`, matching the rule verbatim: a folder with no `page.jsonl` is checked for `task.jsonl` then `session.jsonl` before falling back to `page.jsonl`.

**Where it shows:** the standalone page (`?src=<session.jsonl url>`), the session page's Chat tab under its **Chat v2** chip (`?tab=chat&chat_view=v2`; `ai/AISession/AISessionDetail.js`), the ✦ sheet under the **v2** chip in its head, and the desktop drawer's AI tab under the same chip beside "+ New session" (both use `ext/drawer/ChatView.js`: one chip, one `lew42.sheet.chat_view` choice for both): it draws the sheet's own voice session file in place of the bubbles, follows a New session or a resume, and keeps the choice on this device (`localStorage` `lew42.sheet.chat_view`); the composer and the mic footer stay. Sessions migrated by `Server/PromptsToSession.mjs` already hold Prompts, for example [session e00f55c9](/framework/ai/sessions/2026/10/20/session-e00f55c9/?tab=chat&chat_view=v2).

## Decisions

- Fields are still read from a plain fold, not the real `Prompt`/`Question` classes (`core/Task/Prompt.js`, `Question.js`, now landed): the view needs the raw LINES, never an Item tree built from them, so `ChatV2Model` keeps its own small reads (`title`, `anchor`, `phase`…) matched by hand to the classes' own rules. The alternative, `Prompt.from(line)` read-only getters straight off the lines, wins once core exposes a cheap fold that does not require hydrating a live Item.
- Child cards are `ChatV2.child`, not `TaskView.row`, which needs a live Task; it reuses `TaskView.STAGE` for the icons.
- **In place, never redraw:** `ChatV2` keeps one `View` per item id (`els`), plus three containers per prompt (`head`, `raw`, `nest`) so a change to its own fields never touches its children. `ChatV2Model.apply(line)` says what the line touched — an add (with its parent, `null` at the root) or a field change on an id already drawn — and `ChatV2.apply_one` either appends one new element where it belongs or calls `view.empty(bodyFn)` to refill that ONE element's content, keeping its `.el` (so references elsewhere, and the scroll position, never move). The alternative, a keyed diff of the whole tree (React/morphdom-style), wins once the model's shape gets deep enough that per-field patch rules like this one outnumber the handful here — this chat is three levels deep at most, so hand-written patches stay cheaper.
- **One Prompt per thought, not one per `say()` call.** `s.prompt` stays open across every line of a held thought (pushing raw, growing paragraph "a") and closes only when that thought is handed to a seat. Alternative (round 1's build): one Prompt per `voice_say` call — wrong whenever a thought held several spoken lines before release, since `voice_say` only ever saw the already-released batch, so live speech reached Chat v2 only after the pause, not while the owner talked.
- **`p-<ms>` ids, minted fresh, not `Server/PromptsToSession.mjs`'s `prompt_delta()`.** That helper folds an EXISTING `prompts.jsonl` row into a Prompt; a voice session never has one (`Servex/agents/PromptTasks.js`'s `record_for()` only recognizes a VS Code tab, `kind: "vscode-tab"`), so there is no row to fold and no risk of a second Prompt for one utterance — this is the first writer, not a second one. A millisecond collision (two Prompts made in the same `Date.now()`) is guarded in `PromptLines.js` with a per-prefix monotonic bump, found desk-checking back-to-back standalone lines.
- **`kind` lives on `/api/session/say` (Sessions.js), not `Servex/Servex.js`'s `/api/voice`.** Round 1 reused `/api/voice` because the brief named that exact route and line; it turned out to belong to a different system (`ext/refine/VoicePage.js`, the Live-Refine demo, keyed by a Claude transcript uuid, not a voice session id) and was reverted whole. `/api/session/say` is the real speech path the owner's words already travel, so the page's own reports travel the same wire a spoken line does, just tagged differently.
- **Errors are filed by the route (`say()`), not the fast seat.** The fast seat never sees a `kind: "error"` line at all (an early return in `say()`, before anything is sent to either seat) — simpler and cheaper than teaching an LLM to recognize and re-route its own crash reports.
