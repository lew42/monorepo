# Brief, 2026-11-17: what Michael wants (essence)

Source: [owner-words-2026-11-17.md](./owner-words-2026-11-17.md) (verbatim). Rules every agent follows: [rules.md](./rules.md).

The goal: **a very simple design system that looks extremely simple.** Every page is clean and structured top to bottom. He is confused by the many Figma choices and wants research, not more building.

## Decided (owner)

1. **Keep Root.** One auto-layout Root per page stays: it is what stopped the broken, overlapping layouts, and it lets agents screenshot and measure a page. Removing Root, so the folders show in Assets, can be a pre-publish step later. Use auto layout all the way down, with nothing fixed-positioned.
2. **Compact pages.** A page's top-level view reads roughly 2:1 to square, and a bit taller is fine. No extreme ratios and no big voids where one part sprawls past the rest. Leave white space only where it helps, such as on title pages.
3. **The Index is the design system.** An agent building a design reads the Index and uses only approved things from it, as instances, overriding the text, images and slot contents.
4. **Reduce.** Give each thing one logical home and no duplicates on the Index. The Index shows each main thing and the variants worth listing. Everything else lives on its own page as overrides or slot content.
5. **No permutation grids** (not 300 buttons). Atoms (buttons, text, icons) need no per-size previews. Only layout (columns, flex, padding) needs previews at several widths.
6. **Keep the file links in the readme** (done: readme "Files").
7. **Minimal Index, basics only; a level-2 system can come later.** The Index lists categories and shows each one's system as a schematic, not a catalogue. Example: icons are shown as a few sizes, framings and text pairings, not every arrow. The Icons page stays the full icon browser. Elements holds text, buttons and possibly icons. For each page, decide what its preview holds and how it is laid out; together those previews make the kit.
8. **Goal: polish and publish.** Every page is clean, and every token is defined once, in a logical place.
9. **Change safely.** Propose first. Build beside the old version, never in place. Archive, don't delete. Do one page at a time, and roll nothing out until he approves the pilot. He checks the file himself before anything major.

## Open: research these, then recommend

- **A. Organization.** Do popular kits organize by size or layout, as our size pages do, or by element type? Why? How does container-to-content swapping work across resolutions, for example 1920 to 1600 sections, and for cards and their content?
- **B. Properties vs variants.** Answered: [research/properties.md](./research/properties.md).
  - Do properties give you variants without drawing them?
  - Variants don't inherit from each other (true?), and the "base component" workaround.
  - Instance-swap properties vs native swap (for icons, native swap seems better).
  - Slots: a Card with one Content slot vs a default Card you detach and edit.
  - The convention "the first item of a repeated grid is the master, the rest are instances of it."
  - When should something be a component at all?
- **C. Color.** One Fill token, or a BG + Surface split? The options:
  1. cards left on Auto with one fill, which gives same-on-same and low contrast;
  2. the mode set on each card;
  3. a transparent wrapper that sets the scheme for its cards;
  4. BG and Surface tokens, so Auto cards contrast with their section and a group of cards dropped into a dark section flips on its own (his ideal).

  Does mode inheritance hold up? What do kits do (Material 3 surface containers, and others)?
- **D. Grids.** Answered: [research/properties.md](./research/properties.md#5-grids). How do modern kits build grids? Is it the Figma grid auto layout? The column count can't be bound to a variable, so what do they do instead?
- **E. Process.** Separate (1) designing the system, (2) designing the theme, and (3) designing outcomes, meaning real pages that are not masters. Find the standard words for these. When should a design be a master and when a one-off? *Answered (with F's preview set): [research/process.md](./research/process.md).*
- **F. Previews.** Per-scheme and per-width previews cost space. A possible set:
  - the master at Default width;
  - a mobile preview in each scheme;
  - optionally Desktop;
  - Mega maybe not documented.

  Are 8 resolutions too many?
- **G. Real kits.** Answered: [research/figma-kits.md](./research/figma-kits.md). Look at the libraries still attached to the Claude November 2026 file (Figma's default UI kits): how do they organize pages, top-level frames, names and components?
- **H. The Index today.** What is on it, what a reduced Index-as-system would hold, and a 2:1 layout for it. *Answered: [research/index-audit.md](./research/index-audit.md).*
