# Owner notes, 2026-10-16 (night): seeing tasks (dictated; captured by voice-app)

Fourth note of the day. The point of the task system: see what was asked for, see what is done, keep working on what is not. Read the three earlier notes first.

## The simplest path, before refinement

Refinement (Whisper, real time, interrupts, voice) comes second. First: a dictation, from the mobile app, the website or the VS Code sidebar, becomes structured tasks a person can see. One pathway for every prompt, whatever its source; the same task system for all of them.

## Where, and the session reference

- A task made while working on a module goes in that module's `tasks/` folder. Automatic: the agent names the module, the tool puts it there.
- The session logs a reference to every task it creates or works on, so a session is an overview of its tasks. Automatic: the tool call carries the agent id, so the tool appends the reference; no agent has to remember.
- Cost per task is the sum of the agents that ran on it. Tasks often have their own minion or helper; that is how the sum works.

## Group, do not scatter

- Dozens of flat mini-tasks in a module's list mean nothing ("what did I ask for?"). Directive: **group when appropriate.** A refinement of an existing task goes into that task, not a new one. A quick fix on an old task may be a new task.
- Long-lived tasks: a goal or project that work accrues to, not retired after one landing. No separate Project class: a Task is the container; a parent with many children renders bigger and previews its children.
- Not every task is long-lived: "fix this" tasks are completed and gone. If a task is not complete, it stays in view.
- Notes vs tasks: some dictations are ideas to keep beside a module while designing, not work to fire off. Masterminds should not turn every "this is broken" into a to-do; planning vs quick fix is a judgement the refinement step will make. `requirements.md` files stay: they say what was asked and what is expected, and the review checks delivery against them.

## The views

- **Module page, Tasks tab**: every task in `<module>/tasks/`, prioritised: recency times weight, so what just happened rises and what matters stays up, and old, light things fall off. Big tasks look bigger.
- **Segmented progress**: a composite task with N children shows N small bars that light as each child completes. No bar for a single-step task.
- **/live**: a context card (the module's icon and title, reached by a mention) wraps the task or goal. Two modes wanted: (1) the live presentation: only what we are talking about now, two or three things at most; old topics collapse as the conversation drifts, and the agent can navigate the owner's browser there (through MCP); (2) the grid: prioritised tasks wrapped in their context, recency times weight. Tabs on /live to switch.
- Risk the owner expects: /live becomes an inbox blown up with marginal things. The prioritised view and grouping are the answer.
