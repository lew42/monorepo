# Plan review: the shape is right, but four traps sit in the path, and build B's job crosses build A's fence

A fresh read of [plan.md](../../plan.md) and the shape docs, checked against the code on 2026-10-28 (`michael/dev` at `18728e396`). Paths are from `public/framework/` unless they start with `Servex/` or `Server/`.

**In one breath:** start with the backbone, as planned. But "each level's `get` takes the rest of the path" breaks silently in two cases I reproduced in node (an id that spells a method name, and a list made by a getter). The item tool is not yet one tool for any item. A View can't be stored. And build B can't do its job without editing build A's files.

**Measured, so you don't have to worry about it:** reading dotted keys is safe for today's records. In 9,615 `session`/`task`/`page`/`improvements.jsonl` files there are 0 dotted keys in 129,723 lines. But **keep writing nested lines, never dotted ones.** About 20 scripts and views read lines by their shape, for example `Server/PromptRecords.mjs`, `Server/ChildLinks.mjs` and `ext/Chat/v2/ChatV2Model.js`. A data key with a dot in it, like a file name, must ride inside an `add` payload. That replaces [ids-and-paths.md](../../ids-and-paths.md) §4's "write the path form when two or more hops deep".

## The six questions, briefly

1. **The backbone** is right. Where it runs: see F1 below. The item tool: not yet one tool (findings 3–5).
2. **Path traps:** method-named ids (1), lists made by getters (2), dotted data keys (none today), old lines (the id-only search survives as a fallback). A new one: **a path that walks through a `Ref`** must not silently write into another file. Walking through a ref is for reading; a write names the target's own file.
3. **References and moves:** sound inside one file. Across files, it needs the id fallback (finding 8).
4. **The View in storage:** it doesn't serialize, and shouldn't. Store data parts; their `View` draws them (finding 6).
5. **The order** is right, with four additions:
   - **First,** before any code, a baseline that replays every record file and compares it with the result after the change.
   - **Then step 1d,** one writer (finding 5).
   - **Before step 4,** references across files that resolve in the browser, which F2 needs. Today only node resolves them (`Task.js:454-461`); the browser shows a "loading" stub.
   - **With step 4,** 8-character random ids, and the item tool stops making ids from titles. Ids made from titles are what hit finding 1.
6. **The three things most likely to go wrong:**
   - **(A)** "Each level's `get`" is built as written, and `pages` or a member called `save` drops changes silently. Test both.
   - **(A)** The tests pass in the worktree, but the agent path (Servex, main-tree code) is never exercised.
   - **(B)** The fence collision: B edits `Item.js`/`List.js` (a merge conflict with A), or merges three views into a fourth.

## The forks, with my lean

- **F1, where the live instance runs: each project's dev server, one per tree, worktrees included.**
  - Why: it runs that tree's own code, so a worktree tests its own backbone. It already tails the files and pushes the new lines (`Server/plugins/SocketServer/Tail.js`). A restart touches one project only.
  - Servex keeps the agents, and its item tool forwards each write to the right dev server. When that server is down, it falls back to a plain append, as today.
  - Against Servex: one copy of the framework code serves every project (finding 3). Heavy replays already block its event loop (that is why `run_item` drops timing breadcrumbs, `page_tools.js:1035`). A restart is refused while agents work.
  - Servex would win if there were only ever one project.
- **F2, a task handed to a child: move, as the owner leans,** but only once refs across files resolve in the browser and fall back to the id (finding 8). Until then, the parent's rows show "loading".
- **F3, Prompts and Questions: messages.** The task-path counts settle it (111 of the 223 "open tasks").
- **F4, sentences: their own list.** Anchors never move.
- **F5, the default view: one.** Pick the existing view that already draws the collapsed row. Re-export the other two and mark them deprecated, rather than writing a fourth.
