# Reset: recovering when the log was rewritten under a reader (R4)

**The problem.** A reader's cursor is a byte offset into a `.jsonl` file. `Server/SessionConsolidate.mjs` rewrites a url inside an already-read line and appends more; `Server/page-files-migrate.mjs` merges another folder's lines in front of a live file's own; `Runtime.safe_write` (write tmp, fsync, rename) replaces the whole file atomically for both. Before this, `Server/plugins/SocketServer/Tail.js` only noticed a rewrite that made the file **shorter** than a reader's offset. A same-size or longer rewrite looked exactly like an ordinary append, so the reader was sent bytes from the middle of the OLD content: a torn line, lines it already had, or neither of the lines it was missing. Research: [research/2026/10/29/persistence-sync/persistence-sync/lessons/sync-protocol.md](/framework/research/2026/10/29/persistence-sync/persistence-sync/lessons/sync-protocol.md), R4.

Two independent fixes, one on each side of the wire:

## 1. The server proves a cursor before trusting it (`Tail.js`)

Every socket's offset now carries **proof**: the up-to-256 bytes of the file just before that offset, read fresh each time (never kept as a growing history — `Tail.js`'s `proof_at()`). Before answering a `change` event (or a resubscribe with a non-zero offset), `rewritten(file, from, proof)` runs two checks:

1. **The gap check.** The byte right before `from` must still be `\n` — every offset `read()` hands out lands just past one, so anything else (the file shorter, longer with different content, a rename-over with a different shape) proves the file no longer has the same lines up to `from`.
2. **The window.** Only when the gap check passes: are the 256 bytes just before `from` still exactly what this socket saw last time? This is the one check that catches a **same-length replacement** — `Runtime.safe_write` correcting a url inside an already-read line, where the line count and every boundary after it are untouched, so the gap check alone sees nothing wrong.

Either check failing sends `jsonl_reset` instead of a frame of lines. `subscribe()` with a resumed offset (a reconnect handing back its old cursor) only has the gap check available — there is no stored proof yet for a cursor nobody has read through this process before. Two sockets sitting at the same offset are checked by offset *and* proof together, never offset alone: one may have subscribed just before a same-size rewrite and the other just after, and sharing a single verdict between them would give the second socket the first's answer by Map iteration order (review, note 8).

**What this does not catch.** The window is only the 256 bytes right before the cursor. A same-length rewrite of an EARLY line, more than 256 bytes before a reader's current position, leaves no trace there and is missed until that reader's own cursor passes through the changed bytes (it won't, since the length is the same) — in practice, until the next full reconnect re-reads from an earlier offset, or forever if the reader never goes back. Catching every such case would mean a proof covering the WHOLE file (or a sidecar `epoch` line a rewriter bumps — the "better" alternative sync-protocol.md R4 names, not built: it needs every rewriter, not just `Runtime.safe_write`, to remember to bump it, where the 256-byte window needs nothing from any caller). Accepted for now: this is strictly rarer than the already-rare case this entire fix targets (two writers, or a rewrite, racing one `change` event), and it still exceeds today's behaviour, which caught no same-length rewrite anywhere in the file.

Test: `Server/plugins/SocketServer/Tail.rewrite.test.mjs` — shorter, same-size (the one that needs the window, not just the gap check), longer two ways (a compaction racing an edit; a migration merging another folder's lines in front), and a rename-over.

## 2. The reader applies only what it has not already applied (`Store.js`)

`live.js`'s `jsonl_reset` handler (unchanged) sets the reader's offset back to 0 and resubscribes — the server then answers with the **whole current file in one frame**, the same as any fresh subscribe. Before this, `Store.reset()` only cleared `count`, so that full replay ran every line again on top of a host that already had most of them: a Task's verb ran twice, a counter double-counted.

- **`this.applied`** (a `Map<hash, count>`) is a running multiset of every line this store has actually applied — replayed, or skipped as its own echo (which already happened once, optimistically, at write time). It is keyed by `Store.hash_line(entry)`, a 32-bit FNV-1a hash of `JSON.stringify(entry)` — never the lines' own text, so a long-lived store's memory for this stays small (a few bytes per line) even for a multi-megabyte log.
- **`reset()`** takes a spendable copy, `this.skip = new Map(this.applied)`.
- **`read()`** checks `this.skip` first, per entry (`consume()`): a match spends one credit and the line is **not** replayed — it is already in the host. A line `skip` has no credit left for — because it is genuinely new, or because a rewrite changed its text (its hash no longer matches anything `applied` ever held) — runs as normal. Because the server always answers a reset with the whole file in one call, the recovery is always exactly one `read()` call: `skip` is cleared at the end of that call regardless of whether every credit was spent (a compaction can drop a line for good — nothing left to match it against, and there is nothing left to apply for it either). The host then gets one `"reset"` event, so a view can redraw.
- **Why a multiset, not a set.** Two textually identical lines (two bare `{"increment()":{}}` calls) hash the same; a set would only remember "seen", so the second (real) occurrence would be skipped as if it were a duplicate of the first. The count lets `consume()` tell "the Nth time we saw this exact line" apart from "the N+1th" — in file order, matching how the lines actually arrived. Test: `reset.test.mjs`'s three identical `increment()` lines (two already applied before the rewrite, a third genuinely new).
- **The one recovery `read()` must actually happen, even with nothing in it.** A rewrite that leaves the file empty (or with nothing past byte 0) answers the resubscribe with an empty frame; `live.js`'s `jsonl()` now calls `read([])` for that frame too (not only a frame with lines), because that is the ONE call that clears `skip`. Before this, an empty recovery frame left `skip` armed, and the next ordinary append whose text happened to match an old line was silently swallowed as if it were that same old line again (review, finding 1). Test: `reset.test.mjs`'s empty-recovery case.
- **New lines land after the ones already there, not necessarily in file order.** `consume()` walks the fresh read in file order, but a line it does NOT recognise is applied right then, onto the host exactly as the host is at that moment — not rebuilt from a clean slate in file order the way a fresh replay is. For a line that only ever ADDS or SETS by id this is the same result either way (the target, found or made, is the same item whichever order the file now lists it in). It is NOT the same result for an order-sensitive verb with no explicit position: a migration that merges another folder's lines in FRONT of a file's own (Tail test case D) puts its genuinely-new line first in the file, but the recovered host still runs it as if it were received now, which for a plain `List.add` with no `after` lands it at the END of the list the host already has — a fresh replay of the same new file, building the list from nothing in file order, puts it first. `reset.test.mjs`'s own checks only exercise lines appended at the end, where this never shows up; a case with new content in front is not pinned here (review, note 9).

**Why re-applying a text-changed line is safe for what `SessionConsolidate` rewrites.** It only ever rewrites a url string inside a `{"set":{...}}`-shaped line or inside a `task`/`file` line that names its target by id. Both are **idempotent on replay**: a `set` just assigns the (now-corrected) value again, and a line that resolves "the item with this id" finds the same item whether its url field says the old folder or the new one. **What would not be safe:** a verb with no stable target to re-resolve against — an open-ended `move` (if its rewrite ever changed which list it names) or a text append (running it again would append twice) — but nothing in this codebase rewrites a `move` or an append line's content today; if one ever does, it needs its own idempotent replay, the same way `set` and the item-tool's id-based lines already have it.

**A store opened from a snapshot (`Store.use_snapshot`).** `this.applied` only ever records lines this store itself read — which, for a snapshot-started store, is just the lines *after* the snapshot's cutoff. It has no record of what the snapshot folded in, so `skip` cannot tell "already in the snapshot" from "genuinely new", and a naive recovery read would duplicate everything the snapshot already holds onto the live host. Two ways to handle it:

- **Built: keep the live state and warn (`this.frozen`).** `reset()` checks `this.snapshot`; if set, it warns once and sets `this.frozen`, and `read()` becomes a no-op for that store from then on (every entry is skipped, `count` still advances). The live object stops updating until the page reloads and the store is rebuilt from scratch — safe, if stale for however long the tab stays open. Test: `reset.test.mjs`'s snapshot case — a reset on such a store leaves the host exactly as it was.
- **Not built: rebuild by full replay, then `restore()`.** Build a brand-new, empty instance of the host's class, replay **every** line of the rewritten file onto it from scratch (ignoring the snapshot, since there is no way to tell if it is still valid), then call the *existing* live host's `restore(fresh.toJSON(), …)` — the same method a snapshot itself uses to seed a host — so the live object's identity (and every reference to it) survives while its contents are replaced wholesale. Not built: it costs a full replay (the exact cost snapshots exist to avoid) every time a snapshot-started store sees a rewrite, and needs checking that `restore()` onto an already-populated host behaves the same as onto a fresh one (today it is only ever called on a fresh instance: `Item.from_snapshot`, `Item.open`). Worth building if a snapshot-started store seeing a live rewrite turns out to be common; today it is rarer still than the rewrite case itself.

**What this costs.** `this.applied` grows for the life of the store — one Map entry (a number key, a number value) per line ever applied, never freed. For a store that stays open for a very long session with a very large log, this is the one unbounded structure the fix adds; not addressed here, since it is strictly smaller than the log itself and no store observed in testing approaches a size where it matters.

Test: `public/framework/core/Item/reset.test.mjs` — opens a real `Item` (with a `List` and a non-idempotent `as_call` verb) from lines, applies a live line, rewrites the file the `SessionConsolidate` way (an early line's text corrected in place, same length, more lines appended), resets, and checks the result against a fresh replay of the new file: the rewritten field's new value lands, the `List` add is not duplicated, and every verb ran exactly once — the lines already applied are skipped, only the genuinely new one runs.

## What was not built

**`epoch`** (brief step 3): a sidecar or counter a rewriter bumps, which `Tail.js` could check instead of (or alongside) the byte-window proof. Skipped: the gap check plus the 256-byte window already catches every case this task's tests ask for (shorter, same-size, both "longer" shapes, and a rename-over), and an `epoch` would need every future rewriter to remember to bump it, where the window needs nothing from any caller. Worth building if a rewrite more than 256 bytes before a reader's cursor, at exactly the old length, turns out to happen in practice (see "What this does not catch" above).
