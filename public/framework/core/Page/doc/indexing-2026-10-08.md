# Indexing, directory deltas and querying — the owner's questions, 2026-10-08

Recorded from dictation; open architecture questions for the core page system, with what the code already shows.

## What exists (verified by looking at the files)
`public/framework/ai/2026/page.jsonl` and `ai/sessions/2026/09/cards/page.jsonl` already hold **file-system deltas as lines**: `{"file":"28/"}` for presence, `{"file":"28/","gone":true}` for removal, `{"file":"10/page.jsonl"}`, plus a `{"title":"September 2026"}` line. The year / month / day directory tree is therefore already a partitioned index of its children, written by something (find what: the Directory plugin or a Servex writer) as appended deltas, not a rewritten `directory.json`. Confirm who writes these lines and whether it is automatic for every directory.

## The questions
1. **Is appending deltas to each `page.jsonl` the right home for directory presence/removal** (instead of rewriting a `directory.json` on every change)? It is cheap and streamable. Record when to use it and when not (e.g. very large flat directories).
2. **A session index.** Creating a session folder alone does not get it onto the Sessions dashboard. Candidate: an append-only `sessions.jsonl` at a higher level (or per date partition, `ai/sessions/2026/10/08/cards/page.jsonl` style) with **one line per session** carrying the preview data: id, name, icon, total cost, `cost_complete` (boolean), state, start/updated, tags, core links, alert count. The dashboard renders from the index (live-tailed) and loads a session's own files only on click.
3. **Querying without loading 4,000 files.** Treat sessions as a database without indexes: filters run over the index lines (partitioned by date, so a date filter loads only those partitions); detail comes from the session's own files. Decide: one big index vs date partitions (owner leans to partitions: year/month/day), and whether index data is derived (rebuildable from the logs) rather than a second source of truth.
4. **Cache vs live.** The owner leans to loading live data rather than a cache; an index that is itself tailed live avoids staleness.

Owners: `ai/2026-10-08/session-class` (sessions side) and the core page work. See also `ai/sessions/doc/data/data-architecture.md`.

## Addendum (owner + mastermind, 2026-10-09 17:25) — the sidebar, search and the 16 MB directory.json

**The owner's report:** the sidebar's "Filter pages" box cannot find Dictate, because children load only when a branch is twirled open, and a twirl takes up to a minute to render.

**Measured:** `/framework/directory.json` (the whole file tree, one file, read by the page system, search and the AI pages) had grown to **16 MB, 56,323 entries, 58% of them `ai/sessions/2026/`** (the session migration this morning). Those files are written constantly, so `Server/plugins/Directory.js` re-walked and rewrote the tree about once a second, and every open tab was told to re-fetch it. Fixed at 17:20 (commit 9b7f9b686): that subtree is left out (sessions have their own `index.json`); the file is now 5.8 MB and quiet. The twirl delay should drop; verify.

**The owner's question: one parent index vs each directory owning its own data.** They worry that a parent holding its children's title and icon breaks portability (you could no longer copy a directory and have it work without running code).
**Recommendation:** each directory stays the source of truth for its own title, icon and children (portable); a parent index is **derived** — a server-built, rebuildable cache, never hand-edited. Concretely, a small **nav index** (path, title, icon, parent; no file lists) built from the declared `children:` tree, maybe 100-300 KB, that the sidebar loads once: the filter then searches every page, and a twirl renders instantly from it. It replaces nothing; `directory.json` stays for file lists until the delta design above lands.
**Status:** recorded, not started (the owner asked for no new tasks on 2026-10-09). It belongs with priority 3 (page system).

## Answer (2026-10-12): navigation from files.jsonl, and the orphan check

**The owner asked:** (1) the nav is a hand-written `children:` string, so anything new is invisible until a parent names it (`ext/Figma` was missing from `ext/page.js`). Could the nav use `files.jsonl` so new things appear on their own? (2) Was the dynamic sub-page index ever built?

**Answer to 2:** the *nav index* of the 2026-10-09 addendum above (one derived file for the sidebar filter) was **not built**. But the piece underneath it already exists: `Page.listing(url)` reads a folder's own `files.jsonl` and `Listing.pages` already names every subfolder holding a `page.js` or `page.jsonl`. Nothing used it to declare children.

**Measured:** `node Server/OrphanCheck.mjs` found **93 pages in 18 modules** with a `page.js` their parent doesn't name (worst: `styles/layouts` 33, `ui` 29, `ext/Figma/palette` 7, `ai` 5, `ux/Dictate` 4). Some are reached another way (a tab, a data source), so the number is an upper bound, not a bug list. Run it for the list.

**Recommendation: opt-in `auto`, no cache, no new file.**
- `children: "Classify markdown auto"` — named children first, in the order written; the word `auto` then adds every subfolder with a page, alphabetical. A new folder with a `page.js` appears with no edit to the parent. Built in `Page.declare()` (about 5 lines) on the existing `child_source` seam and `Page.listing()`.
- Order stays in the parent's own string (the owner's reading order for the named ones); the unnamed ones are alphabetical. A per-page `order:` field would force loading every child page just to sort, so it is **not** built; add it only if alphabetical proves wrong.
- Pages stay portable: each folder still owns its title and icon; the parent only learns the names, from its own `files.jsonl`.
- The sidebar filter's problem (children unknown until twirled) is **not** solved by this; that still needs the derived nav index above. `auto` fixes "invisible until named", not "unsearchable until opened".
- Applied to `ext/page.js` first (that also surfaces `Figma` and `DataGrid`). Other parents opt in one at a time after you have looked at the result.

**The gate:** `Server/OrphanCheck.mjs` (one class) runs inside `merge.mjs` as a **warning** for any changed page whose parent doesn't name it. Make it a refusal once the 93 are cleared or opted into `auto`.
