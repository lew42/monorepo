# Eric — Phase 3 report

## 1. First thing I'd change

The error boundary doesn't cover what it needs to, and when it does fire it also breaks navigation. `App.instantiate()` awaits `load()` with no try/catch of its own; inside `load()`, only the `import("/page.js")` call is wrapped — `page.activate()` three lines later (which renders every page in the chain and runs arbitrary `content()` code) is unguarded. A throw there is an unhandled rejection: `initialize()`, `inject()` and `ready.resolve()` never run, `$app` never gets appended to `<body>`, and the visitor gets a blank white page with nothing in the UI explaining why. Separately, when `error()` *does* fire (an import failure), it calls `this.$app.empty()` — and in this site `$app` is the whole chrome node, sidebar included, so the one page that most needs navigation is the one page where the sidebar has been deleted. Both are one-line-scale fixes (wrap `page.activate()` too; render the error into `$pages`, not `$app`) against a real, visitor-facing failure mode — the kind of trade I take immediately, because it costs almost nothing and removes a genuine dead end.

## 2. Divergence that matters

Nothing here breaks the arbitration list — I checked LOAD, DIFF, MODE RESOLUTION, MODE CARRIER, ORDERING, `link()`, adoption, `.page-content`, and the empty hooks against the code, and all ten hold exactly as decided. The divergence worth naming is from my own proposal, not the arbitration. I had `App.resolve()` return the whole chain and loop `chain.forEach((page,i) => page.activate(i === chain.length-1))`, with mode as a separate `App.apply_mode(chain)` step. The built code inverts that: `Page.activate()` (`Page.class.js`) is the one verb, and it pulls its own ancestors along via `mount()`'s recursion before handing the whole chain to `App.mark()` for classing/mode/order in one place. That's a better shape than mine — it's what makes `button("Intro").click(() => intro.activate())` work from a page that was never resolved from a url at all, which my `resolve()`-only entry point didn't support. Worth recording because it's a real structural change that happened without a line in the council's decision table, not just an implementation detail.

## 3. Silent failure

Covered above (§1) — the unguarded `page.activate()` in `App.load()` is the one that would never announce itself the way `App.error()` does; it just leaves the page blank. Second, smaller one: navigating to `/about` (no trailing slash) resolves successfully to the same page as `/about/`, because `App.resolve()` only ever looks at `pathname.split("/").filter(Boolean)` and never compares back against `page.url`. Harmless today — the page renders correctly and sidebar highlighting still matches, since marking uses the canonical `page.url` — but it means two different address-bar strings silently render as "the same page, everything in agreement," which will confuse anyone who later treats the url as ground truth (a Router's `pushState`, a canonical `<link>`, an analytics event keyed on path).

## 4. Dissent

Cutting `.page-content` was the right call, not a real dissent — I kept it specifically to survive the nested-flex traps that don't exist any more in a flat, sibling-per-depth container, and I'd have cut it myself once that trap was gone. The one thing I'd still flag: `.page-content` was quietly doing a second job I didn't name loudly enough in the proposal — separating "am I visible" (the outer box, `mode`/`display`) from "where do my children go" (an inner box a fourth mode could redirect independently of the title). Losing that split costs nothing for the three modes built here. It's the first thing I'd expect to *re-add*, not cut further, the day a tabs-style mode needs a slot distinct from the page's own `<h1>` — worth having on record now rather than rediscovering it mid-implementation.

## 5. Readme vs code

`readme.md` says "Two classes, **~165 lines**, and it runs." The actual files are `App.js` (149 lines) and `Page.class.js` (107 lines) — 256 together, about 55% more than claimed. The ~165 figure traces back to the demo copy in `site/page.js`'s `content()` (`App ... ~90 lines`, `Page ... ~75`), which is itself stale against the real files — so the inaccuracy exists in two places, and the readme's number is a copy of the wrong one rather than an independent count.
