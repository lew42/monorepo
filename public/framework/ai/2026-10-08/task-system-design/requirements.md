## Step 2 — the design (the point of this task): `design.md`, one screen + links
The owner's thinking, to be turned into a proposal (decide with the `decide` skill: choose a default, record the alternative):
1. **Composition, not inheritance.** A task *has a* page (`task.page`, `page.task` reference each other); it does not extend Page, because Page is already a big Item with many methods and extending it causes namespace conflicts. The same pattern for **sessions** (`session.page` / `page.session`): `session.jsonl` holds session facts, `page.jsonl` holds page facts; a task likewise has `task.jsonl` + `page.jsonl`. General principle: almost anything can have a page rather than be one. Specify how the two files render in harmony, which loads when, and the one place a fact lives (reference, don't duplicate).
2. **Tasks live anywhere.** A task is created inside a session, a page, a module, and can be **moved** (core page CRUD: create / read / update / delete / move should be solid and easy; note this gap in `core/Page` docs) while keeping a **backlink**: the creating session still lists it even if the data moved. Offer 2–3 ways to do the backlink and recommend one.
3. **Recursive structure.** A task is a list of tasks (a task *has* or extends `List`); completion state of a parent is the aggregate of its subtasks. State whether recursion is worth it; recommend.
4. **Lifecycle**: start / pause / resume / finish (plus blocked, abandoned), who may change state, and how it shows in the UI; an AI planning a project can lay out a structured hierarchy of tasks and subtasks *before* starting any.
5. **UI**: a task card (name, state, progress aggregate, owner, links to session and page, sub-task rows) using existing card/list components; where tasks appear in the Sessions dashboard.
6. **Works with the new Session system** (`2026-10-08/session-class`, `sessions/doc/record-spec.md`, `data-architecture-2026-10-08.md`): sessions create and manage tasks; a task's cost can be rolled up from its sessions.
7. **Tools**: how agents create/update tasks. The SDK lets us define a **plain node function as an in-process tool** (see `Servex/agents/tools.js`, `createSdkMcpServer`/`tool`), which needs no networked MCP hop. Document which Servex tools use which mechanism, and recommend using in-process tools wherever no network is needed; list the tool set the task system needs. Add this to the AI tools docs (`ai/doc/mcp.md`).
