# 3c — the layout vocabulary (standard / wide / fill) and mining /imagine/

Read as a new user chasing the owner's three words. There are **four separate systems** that
each claim a "width" or "layout" vocabulary, and none of them uses the owner's names
(standard/wide/fill) for the owner's meanings. That mismatch is the main finding.

## Findings

- **wrong** — the owner's "wide" (two columns, any proportion, stacks on mobile) is not the
  site's `width: "wide"`. Core's word means *one track, every leftover pixel, no second
  column* ([`core/Page/words.js`](/framework/core/Page/words.js) `WIDTH`). The owner's "wide"
  is closer to the `main-aside` **arrangement** word, or to a 2-column entry in the Layout
  catalogue ([`equal`](/framework/core/Layout/equal/), [`golden`](/framework/core/Layout/golden/),
  [`main-aside`](/framework/core/Layout/main-aside/)).
- **wrong** — the owner's "fill" (three or more standard columns) is not core's `fill`. Core's
  `fill` is a *column's own width inside a `columns()` row* — "take the leftover, no ceiling"
  ([`doc/columns.md`](/framework/core/Page/doc/columns/)) — not "arrange the page as 3+
  columns". The owner's "fill" is closer to a Layout-catalogue 3-column entry
  ([`thirds`](/framework/core/Layout/thirds/), [`dashboard-row`](/framework/core/Layout/dashboard-row/))
  or to the columns realm's **even mode** (`this.columns({ even: true })`), which computes how
  many same-width columns fit a row.
- **missing** — there is no single doc page that answers "I want standard / wide / fill" and
  hands back one word to type. A new user has to already know the difference between a page's
  `width:` word, a column's `width:` word, an `arrangement:` word, and a Layout-catalogue name
  before they can find the right one. `doc/layout.md` even says this itself: *"We need a
  strong, simple strategy for robust page layouts and we do not have one yet."*
  ([`/framework/core/Page/doc/layout.md`](/framework/core/Page/doc/layout.md), open since
  2026-08-17).
- **unlinked** — [`core/Page/doc/layout-overview.md`](/framework/core/Page/doc/layout-overview.md)
  (the "five ideas, each with one home" index) never mentions the six page words
  ([`doc/words.md`](/framework/core/Page/doc/words.md)) or the Layout catalogue
  ([`/framework/core/Layout/`](/framework/core/Layout/)) at all — the exact two places a reader
  chasing "what are my layout choices" needs next.
- **verbose** — `doc/columns.md` is 660 lines carrying the whole design history (three tuning
  passes, measured pixel tables) ahead of the one paragraph a new user needs: the six-word
  table near the top is good; everything from "A column that is open never pays for the next
  one" down is process record, not a new-user path.
- **buried** — top-down shape (background, padding, full-bleed) is real and documented but
  scattered: `surface`/`background` live in `doc/words.md`, the grid tracks (`main`/`wide`/
  `bleed`) live in [`/framework/styles/doc/layout-system.md`](/framework/styles/doc/layout-system.md),
  and column padding/bleed live in `doc/columns.md`'s `bleed` section. The owner said this
  "counts as much as column count" — it has no page of its own.
- **missing** — `/imagine/` is not linked from any core/Page layout doc. A reader who lands on
  `doc/layout.md` or `doc/columns.md` has no path to the 25+ past layout demos below.

## Simplest first

- **Standard (one column, 300–1000px, responsive):** the site's actual default — a page that
  says nothing. `new Page({ content(){ md("..."); } })` renders in the `main` track (40em ≈
  the standard range) automatically. This is the "before" example `doc/words.md` already
  shows — put it first, everywhere "standard" is asked about.
- **Wide (two columns, any proportion, stacks on mobile):** the Layout catalogue's
  [`main-aside`](/framework/core/Layout/main-aside/) or [`equal`](/framework/core/Layout/equal/)
  — one `arrangement: "main-aside"` on a page, not a hand-built grid. Show the code, then the
  live page at wide and at 390 stacked.
- **Fill (3+ standard columns, responsive):** `this.columns({ even: true })` from
  [`doc/columns.md`](/framework/core/Page/doc/columns/) — the two-line arithmetic
  (`N = floor(available / recommended)`) is the whole mechanism. Show the Finder live, then the
  `/imagine/platform/` before/after numbers already measured (535px → 640px at 1280).

## Suggested structure

A **Layout** top tab on `core/Page/`, separate from Methods/Properties, with left-nav:

1. **Choosing a layout** (new page) — the owner's three words as the entry point: standard /
   wide / fill / full-bleed, each one sentence + a link to its real mechanism. This is the page
   that does not exist yet and is worth building first — it is pure navigation, cites nothing
   new.
2. **Standard** → links to the page grid (`main` track) in `layout-system.md`.
3. **Wide** → links to `main-aside`/`equal` in the Layout catalogue.
4. **Fill / columns** → `doc/columns.md`, trimmed to: the six width words table, the `default`
   column, the even mode. The tuning history (three passes, the measured pixel tables) moves to
   a linked `doc/columns-history.md` — a reader chasing "how do I make 3 columns" doesn't need
   to read the third tuning's rejected alternative.
5. **Top-down shape** (new page) — background/padding/bleed in one place: `surface`,
   `background`, and `bleed` pulled together from `doc/words.md` and `doc/columns.md`.
6. **The full catalogue** → link out to `/framework/core/Layout/` (30 arrangements) as "more
   shapes than the three basics."

Too trivial for their own page: `narrow` and `reading` (one line each in the words table is
enough — they're "standard, capped tighter" and "standard, the default").

## Value per space

1. **Choosing a layout (new nav page)** — fundamental, one click fixes the whole confusion
   above, costs almost nothing to build (it only links).
2. **Standard = the default page** — fundamental, trivially shown (a page with no class).
3. **Fill = even columns** — fundamental for the owner's ask, already has a live demo (Finder)
   and measured numbers ready to reuse.
4. **Wide = main-aside / equal** — fundamental, has a live catalogue page already proven at
   seven widths.
5. **Top-down shape (background/padding/bleed)** — the owner named this as equally important;
   currently invisible, worth a page.
6. **The word-collision warning itself** (wide ≠ wide, fill ≠ fill) — confusing but necessary;
   one callout box, not a whole page.
7. **`hug`/`small`/`large` column words** — fundamental to columns but secondary to the
   standard/wide/fill story; keep in `doc/columns.md`, don't promote.
8. **Even vs. elastic mode / `fit: floor` vs `round`** — real and well-measured but deep
   process detail; confusing to a new user and hard to show briefly — low value per space,
   leave it where it is (`doc/columns.md`).
9. **The Layout catalogue's 30 named arrangements** — valuable as a browsable reference, but
   each one is proven CSS, not paging vocabulary; link out, don't fold in.
10. **Column-resize/drag mechanics** — real feature, but a "how it works" detail, not part of
    the standard/wide/fill choice; stays a footnote.

## Mining /imagine/ — past layout work worth folding into paging

- [/imagine/layouts/](/imagine/layouts/) — dead end by design: redirects to
  `/framework/core/Layout/` (the 30 named arrangements) and `/layouts/` (the judged standard).
  Nothing to fold in; it already points at core.
- [/framework/core/Layout/](/framework/core/Layout/) — **the 30-arrangement catalogue itself**,
  each proven at seven widths — this IS the "wide"/"fill" content, just not named that; fold by
  linking, not copying.
- [/imagine/paging/](/imagine/paging/) — the six-word live control surface (navigation,
  content, width/"room", arrangement, surface+background, type size); every value is a real
  page you can turn a dropdown on. Worth linking from `doc/words.md` as "try it live."
- [/imagine/sections/](/imagine/sections/) — horizontal bands cut into 2/3/4 columns with a
  framed middle; six distributions including `rail-main-aside`. Relevant to "wide" and "fill"
  as an alternate, non-columns way to get multi-column.
- [/imagine/shells/](/imagine/shells/) — ten whole-app chrome layouts (rails/bars/canvas); a 3×3
  grid where an undeclared part costs a 0px track. Relevant to "top-down shape" (background,
  padding) more than to column count.
- [/imagine/screens/](/imagine/screens/) — eight demos of what "next" does to the screen
  (divide, stack, deck, uneven, quad…); the clearest existing "fill = 3+ columns, how they
  respond" material — `full` replaces, `fill` joins and divides. Worth citing directly under
  the fill/columns doc.
- [/imagine/gallery/](/imagine/gallery/), [/imagine/vary/](/imagine/vary/),
  [/imagine/team/](/imagine/team/) — columns-realm case studies (a roster+board app); useful as
  "here's fill/columns used for a real app," not as vocabulary.

## Note

Not read in full (budget): every `/imagine/paging/library/` preset page, `/imagine/shells/`'s
