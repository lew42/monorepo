# The task loop: node opens, chases and checks tasks

Design (picture and table): [/framework/ai/2026/09/28/skills-as-a-workflow-tasks-chased-by-nod/design.md](/framework/ai/2026/09/28/skills-as-a-workflow-tasks-chased-by-nod/design.md). Owner's words: `.claude/prompts/2026-09-28.jsonl`, the prompt containing "consider the skills system kind of a workflow process". Build every row marked **task-loop**:

1. **Open by node:** `spawn_agent` takes `task: {dir, card, brief}` and writes task.jsonl line 1 (session_id, card, brief, model) before the agent's first turn. The new-task skill then says: already done for you if your brief names a task dir.
2. **The role's skills:** `roles.js` takes a list of skills per role and puts them all in the first turn.
3. **The task loop** in Servex: every 5 minutes, find open tasks (no `landed_at`) that have been quiet for 20 minutes, or whose agent ended without landing. Wake the owning agent with "land, or say why", at most twice, 30 minutes apart; then put the task on the Waiting-on-you list (a `card_ask` if that task has landed, else a card message). Log each chase in the task's own task.jsonl. Only a landing or the owner closes a task.
4. **Doc check on landing:** `Server/on-landing.mjs` also checks that every module the task touched has a readme.md, a doc/ and resolving links, and posts one nag line on the card when not.
5. **Land needs an outcome:** the ledger refuses a `landed_at` with no outcome and says so in the task log.
6. **Docs:** `Servex/doc/task-loop.md`, one screen, with the picture first.

**Proof:** a test task left quiet for 20 minutes (shorten the timer for the test) gets chased, then escalates; a real landing without a doc gets its nag; the count of today's open tasks the loop found on its first run. **Fence:** `Servex/` (the loop and the spawn line 1), `Servex/agents/roles.js`, `Server/on-landing.mjs`, `.claude/hooks/ledger.mjs` (the outcome check only), the new-task skill's one line. Coordinate with recursive-pairs if it is running: it owns agent idle/stop/resume. Own worktree; Servex changes proved on a private Servex first.

## Ownership of the heartbeat (mastermind-servex-3)

**Task-loop owns the heartbeat and the step loop**: the once-a-minute check, the prompt after 5 silent minutes, escalation, and `finish_step`. Recursive-pairs owns only stopping and resuming idle agents, and calls nothing of its own on silence. Build the heartbeat on agent events (turn ended, tool called) where Servex already emits them, with the minute tick only as a backstop.

In short, fold into your design:
1. **Event-driven, not timed wakes.** React the moment something happens (a message, a file line, an agent ending its turn). A 15-minute wake is a blind fallback only.
2. **A step loop:** a plan with N steps. The harness re-prompts the agent with step k ("here is step 2: …"). The agent calls a finish-step tool, and the loop sends step k+1. Code, not the AI, keeps the place.
3. **A heartbeat:** a working agent posts an update about every minute. If it has been silent for 5 minutes, the harness prompts it for an update. If it's still silent, escalate to the Servex mastermind (restart it, or look into it).
4. **Harness-agnostic:** write all of this as plain node over agent messages, so it works the same on the Claude SDK today and on an OpenRouter or local-model harness later.

## Added: a landed task's dev server goes down (mastermind-servex-3)

On 09-28, 24 dev-server pairs (about 2.1 GB) were still running for worktrees whose tasks had landed days before, and 37 were running in all. Nothing takes a worktree's server down when its task ends.
7. **On landing**, the task loop runs `node Server/worktree-down.mjs <worktree>` for the task's worktree: it stops the server, and removes the worktree only when it is clean. A dirty one is reported on the card with its untracked files named, because those may be work that never merged.
8. **A sweep on the loop's tick:** stop any `server.js` + `run.js` pair whose worktree dir is gone, or whose task has landed. Never touch the main tree's server or Servex's own.
9. **"Landed" is not enough to take a server down** (09-28: collab-rounds had a `landed_at`, but its branch wasn't merged and its minion was still fixing a bug when its server was stopped). Stop a worktree's server only when all three are true: the task has `landed_at`; its branch is merged into michael/dev (`git merge-base --is-ancestor`); and no live agent is working whose parent is that task's mastermind (or whose own task dir is it). Otherwise, skip it and say why on the card.
