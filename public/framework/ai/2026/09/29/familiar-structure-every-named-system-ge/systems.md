# Systems that need a familiar-structure page

A **system**, in the owner's sense, is a repeated pattern of code — "a certain way of doing
things" — not a single class. `core/Page/jsonl/` is the model: its own folder, its own readme,
one job (explain the page.jsonl log). Most patterns below don't get that; their explanation is
scattered across a module's `doc/*.md`, a skill file, or a one-off task page that will scroll off
the dashboard.

Sorted most-foundational (everything else depends on it) to least.

| System | What it is | Lives today | Has its own page? | Name | Suggested page |
|---|---|---|---|---|---|
| `children:` declaration | A page names its children in one string/array/object; nothing is crawled — a page exists only because its parent named it | Read by `Router.js`, written by every `page.js`; explained in `core/Page/doc/declaring.md` and `data-children.md` | No — split across two doc files inside Page's doc, no page of its own | Clear enough as `children:` | `core/Page/children/` — "how a page gets found" |
| `route()` | A page claims a URL segment it never declared as a child — the dynamic-page escape hatch (Router tries memory, then `route()`, then a file) | `Router.js` (calls it), implemented per-page, e.g. `imagine/paging/make/page.js` | No — mentioned only in code comments and scattered doc asides | Clear as a word, but easy to confuse with `Router` routing in general | `core/Page/dynamic/` — "a page that answers a URL it didn't name" |
| `page.jsonl` (the log) | Append-only JSON-lines file that IS a page's content/history — task cards, day logs, AI cards all use it | `core/Page/jsonl/` | **Yes — done right.** Own folder, own readme | Clear | (model; no action) |
| Thing.View / parts as static subclasses | A component's sub-pieces (`Panel.View`, `Item.View`) are static nested classes on the parent, not separate files, so the parts stay visibly owned | `core/View/`, used throughout `core/`, `ext/Panel/`, named as a rule in the `code` skill | Partial — `core/View/` has a readme about View itself, but the "parts are static subclasses" convention is only written in `.claude/skills/code/SKILL.md`, not on any page a browsing reader finds | "Thing.View" is not a name anyone types — the pattern has no name on the site at all | `core/View/doc/parts.md` (or a short page: "static subclass parts") |
| task.jsonl verbs | The fixed vocabulary (`assign`, `log`, `decision`, `agent`, `chat`, `ask`, `verdict`, `rank`…) that a task's log is built from; an unknown verb silently renders nothing | `ext/JSONL/doc/task-jsonl.md`, read by `ext/AITask` | Yes — `ext/JSONL/` has a page and this doc file | Clear | (fine as-is; maybe promote `task-jsonl.md` from a doc page to a top-level JSONL "dialects" list once a second `.jsonl` format exists) |
| Card folders (`page.jsonl` per card) | "One folder per card" — `Servex/cards/Cards.js` is the only writer; a card's id is its folder path; sub-cards nest to any depth | `Servex/cards/readme.md` | Yes, but it's a **Servex-only** readme — no equivalent page on the actual site under `/framework/`, even though every AI-board card the owner looks at is one of these | Clear ("card") | Add a short `core/Page/jsonl/cards.md` page (or link) so a site reader lands on the same explanation Servex agents get |
| `place` lines | A card's `page.jsonl` can carry a `{"place": {...}}` line that embeds another module's live output (a decision list, a file tree, this very report) directly into the card | Drawn by `public/framework/ai2/card.js` (`draw_placed`); one example documented in `Server/doc/decide.md` for the Decision case only | No — the *general* mechanic (any module can be "placed") is undocumented; only the one Decision-module example is written down | "place" reads fine once you know it, opaque before that | `ai2/doc/place.md` — the general contract: what a placeable module must export, how it's drawn |
| Width words (page columns) | Six fixed words (`full`, `wide`, `column`, …) that set a page's column width; a drag writes the same tokens one level stronger | `core/Page/doc/columns.md` (page-level) **and separately** `ext/layout/doc/vocabulary.md` + `styles/layouts/*/words.js` (layout-level) | Partially — each half has doc, but a reader has no single page tying "width word" together as one concept used in two places | Same name, two systems — genuinely confusing | A short `styles/layouts/words/` page that states the one word-list and links both consumers, instead of two independent explanations |
| The reload hold | `node Server/hold.mjs on/off --paths …` — the fence that stops an agent's batch of writes from flashing broken pages on the owner's live tabs | `Server/hold.mjs`, explained in `CLAUDE.md`, `Server/doc/watch.md`, and two task write-ups (`ai/sessions/2026/09/19/reload-hold/`, `ai/sessions/2026/09/22/f875ec48-d91a-4890-b15f-db197b55aa13/reload-rethink/`) | No permanent page — the fullest explanation is two dated **task** pages, which will scroll off the dashboard even though every agent needs this rule forever | Clear ("hold") | `Server/doc/watch.md` already exists as the intended home — it just isn't a site-browsable page since `Server/` is dev-only; worth a short `dev/` mirror page since agents (the readers) hit it via CLAUDE.md, not Server's own doc tree |
| The readme chain | A directory/page-scoped agent opens already having read every `readme.md` from repo root down to it, in order, before touching anything | `Servex/doc/readme-chain.md`, code in `Servex/agents/readme-chain.js` | No site page — Servex-internal doc only | Clear | Belongs beside the `code` skill's directory-readme-first rule; a short page isn't essential since it's an agent-only mechanic, not something the owner browses |
| The `.jsonl` append helper | `node .claude/hooks/append.mjs <file> <lines.json>` — the only sanctioned way to add a line to any `.jsonl`; stamps clock, sniffs newline, re-parses, refuses on a bad line | `.claude/hooks/append.mjs`, explained in the `new-task` skill and `ext/JSONL` doc | Partial — `ext/JSONL/readme.md` explains the *format*; the *helper script* itself is only explained inside skill text, not in JSONL's own doc | Clear | `ext/JSONL/doc/appending.md` — one page, "how anything writes a line," linked from every skill that currently repeats the warning |
| Demo system (five blocks) | Every module's demo page is built from five fixed blocks; `.page.standard` layout; `demo.tree()` | `ext/demo/` | Yes — readme + page | Clear | (fine) |
| `catalog()` rail | The picker rail used to browse a set of named things (layouts, demos) | `ext/catalog/` | Yes — readme + page | Clear | (fine) |
| Doc system (`ext/Doc`) | Generates a module's Docs tab live from its readme + `doc/*.md`, replacing the old "classdoc" | `ext/Doc/` | Yes — readme + page + overview | Clear | (fine) |
| Saver / Draggable / Panel | Persistence, drag gestures, and the arranging-chrome system (divide/drag/align/fill) | `ext/Saver/`, `ext/Draggable/`, `ext/Panel/` | Yes, all three have readmes | Clear | (fine) |
| Worktree take/return + `merge.mjs` smoke test | Every minion's fixed landing path: `take_worktree` → write → `node Server/merge.mjs` (loads touched pages, checks zero console/page/module errors) → merge → `return_worktree` | Explained inline in the `minion` skill; code in `Server/merge.mjs` | No dedicated doc page — it's skill text plus a script, nothing an owner would browse to | Clear ("worktree", "merge") as agent jargon | Low priority — this is an agent-only workflow, not something the owner looks at; a `Server/doc/merge.md` would mainly help a future minion reading code cold |
| Spawn / requirements protocol | Orchestrator writes a brief to `ai/<date>/<slug>/requirements.md` with explicit file-ownership fences before spawning a minion | `Servex/agents/`, described in memory notes and the `minion`/`spawn-requirements` conventions, not in a single doc file | No — reconstructed from scattered task write-ups each time | Clear | `Servex/agents/doc/requirements.md` — the fixed shape of a brief, once, so it stops being re-derived per task |

## What would help most

Five pages would close most of the gap, in this order. First, **`core/Page/children/`** and
**`core/Page/dynamic/`** — `children:` and `route()` are the two most-used, least-explained
mechanics in the whole framework; a newcomer reads a `page.js` and hits both in the first ten
lines with no page to click through to. Third, **`ext/JSONL/doc/appending.md`** — the
`append.mjs` helper is quoted as a warning in half a dozen skills instead of explained once, and
every agent that skips it corrupts a log. Fourth, a short **`core/View/doc/parts.md`** for the
static-subclass-parts convention — right now it exists only as a sentence in the `code` skill,
so a reader has no page to check a real example against. Fifth, **`ai2/doc/place.md`** — the
`place` line already threads through cards, decisions and this very report, but only one
consumer (Decision) is documented, so anyone building a second placeable module is guessing at
the contract. The width-words split (page-level vs. layout-level) is real but lower priority: it
confuses only someone reading both doc trees side by side, which is rare.
