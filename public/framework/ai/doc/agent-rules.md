# Agent rules — memory, history, safety and cost (long form)

`CLAUDE.md` keeps one line for each rule below; this is the full wording, moved here word for word on 2026-10-22 ([the move map](../sessions/2026/10/20/session-e00f55c9/sessions-and-tasks/readme-roles/moves.md)). Linked from [the ai readme](../readme.md).

## Memory, history, safety

**Context must not die in sessions** (the owner, 2026-10-08): the useful decisions and insight from a session go to the page or module they concern, linked back to the source prompt, not left in chat. Before major surgery on a system, gather every past ask about it into one place, weed out the conflicts, decide, then build. Agents post an update or log line at least every ~5 minutes of work; a quiet agent is presumed stalled (Servex's `TaskLoop` chases it).

**File each ask the first time** (the owner, 2026-10-21): every owner prompt's asks are filed the first time they are read, as tasks on the session's record or as one-line notes in the readme they concern; a task is a proposal until accepted (`core/Task/readme.md`, "Using tasks").

**Link, don't regenerate** (the owner, 2026-10-08): never spend tokens repeating what is already written. Reference the original prompt, session, task or doc by link (a text link first; embedded previews later, since they load a lot of data). The owner's suggestions are logged on the page they concern so later agents find them there, as a reference to the source prompt, not a retyped copy.

**Never destructive** (the owner, 2026-10-08): data integrity first. Do not delete logs, merge sessions or records, overwrite history, or eliminate anything; add, link and reference instead, and commit as often as you can so git is the undo. If something truly must go, move it aside (a `salvage/` branch, an archive path) and say so. The AI can find a non-destructive way.

**Moves and renames are scripted, never retyped** (the owner, 2026-10-08): to port, move or rename files (sessions, tasks, logs), write a node script that does it procedurally (`git mv`, a dry-run first, a manifest of every old to new path, reversible), preserving everything. An AI never copies data by reading and rewriting it. Also run a **visibility check** on anything we work on: link whatever exists in the repo but not on the site.

**Commit after every working step** (the owner, 2026-10-08): small, frequent commits are the versioned log; uncommitted progress is lost progress and invites regressions. Commit each step that works before starting the next (smoke-test first: never commit something broken; once it works, commit, since git can always roll it back), in a worktree, and merge after reviewing the diff. **Keep GitHub current** (the owner, 2026-10-29: "when we are committing, we should be pushing to GitHub regularly"): a cloud agent clones from GitHub, and on 10-29 its clone was 6,089 commits behind. `Server/merge.mjs` pushes michael/dev after every landing; a commit made straight on michael/dev is followed by `git push origin michael/dev`. When a page is rendered by a template or layout, make it findable which one and where it lives.

**Stream, don't poll** (the owner, 2026-10-08): anything that happens in real time (a transcription, a session doing work, cost, logs) is architected as a stream (JSONL append + the `live()` tail) with updates in about 100 ms, never a timed refresh that shows stale data. When you find yourself writing `setInterval` + `fetch`, look for the stream first.

## Open a task for each piece of work (the owner, 2026-10-24)

A task is a bucket: every token a session spends between its `start` and `complete` is counted against it, and tokens with no task open show as untracked. **Every agent opens a task for each piece of real work and closes it; a tab files each owner ask as a task on its own session.** Work that fits the task you are on needs no new one; unrelated work opens a sibling or child first. A spawned agent is handed its task; an agent given a prompt with no task opens one as its first act. After a hand-off only the agent that holds a task writes to it until it hands it back, and the hand-back starts the review. The full rule, the table of who may write what and the proposed enforcement hook: [task-buckets.md](task-buckets.md). How a task is added and where it shows: [core/Task/readme.md](/framework/core/Task/readme.md) and [core/Session/readme.md](/framework/core/Session/readme.md). The monitor: [/framework/ai/tracking/](/framework/ai/tracking/).

## Name the mastermind for its job (the owner, 2026-10-25)

There is ONE `mastermind` role; "task mastermind" and "sub-mastermind" are only old words for it (aliases in `Servex/agents/roles.js`, [names.md](/Servex/agents/doc/names.md)). Whoever hands off a piece of work, the voice smart seat included, spawns `spawn_agent({role: "mastermind", path: "<folder the work is about>", name: "<its job>"})`, so the id says what it is for (`mastermind-dictation-fix`) instead of `task-mastermind-2`.

## Start fresh children; revive only as a rare exception (the owner, 2026-10-25)

Reviving an old agent (a `send_to_agent` with `revive: true`, or a message to one whose parent is another session) books its new cost and task completion on its **old parent**, not the session you are working in. So work for a session is done by **fresh child sessions of that session** (`spawn_agent`), never by waking an agent that belongs to another session. Reviving is a rare exception, and when you do it, say why in the task log. What makes fresh the safe default: **a mastermind keeps its state documented at all times** (decisions in the module docs, progress in its task log, an open task per piece of work), so a fresh one reads them and resumes. Related: [sessions-and-tasks.md](sessions-and-tasks.md), identity and cost counted once: [core/Session/doc/identity.md](/framework/core/Session/doc/identity.md).

## Structured output first (the owner, 2026-10-24)

Law 5 already says that chat is never read again and the committed repo is the record. This rule is about the **form**: an agent's result is written to a file first, in a structured form, and chat gets a pointer second. "Structured" means a shape a program can read and the owner can filter: a JSONL line (`find`, `outcome`, `result`, an item through the item tool), a table, or a doc with a fixed header, never a long paragraph of findings. Write each result **as soon as you have it**, not in a final report, so a stopped or compacted agent has still left its work. The chat line that follows is one sentence and a link. **The one exception is the sidebar chat**, where the owner is talking with the agent live: there the answer is the reply, and anything that should outlive the talk is also written to its page. Example of the form: the past-work worker logs `find` lines ([skills/past-work/worker.md](../skills/past-work/worker.md)).

## Cost and roles

- **Usage pace (the owner, 2026-10-02):** every mastermind reads the usage snapshot when it starts and before each spawn (`ai/usage.json`; Servex injects it). Pace = the share of the week used ÷ the share of the week gone. Over pace: Sonnet by default, no Opus without a stated reason, fewer agents, no redundant checks, and review the work yourself when the files are already in your context instead of spawning a reviewer. Minions just do their task.
- **Audits go to Haiku, under 100k tokens** (the owner, 2026-10-08): task audits, readme audits, searches and fan-outs use Haiku in small inlined batches; Sonnet is for UI and object-oriented code. A request over 100,000 tokens costs about 5x per token, so every Haiku job stays well under it (aim for 30–60k; never drift over by accident); a node script chunks big inputs (a raw session file, a log) into pieces sized to fit with room for the reply. No Batch API / API key for now.
  **When to go past 100k (the owner, 2026-10-24).** For a **long read** the large context is the point, and Haiku is still the cheapest way to buy it: a deep dive through a readme chain and the docs it links, or a sweep over many search terms (past-work, per-file docs, a module audit). Go past 100k when all of these hold: (1) the job is mostly reading and the output is short (a list or a few lines, written to a file); (2) one agent reading everything beats chunking, because the answer depends on seeing the pieces together; (3) the plan names the expected size and the dollar cost in the brief's `Budget:`; (4) a node script has already cut out what does not need reading (it filters, the model reads). Otherwise chunk under 100k. Never let a Haiku job *drift* over: the limit is a decision stated in the brief, not an accident. The first trial is [past-work-per-file-docs](../sessions/2026/10/24/session-e00f55c9/past-work-per-file-docs/) (its `findings.md` has the method notes and the real token count); measured: about 116k tokens of reading, and it found the right answer (`doc/file/<path>.md`) with a short result. Why a long read stays disposable and a fresh pass stays unbiased: [context.md](context.md).
- **Mind the token burn** (the owner, 2026-10-08): every agent weighs the token cost of a task before starting it, and above all a mastermind. Every turn re-processes the whole context, even on a cache hit, so iterative, long-winded work that keeps going back to the model burns tokens. Rules: (1) **let a script read and calculate** (a node script that reads the data and prints a summary is cheap and good); the model reads only the summary. (2) **Batch tool calls**: request all the files you need in one turn, never one file per turn. (3) **No session replays or long audits unless asked.** (4) When a long iterative pass is truly needed, give it to Haiku, not Sonnet or Opus. (5) Keep sessions short and start fresh when the topic changes.
- **No hard fences between roles** (the owner, 2026-10-08): a minion that can do a mastermind's job should just do it. Do not add rules or tool fences that stop a capable agent; the mastermind is simply the one that decides and splits work.
