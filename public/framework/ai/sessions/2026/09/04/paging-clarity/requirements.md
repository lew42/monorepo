## What lands (in this order — the first three are the point)

1. **The hub teaches in one screen.** At the top, in full plain sentences: what a "page system" is here (a page has an icon, some content, and children; the system is what a click on a child does and what the page looks like while it does it). Then the four mechanisms, each shown by a small, obviously visual example right there on the hub, with its takeaway sentence above it: **swap** shown as TABS (`ext/tabs` — click a tab, the panel's content changes, the box does not move); **launch** shown as a column appearing beside a small box; **expand** shown as an accordion row growing; **takeover** shown as the row becoming one page (a still image or a tiny live version). Then "How to explore this", three numbered steps in plain words.
2. **Sizes mean size.** The content chips (`xs`–`xl`) must grow the SAME sample — the box visibly gets bigger with more of the same thing — never swap the text for different text. The layout chips (`center`–`full`) widen the box. Show the change in place, and say what changed in a caption ("content: s → l; the box grew from 12 to 31 lines"). This is the owner's stated bug; prove it with `ui-test` before and after.
3. **Examples you can see.** The walk becomes **Examples**: the first five each show the RESULT and, beside it, the CONFIGURATION that made it — the three or four `this.pick(...)` lines, visible on the page, not behind a tab. A reader clicks through five examples and sees how it works.
4. **Real things as content.** The `l` and `xl` samples are things the site already built, not placeholder prose: a `ui/` component demo, a `styles/layouts/` arrangement, a blog `Section`, a `previews()` wall, a `Panel`. One table on the hub says which built thing appears where, with links. Read `public/framework/ui/readme.md`, `styles/layouts/`, `ext/Panel/readme.md`, `public/blog/` (Section).
5. **Dynamic pages, temporary persistence, RESET.** Pages created at runtime from the paging vocabulary, with no files on disk — read `public/framework/core/Page/generator/readme.md` first: it already builds real page trees from a spec string, and `/imagine/paging/explorer/` already put mag in it; reuse that, do not build a second tree-from-spec. Everything a reader changes is remembered with `store()` under ONE namespace (say which key shape), and a **RESET** button on the hub clears that namespace and restores the baseline suite. Prove it: change three things on three pages, press RESET, all three are back. Then decide and record in `doc/decisions.md`, with the reason, how CRUD should be added next — `EditablePage extends Page`, or create/edit/delete as `Paging` parts (the `code` skill says parts as static subclasses; weigh it honestly) — and write the store contract a CRUD minion will build on (create a page from a name + words; edit its words; delete it; all inside the namespace RESET clears). Build the smallest CRUD you can prove in the budget; if you stop at the contract, say so.
6. **Every page in the realm starts with its takeaway sentence.** Including the trees, `rightnav/`, `toolbars/`, `explorer/`, `critique/`, `inventory/`. Rewrite headings and captions that only the author would understand.
