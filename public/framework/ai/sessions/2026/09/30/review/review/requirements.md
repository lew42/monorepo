## What the owner asked (each traces to a sentence)
1. **Screenshots belong to the task.** The task mastermind takes them at 400, 1200, 1920 and 3440, saves them in the task folder, and links them from task.jsonl, so anyone can open them in the browser later and ask "was this screenshotted, and why was it approved when it's clearly bad?"
2. **One review, loaded with the whole design system.** One reviewer reads the page, layout, css and content skills, then runs a fixed list of review questions: the same rules, worded as definitive criteria. One reviewer does it all in one pass, the requirements included.
3. **The questions, per system:** requirements (each of the owner's asks, met?); page structure; navigation (first identify the techniques used: tabs, a rail, a bottom rail, a sidebar, a sheet, a modal, full screen; plain links need not be listed; then check each); layout; sizing (fixed height, or auto?); wrapping; spacing and padding (stacked?); colour and contrast; flow.
4. **A review report per task:** each question, its answer, and its evidence (a screenshot region or a measurement), saved in the task folder and linked from the card.
5. **The questions are documented in one place, and each system keeps its own questions beside its rules,** so a new rule brings its question with it.
6. **The measurable parts run by themselves** (12:35): tab-bar row count, stacked padding at the left edge, unexpected wraps, band share of the screen; mastermind-page's `--bands` in `Server/layout-check.mjs` measures these; reuse it, never a second set.

## The design (decided by the architect; build it, and say where it fought you)
- **Questions live beside rules.** Each of `.claude/skills/{page,layout,css,content}/` gets a `questions.md`: a numbered list, each question one sentence, definitive, with the rule it comes from named in brackets, e.g. `3. Is every gap and corner from the spacing clamp, never a constant? [css: the padding law]`. Navigation and sizing/wrapping questions go in `layout/questions.md` unless the page skill owns navigation; requirements questions live in the review skill itself. You MAY add these files (the architect authorises it for this task only); you may not change any SKILL.md except to add one line pointing at its questions.md. Show the architect the `.claude/skills` diff before merging.
- **`.claude/skills/review/SKILL.md`** (new, the one place): who the reviewer is (fresh eyes, never the author), what it loads (page, layout, css, content, and every questions.md), the order (requirements → page structure → navigation, identify first → layout → sizing → wrapping → spacing → colour and contrast → flow), how to answer (one line: yes / no / not applicable, then the evidence: a crop `shots/1200-band-3.png` or a number from `bands.json`), and the report shape. A doc page lists every question from every system, read live from the files (no copy), at `/framework/ai/review/` or under `Server/doc/`, whichever the page skill says.
- **Screenshots:** `node Server/layout-check.mjs <urls> --widths 400,1200,1920,3440 --bands --out <taskdir>/shots/` is the one command; the task mastermind runs it before review and `review.mjs` runs it if missing. task.jsonl gets `{"shots":{"pages":[...],"dir":"shots/","sheet":"shots/sheet.png"}}`; the card shows the sheet.
- **The report:** `<taskdir>/review/report.md`, one section per system, each question with its answer and evidence, and a first line `verdict: pass|fix` so `review.mjs`'s parser keeps working; `review.mjs` links it from task.jsonl and the card. Flags from `--bands` (tab bar over 2 rows at 1200 or 3 at 400, stacked left padding over 3em at 400, a wrap that appears only under 1920, a big band with little ink) appear as evidence under their question, never as a separate audit.
- **`review.mjs`:** every `full` review, and every `light` one that touched a page, uses the review skill (the reviewer's prompt says "load the review skill"), the four widths, and `--bands`; `merge.mjs` refuses a merge whose task has no report when one is due.
