## The system you are writing down

1. **The id is `N-name`.** N = the number of columns at the widest the layout is meant for. The name says how the room is divided — CSS-agnostic: a flex row and a grid that produce the same picture are the SAME layout, and the technique is a tag. A number (`2-1`) only when no honest name exists, and say so. Seed words (fixed; you define them, you may add, you may rename with a logged reason and an alias): `1-flow` `1-centered` `2-equal` `2-sidebar` `3-equal` `3-holy-grail` `N-cards`.
2. **A word is defined so it describes MANY layouts.** Answer the owner's own test in the entry for `cards`: a card is a visible background with padding on each column; a gap is usual (a radius needs one) but not required — columns may butt with a border. Do the same for every word you introduce: `flow`, `centered`, `equal`, `sidebar` (the narrow column; which side is a tag), `holy-grail`, `measure`, `hero`, `split`, `wall`, `rail`, `stack`, `band` — only the ones you can define in a sentence a newcomer accepts. Where two candidate words would split one layout, keep one word and make the difference a tag.
3. **Answer "how would that work in flex? grid? does it change with wrap?"** on every entry: the grid rule, the flex rule, and what wrap does (flex `1 1 <basis>` + `wrap` turns `2-equal` into `1-flow` when the basis stops fitting — say at what width, in terms of the basis). The CSS shown is *one way to get this picture*, never the definition. Where the framework's existing words already produce it (`framework.css` utilities, `cols-row cols-golden`, the five layout words `page rail wall stage solo` in `styles/doc/layout-system.md`), show that recipe first and link the reference. **Introduce no new CSS class for a layout name** unless one demonstrably helps something; if you think one does, write the proposal in `doc/naming.md` instead of shipping it.
4. **Tags are the navigation.** Every id, every word, every technique (`2 column flex`, `2 column grid`, `float`, `multicol`, `table`), every trait (`gap`, `no gap`, `sticky header`, `left`, `right`, `equal`, `fixed width`, `fluid`) is a tag; `/layouts/tag/<tag>/` lists every layout carrying it, and (when `/websites/site/index.json` exists — a sibling is building it tonight; read it if present, show nothing if not) every site carrying it. A tag chip anywhere links there. This is the owner's "click through these tags, and see other layouts that fit that tag" — it is the feature.
5. **Responsiveness is part of the entry**: what this layout usually becomes at 400 (`2-sidebar` → `1-flow` with the sidebar first, or a drawer), in one sentence, as an id.

## Build

- `public/layouts/layouts.json` — the data: `[ { "id": "2-sidebar", "n": 2, "name": "sidebar", "title": "Sidebar", "aliases": ["nav + main", "docs layout"], "summary": "<two plain sentences>", "when": "<one sentence>", "responds": "1-flow", "tags": [...], "css": [ { "tag": "2 column grid", "rules": "grid-template-columns: 16em 1fr" }, { "tag": "2 column flex", "rules": "…", "wrap": "…" } ], "wire": { … the drawing spec … } }, … ]` — one object per layout, and a `words` section defining every word once. This file is the authority the whole corpus cites.
- `public/layouts/Layout.js` — the drawing class: draws a `wire` spec as content-free boxes — section backgrounds, a divider where a section contributes to layout, wireframe text (bars), a placeholder image, a button — at a given width. The spec must be JSON, with roles from a fixed list (`header nav main aside footer hero cards card text image button`), because in wave 2 a Sonnet will write one per real website from its screenshot and draw it at 400 / 1920 / 3440 beside the real shot; write `doc/wire.md` so a cold Sonnet can. The thumbnail is the spec drawn inside a box of the target width, scaled down with `zoom` or a transform to fit — never a container query on the drawing itself (a container query cannot restyle its own container; `silent-render-traps` in the mastermind's memory).
- `public/layouts/page.js` — ONE screen: two sentences (what an id is; the first number is the column count), then the tree: `1` → its layouts, `2` → its layouts, `3` → …, each layout a small live wireframe at 1920 with its id and one sentence; click → `/layouts/<id>/`. The tag row at the bottom.
- `/layouts/<id>/` — the wireframe drawn at 400, 1920 and 3440 side by side (scaled to a common height, so the responsive story reads at a glance), the title, the id, the aliases, the summary, when to use it, what it becomes at 400, then the tags, then one click down: the CSS recipes (grid · flex · wrap) and the examples from the corpus. Route these from the json (read how `public/framework/ai/2026-09-06/page.js` `route(name)` builds a page from a file), never declare each as a child.
- `/layouts/tag/<tag>/` — the tag page (§4).
