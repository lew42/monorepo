verdict: fix
1. [fix] The merge gate can let through a review that asked for fixes. `status()` in Server/review.mjs (diff.patch ~line 500) returns "reviewed: pass" whenever no `[fix]` line parses, even if the review's first line says `verdict: fix`, and merge.mjs's gate (diff.patch line 236) only looks for "unanswered". A reviewer who writes "1) [fix]" or "- [fix]" instead of "1. [fix]" therefore produces a fix verdict that merges with nothing answered. The gate and the phrase should treat "verdict fix, but no findings parsed" as unanswered.
2. [fix] An old review.md can be read as if it were the new one. Server/review.mjs main() (diff.patch ~line 603) spawns the reviewer and then parses `<taskdir>/review.md` if it exists. On a second run where the reviewer dies before writing, the previous review's verdict gets logged against the new head. Delete review.md before spawning the reviewer.
3. [fix] The reviewer is never given the owner's words. The brief (deliverable 1) says the reviewer gets "the brief, the owner's words, the diff and the screenshots", but `buildPrompt` (diff.patch ~line 548) lists only requirements.md, the card dir, the diff and the shots. Add the owner-words file the brief names, or document that requirements.md stands in for it.
4. [fix] Answering a finding is too strict about spelling. `status()` accepts only a reply that is exactly `fixed` (`/^fixed$/i`), so "fixed in 8848a788" or "Fixed." is counted as declined, and the card and the mastermind see a decline that never happened. Use `/^fixed\b/i`, and count as declined only a reply starting `declined`.
5. [note] The card does not show the review on its own (deliverable 5). No card code changed; the finish-task skill line asks the author to paste the `--status` phrase into the outcome. That works, but the phrase goes stale the moment a finding is answered after landing. A later pass could have the card read the review lines in task.jsonl itself.
6. [note] The gate is looser than the brief. The brief says merge refuses without "a review newer than its last commit", but merge.mjs (diff.patch line 235) also accepts a review of any *ancestor* commit. After a `pass` review, any amount of new code can be committed and still merge unreviewed. This is probably the intended trade-off so that fixes need no second round, but it should be written in Server/doc/review.md.
7. [note] `--main` skips the review gate silently (merge.mjs, diff.patch line 204), but the header comment (line 126) says both skips are loud. Print the same warning `--no-review` prints.
8. [note] The refusal does not always give a command you can run. When no review exists yet, it prints `node Server/review.mjs <taskdir or public/framework/ai/<date>/<slug>> …` (proof/gate-refused.txt). That is a template to fill in, not "the one command to run". It could guess the task dir from the branch name (worktree/<slug>).
9. [note] Screenshots are still taken twice, and the "reuse" path never matches. review.mjs looks for `<taskdir>/layout-check/<slug>/` (diff.patch ~line 580), but no skill or tool writes there (layout-check's default is ./layout-check-out). Then merge.mjs takes its own 1920 shot into `.merge-shots/`. Either write the review shots where merge.mjs will look, or have merge.mjs reuse `<taskdir>/review/shots`.
10. [note] A simpler way: `pageUrlFor`, `worktreeBase` and the name-status/numstat parsing are copied word for word into both merge.mjs and review.mjs, even though merge.mjs already imports from review.mjs. Export them once from review.mjs, as the comment "the same rule merge.mjs's pageUrlFor() uses" already admits.
11. [note] The "full" size is broad. `sizeOf` calls *any* new .js/.mjs file full, including a throwaway proof script in a task folder, and a full review with no changed page still asks the four screenshot questions with no screenshots to look at. This review is an example: it asked about screenshots, but there were none, so the UX questions could not be answered. Skip the UX questions when `shotPaths` is empty.
