## Ruled out

- **`Servex/agents/page_tools.js:713` `move_home()`, `:784` `move_to_session()`, `:829` `move_item()`** — all three move an *existing* task's folder to a new home the caller names (`to`); none of them decide a brand-new session's identity or folder name, so they're movers, not creators.
- **`Servex/agents/page_tools.js:217` `write_line()`** — a generic "append one line, `mkdirSync` the parent first" helper used by every page tool for a file that already has a target path decided elsewhere (by `session_file()`, by a caller's explicit `path`, or by `reply-relay.mjs`'s hand-built url above). It never itself picks a session's folder name.
- **`Server/ArchiveSessions.mjs:110/178/212`** — moves *pictures* out to an external archive drive (`E:/Projects/lew42/archive`) for months already on disk; nothing to do with creating a session's own folder.
- **`Servex/agents/move-voice-sessions.mjs:59` `move()`** — a one-shot, hand-run migration script (`node Servex/agents/move-voice-sessions.mjs --apply`) that moves OLD flat `v-*.jsonl` files into the dated store, using the same hand-built `Sessions.session_path()` string as the live voice-session creator above. Not a live, ongoing creator — ruled out as a *duplicate instance* of the Sessions.js finding, not a new candidate.
- **`Server/DatedFiles.mjs:220` `make()`** — the shared primitive `TaskDirs.make()` calls to actually `mkdirSync` once the path is already decided; it doesn't choose a folder name itself, so it's folded into the `TaskDirs.mjs` row rather than listed separately.
- **`Server/session-migrate.mjs`, `Server/session-place.mjs`, `Server/session-rename.mjs`, `Server/SessionDayMove.mjs`, `Server/SessionConsolidate.mjs`** — all rename/move/dedupe EXISTING folders (the tools that clean up after the twins problem this task is about); none of them originate a new session's folder.

## The one worth flagging most

**`reply-relay.mjs` is the odd one out.** It's the only live, frequently-run creator that (a) never asks SessionFolders, (b) writes to a folder shape outside `ai/sessions/YYYY/MM/DD/` entirely (`ai/<day>/<slug>-<id8>/`), and (c) leaves no `{session:…}`/`{assign:…}` first line for `SessionFolders.owner()` to recognize later. If it fires before `session-page.mjs`/`prompt-relay.mjs` make the session's real dated folder (both are plausible orderings across hook invocations), the same session id now has two homes — one correctly in `ai/sessions/YYYY/MM/DD/session-<id8>/`, one stray at `ai/<day>/session-<id8>/` holding only a `Reply` item. That is a second, independent source of the twins bug this task exists to fix, distinct from the three creators that already ask SessionFolders correctly.
