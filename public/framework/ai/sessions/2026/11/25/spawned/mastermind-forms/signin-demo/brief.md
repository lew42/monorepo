## Decisions (the cloud chat's calls)

1. **One auth system: the existing Worker** (`worker/`: Google ID-token verification, signed 30-day cookie = the session, D1 `users`, one `UserDO` per user). No second system. If a `sessions` table is cheap, add it so each sign-in creates a session row the user can list and end (sign out ends the current one); otherwise keep the signed cookie and note it.
2. **Google client id.** the owner already made a Google OAuth app. First search for it: the repo, `.env*`, `worker/`, wrangler configs, `~/.wrangler`, `%USERPROFILE%` notes, Servex logs and past sessions (grep `apps.googleusercontent.com`, `GOOGLE_CLIENT_ID`, the old Cloudflare authentication session's lingering item). A client id is public, so it may go in `wrangler.jsonc` vars. If you find it, wire it; the demo origin must be in its Authorized JavaScript origins, which only the owner can add in Google Cloud Console: put that exact step and the exact origin(s) at the top of the report. If you don't find it, keep the mock path working end to end and ask for the id in one line (the only question allowed). There is no public test client id that works on our origin.
3. **Cloudflare.** Use the Cloudflare MCP if it is on the PC (the owner says its token has broad access) or wrangler. You may create the D1 migrations, Worker secrets and deploy **staging** (staging.lew42.com, or whichever origin serves both the page and `/api` so the cookie works; the page and the API must be same-origin). Do not touch production lew42.com yet. Never put a secret in the repo.
4. **The landing page** (the ad's destination; mobile first): full-height portrait video (`autoplay muted playsinline loop`, poster still, tap for sound), the host's line as a caption, and ONE action button over it, at the bottom above the caption, as in Figma section 14-A. On desktop: the same 9:16 video centred at full height on a dark or blurred backdrop; no separate desktop page now. A short clean URL for ads (your call, e.g. `/join/`). The video keeps playing through every step.
5. **The flow, one button that changes:**
   - **Continue with Google** (GIS, FedCM on). Under it a small "Not working?" link.
   - Signed in -> the button becomes **Allow one notification a week**, with a small line "One notification, every week. Nothing else."
   - Tap -> if iOS Safari and not running from the home screen: a sheet with add-to-home-screen steps (Share, Add to Home Screen, open it from there, tap Allow); otherwise `Notification.requestPermission()` -> `PushManager.subscribe` (VAPID) -> save the subscription for that user.
   - Done -> "You're in. See you next week." plus, for testing, **Send me a test notification now**.
   - **In-app browser detected** (your detector from inapp/proposal.md): replace the Google button with the "open in your browser" card (Android `intent://` button; iOS menu steps), **Copy link** and **Share** (navigator.share, so they can send it to themselves). Email or SMS magic links come later, after the owner picks a sender: not now.
6. **Settings sheet** (a small gear or the avatar): Signed in as X; **Sign out** (end the session, clear the cookie, `google.accounts.id.disableAutoSelect()`); **Turn off notifications** (unsubscribe, delete the stored subscription); **Delete account** (confirm, then `DELETE /api/me` wipes the D1 row, the user's UserDO storage, sessions and push subscriptions, then `google.accounts.id.revoke(email)` so Google forgets the grant and the next sign-in shows the consent text again). This is how the owner re-runs the whole flow.
7. **A debug strip** behind `?debug=1`: in-app browser yes/no and which, iOS/Android, standalone, `Notification.permission`, push supported, signed in and user id, subscription present; and a **Reset everything** button for test loops.
8. **Push.** A PWA manifest and a service worker on the landing's scope; VAPID keys generated on the PC and stored as Worker secrets (public key served to the page); subscriptions stored per user (UserDO or a D1 table, your call); routes `POST /api/push/subscribe`, `DELETE /api/push/subscribe`, `POST /api/push/test` (sends to the caller only); a weekly Cron Trigger that sends one notification to every subscribed user (the payload text from a config value the owner can change; default "New this week: watch part 2" linking back to the landing). Use a Workers-compatible Web Push implementation (Web Crypto); test with a real Chrome subscription on the PC.
9. **Copy** (editable in one place): help-me-test framing with a hint of value, e.g. "I'm building a way for anyone to have their own app like this. Help me test it: sign in, and I'll send you one notification a week."
10. **The video.** A placeholder until the owner records his own: the cloud chat is generating a short talking-head clip from the F1 still V01 (kitchen host) and will send its URL; use the still V01 as the poster until then (`.scratch/forms/stills-results.json` has its fal.media URL).
11. **Real-time later:** find the past work on Durable Objects and WebSockets for documents (one DO per document, shared vs multiple sockets) and note in the auth proposal how a per-user live connection would attach. Don't build it now.
