## Scope and fences

- **You OWN:** `public/framework/ui/**` and `public/framework/ux/**` (create it), including `ui/skill-suggestions.md` and `ux/skill-suggestions.md`.
- **READ-ONLY:** `core/**`, `styles/**` (framework.css changes = proposals), `ext/**` (⚠ a sibling mastermind owns `ext/Playground/` RIGHT NOW; `ext/Panel` is read-only pending the owner), `CLAUDE.md`, skill SKILL.md files (appending one evidence line to a skill's `improvements.md` is allowed and mandated when a skill misleads — skill-improvement skill).
- **Safety, repeat in every minion brief:** never kill or restart the dev server (localhost:80, the owner's own terminal); never drive the owner's live browser tabs — screenshots via the mcp `site` `shot` tool (fresh headless chromium) or Playwright headless scripts in the session scratchpad (prefix files `ux-`); never `git stash` (shared tree — diff, don't stash); never commit or push; scratch never goes in the repo.
- **Constraints:** no build step (everything under public/ runs as-is, real `.js` URLs), no server at runtime, no new npm dependency. Load the `code`, `css`, and `layout` skills before writing; `new-css-class` before ANY new class name (all ui css classes carry the `ui-` prefix — the owner's explicit rule); `new-page` for any page.js; `documentation` before landing a module.
- Traps that never throw (bitten before): no DOM after an `await`; every CSS rule inside a layer; only `p()`/`h1`–`h6` read backticks — one backtick inside `` css(`…`) `` kills every page; `**/` in a JS doc comment closes the block; framework.css `max-width:100%` and util-layer `:first-child` beat component CSS; resolve URLs against `import.meta`; a declared child without a page.js 404s; MCP `eval` runs in a hidden tab — hidden tabs do not lay out, use `shot` for rendering truth.

## The program (priority order — plan first, then build in waves)

1. **The ui/ ↔ ux/ system plan.** One page: what ui/ is (html+css templates, `ui-` prefixed CSS, minimal or no behavior), what ux/ is (behavioral classes, extendable, variants as named extensions), the graduation rule between them, and how themes/config words bind the two. Write it as `ux/readme.md` (+ `doc/` for depth) and mirror the ui side into `ui/readme.md`/`ui/doc/`. Fold in the audit at `../ui-behaviors-audit/` when it lands.
2. **Config words / themes.** A small set of CSS classes that re-skin an entire section: contrast (`ui-contrast`), density (explore naming: compact/mini/micro vs small), spacing, color. Study the DevBar (find it under `ext/` — its whole styling is the owner's reference for a unified section-wide system) and the core framework's existing utility vocabulary (the css skill makes you read framework.css) — lean on core, don't mint fresh classes per component. Deliver: the word list, the stylesheet(s), and a demo page where toggling the words visibly re-skins a whole section.
3. **Card systems.** Types of cards × types of content; spacing/color variants driven by the config words, not per-card CSS. Toolbars. File explorers/tree views. Every demo must work mobile ↔ 3440 (stacking, hiding, drawers, sheets).
4. **The ux/ workflow library.** Typical workflows as reusable, responsive ux modules: signup, login, social login, password reset, wizard/steps, lessons/chapters/guides (a `ux/Course`-like whole system is in-bounds), game UX, team UX. Start with 2–3 done well (show, don't tell — a demo you can open) rather than all shallow. ux views use ui templates wherever possible; each ux gets its own css class + stylesheet only when it must.
5. **Large screens.** Thoroughly explore full-3440 layouts: coordinated regions, left sidebar for nav/previews, filters, master-detail. Same pages must degrade to mobile.
6. **Class-pattern exploration.** Named progressions (`class CardHero extends Card`, never numbers) vs `Class.prototype.assign(mixin…)`. Simplicity is gold; different modules may deliberately try different patterns — record the verdict per pattern in doc/decisions.md, evidence not taste.
7. **Skills.** Read `.claude/skills/ui-test/SKILL.md` — see how it works, use it to prove interactive demos. Have minions write `ui/skill-suggestions.md` and `ux/skill-suggestions.md`: important lessons learned in this run + what a ui-design / ux-design skill should contain — minimal, not overly restrictive. These are suggestions for the owner, not new skills — do not create SKILL.md files.

**Verification is part of every wave:** every page a minion lands gets loaded through its parent (nothing crawls — a page nobody links to does not exist) and screenshotted at ~360, 768, 1280, and 3440 wide (`shot` takes a width). A claim without a clickable link or screenshot is not a result.

**What to cut first if pace bites:** #6 exploration breadth, then #5 extra layouts, then #4 beyond the first three workflows. Never cut verification of what shipped.
