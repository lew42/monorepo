# Docs check — a fresh newcomer's read of Events, List, Item, Page, filesystem readmes (no code read, readmes only)

1. **Item/readme.md diagram vs Page/readme.md header — contradicts the class chain.** `core/Item/readme.md` draws `└─ Page (core/Page) // Page extends Item`, but `core/Page/readme.md` opens with `Page extends PageLog extends Item`. `PageLog` is never named, linked, or explained in any of the eight readmes read. Fix: show `PageLog` in Item's diagram too, and add one line in Page's readme saying what `PageLog` adds over plain `Item`.

2. **Item/readme.md's own Use example contradicts filesystem's one-writer rule.** The example is `const doc = await Item.open(new FileSaver({ path: "/data/doc.json" }));` — `FileSaver` is never defined or linked anywhere, yet `ext/filesystem/readme.md` states "**`FsFile` is the only thing on the site that writes files.** Nothing else calls the dev socket's write or append RPC." A newcomer can't tell if `FileSaver` is legal, stale, or a stand-in. Fix: replace the example with a real, linked saver (ideally one built on `FsFile`) or say explicitly that `FileSaver` is illustrative pseudocode.

3. **core/readme.md's title and its own Index disagree on the count "seven."** The header says "the seven classes under every page," the **More** section lists exactly seven (View, Page, Router, App, Sidebar, Item, List), but the **Index** section above it lists thirteen entries (App, Item, Layout, List, Page, Router, Search, Section, Shell, Sidebar, View, `new`, `doc`). A newcomer counting from the top of the file gets a different number than the title promises. Fix: mark in the Index which entries are the seven "under every page" vs. which are extras (Layout, Search, Section, Shell, `new`).

4. **Saving + replaying an Item as `.jsonl` is asserted, never demonstrated.** `core/Item/readme.md` says `store: Item.Store` "replays/appends/tails one .jsonl file," and `core/Page/readme.md` says the store is "attached by `Page.jsonl()`" — but neither readme's `Use` block actually attaches a store, appends a change, or replays one, unlike `core/List/readme.md`, which does show a worked `LiveList` example. A newcomer cannot do this task from the readmes alone. Fix: add a two-to-three-line attach/replay example next to Item's or List's existing `Use` block.

5. **Two unrelated things are both called "children" across sibling readmes.** `core/List/readme.md` renames List's own array field to `items` ("✅ (renamed from `children` 2026-10-02)"), priming the reader to think `children` is retired — but `core/Page/readme.md` keeps a property literally named `children`, described as "a Map-SHAPED VIEW over `pages`," unrelated to List's old field. Fix: one clarifying line in Page's readme noting its `children` predates and is unrelated to List's renamed property.

6. **The filesystem readme's one-writer claim is never reconciled with Item/Page's own store writes.** `ext/filesystem/readme.md`: "`FsFile` is the only thing on the site that writes files." `core/Item/readme.md` and `core/Page/readme.md` both describe `Item.Store` appending `.jsonl` lines. Nothing states that `Store` is built on `FsFile.append` under the hood, so the two claims read as contradictory until a reader assumes the connection. Fix: one line in Item's or Page's readme confirming `Store` calls `FsFile.append`/`FsFile.write`.

7. **Aspirational classes sit undistinguished next to shipped ones in the same code block.** `core/Page/readme.md`'s architecture block marks `Card extends Page` with ✅ but `System extends Page` with 🔶 ("design") right below it, in the same fenced block as several ✅ lines — easy to skim past the one un-ticked emoji and assume `System` already exists. Fix: move 🔶 items to a separate "not yet built" line, or a trailing comment emphasizing it's not shipped.
