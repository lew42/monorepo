# Prompt breakdown: one parent outcome task per prompt (prompt-breakdown items 10, 11, 12)

Today every ask a prompt holds becomes its own ROOT task in the session's record. Measured on session e00f55c9 (`public/framework/ai/sessions/2026/10/20/session-e00f55c9/session.jsonl`): **341 prompt-sourced root `tasks.add` lines from 87 distinct prompts** (about 4 per prompt, 356 root adds in all, 0 nested adds). The owner wants a prompt's asks grouped: ONE parent outcome task per prompt with the asks as subtasks, or the asks filed under an existing open task when it is the same work.

## Where it is today (read first)
- `Server/PromptRecords.mjs`: `file(ps)` (~181) is step 4: it loops over a prompt's parts and for each open `ask` (kind in `def.file_kinds`) calls `run_item({path: record, delta: {tasks: {add}}})`, then records the part's `outcome: {is:"task", ref}`. `parts_one()` (~141) produces `row.subject` ("a few of the owner's words") and the parts. `task_state()` (~209) resolves a part's `ref` to a state; it only scans TOP-LEVEL `l.tasks.add` lines for nested ids.
- `Servex/agents/PromptTasks.js`: `run()` calls `parts_one` then `file`; `sweep()` moves accepted tasks with a `module_hint` to `<module>/tasks/<slug>/` (top-level tasks of the record only).
- Subtasks exist in the task model: a parent's `tasks.add` as a nested delta (`core/Task/doc/owner-2026-10-16-top-down.md`, `core/Task/doc/owner-2026-10-16-node-side.md`: `{"<parent id>":{"tasks":{"add":{...}}}}`). A parent's `complete()` refuses while a subtask is open, and its completion is the share of complete subtasks, so completing the asks completes the outcome.
- `Prompt.progress(state)` (core/Prompt) counts the parts whose ref resolves via `task_state()`.

## Build
1. **Group in `file()`.** For a prompt with TWO OR MORE fileable asks: first add one parent task (`title` = `row.subject` cleaned to a short outcome phrase, `state: "idle"`, `from: "owner"`, the same `source: {session, line, prompt}`, a `module_hint` only when every ask shares one), then add each ask as a subtask of it (nested delta). A prompt with ONE ask files as today (no wrapper). The part's outcome `ref` is the subtask's id/path. Rules (`Write down: …`) stay as they are, grouped under the same parent too if the prompt has a parent.
2. **`task_state()` and `Prompt.progress` must see nested subtasks** (a ref to a subtask resolves; a completed subtask reads complete, a stopped one stopped). Extend the scan; do not build a second resolver (law 6). Keep `sweep()` working: the parent is the unit that moves home.
3. **Existing-open-task match (small).** Before adding the parent, ONE Haiku call (`PromptRecords.ask`, no tools, the live process only): given this prompt's subject and asks plus the titles of the session's currently OPEN root tasks, answer JSON `{"attach_to": "<task id>"|null}`. When an id comes back and it is in the list, add the asks as subtasks of THAT task and skip the new parent. If this proves flaky in a test, ship step 1 alone and log the match as a follow-up in your report.
4. **Measure.** Write `Server/prompt-group-dry.mjs` (a dry run, writes nothing): replays the e00f55c9 `prompts.jsonl` parts and reports root tasks before (341 for prompts) and after the grouping rule (parents + single-ask prompts), as a one-line table. Put the numbers in your report and in the doc below.
5. **Refinement principles doc (items 11-12).** A short doc `public/framework/core/Session/doc/prompt-breakdown.md` (link it from `core/Session/doc/prompt-tasks.md` and the Session readme): the principles in one screen (what a prompt becomes: one outcome task, asks as subtasks, rules as doc notes, questions answered; asks are never merged or lost; quote the owner's qualifiers; a task is an outcome, not an operating principle; completion rolls up from subtasks to the prompt).
