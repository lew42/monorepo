## The owner's problem, in one sentence
On the AI Sessions tab, the column-resize handle lags because `ext/grip`
mounts one full-document `pointermove` listener PER COLUMN (9 of them) just
to show a "near the edge" glow — moving the mouse anywhere on the page runs 9
`getBoundingClientRect()` calls every frame. The owner also doesn't want to
keep hand-building one grid per page; "we should turn it into a reusable
component and fix it once."

## UI vs UX (the owner's own distinction — follow it exactly)
> If it's pure HTML and CSS (even if rendered by JS), it's UI — not a class,
> no JS needed to exist. If it needs JS (state, listeners), it's UX. An ext
> may bundle several UI+UX pieces into one package.

So build it in two layers:

1. **`ui/datagrid/datagrid.js`** — `datagrid(columns, rows)`, a plain function
   (like `ui.table`) that renders ONLY markup + CSS: a CSS-grid container,
   one `--col-<key>` custom property per column (defaulted inline so it
   renders correctly with zero JS), header cells, body cells. No listeners,
   no class, no state. This is the part that "doesn't need JavaScript" —
   wire it into `ui.js`'s export list and `ui/page.js`'s wall the same way
   `table` is (see `ui/readme.md`'s own note: a css-only component's page.js
   never imports its own file, or it renders unstyled).
   Add its one line to `ui/readme.md`'s Index (alphabetical, like the rest),
   plus the one line the parent brief asks for near the top of that readme:
   "UI = HTML + CSS only, no JavaScript needed (a function that only renders
   markup is fine); behaviour lives in `ux/`; an `ext/` may bundle both."

2. **`ext/DataGrid/DataGrid.js`** — `export default class DataGrid`, the
   behavior layer, built ON TOP of `datagrid()`'s markup (import it, don't
   duplicate it). Constructor takes:
   ```js
   new DataGrid({
     columns: [{ key, label, width, min, type /* "text"|"number"|"date" */, format, sort }],
     rows: [...],              // a plain array OR an async function returning one (jsonl source)
   })
   ```
   Exposes `.mount($parent)` (or follow `View`'s own `.el`/`append` convention
   — check `core/View/View.js` for the house pattern other ext classes use,
   e.g. `Panel2`). Behaviors:

   - **Resize** — ONE pointer-event listener pair on the grid's own header
     row (event delegation: read `e.target.closest(".dg-grip")` to know
     which column), not one per column. On drag, write exactly one CSS
     custom property (`--col-<key>`) per frame — no other layout reflow, no
     React-style re-render. This directly fixes the owner's measured bug
     (108% CPU / 1.37GB from 9 document-level listeners) — say in your log
     how many listeners your version mounts total, compared to grip's 9.
   - **Handle visibility** — a full-height hit strip between columns,
     visible on `:hover` via plain CSS (no JS-driven "near" zone, no delay).
     This is simpler than `ext/grip`'s near-zone trick and is the actual fix
     for "slow to appear."
   - **Sort** — click a sortable header, re-sorts `rows` in place (or via a
     comparator you pick per `column.type`), re-renders only the body.
   - **Filter** — auto-generated from `column.type`:
     - `date` → a from/to range (reuse the plain `<input type=date>` pattern
       `sessions/page.js` already has, don't invent a date-picker).
     - small distinct value sets (≤ ~12 uniques among the first few hundred
       rows is a reasonable "small set" heuristic — say your own threshold
       in the code comment) → checkbox chips, same idea as sessions'
       role-filter checkboxes.
     - `number` → min/max inputs.
     No extra code needed per data set — a caller gets filters just by
     giving columns a `type`.
   - **Windowing** — past a few hundred rows, only the rows in (or just
     outside) the visible scroll range exist in the DOM. Simplest approach
     that actually works: fixed row height, one scroll listener on the
     grid's scroll container, render `visible_rows = rows.slice(start, end)`
     into the body, with a spacer (`padding-top`/`padding-bottom`, or a
     single leading/trailing filler row) sized to the rows NOT rendered, so
     the scrollbar's length/position stay correct. Don't reach for a virtual-
     scroll library — none exists in this repo and CLAUDE.md forbids a new
     npm dependency.
