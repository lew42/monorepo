# Dictation 15 (2026-10-17): past work before building, readme indexing, routine procedures inside the task system, an overview

## The asks

1. **Where is the past-work query?** A search over past work was built and an enhancement was discussed; the owner does not know where that stands.
2. **Build "does it already exist?" into the systems, above all at the mastermind level:** whenever an agent is deployed to build something, check first whether it exists and where.
3. **Index through the readme system** as the main discovery mechanism. Open question: how to structure readmes so they give a thorough overview without becoming a massive context load (a folder with 50 to 100 things and a paragraph each is too much). A throwaway Haiku minion under 100k tokens can load the readme chain and do the search itself, cheaply; it should be documented somewhere how indexing works.
4. **Routine procedures built into the task system as templates:** a code task is committed and probably has a worktree; today these rules are English and the AIs are trusted to follow them. With a node-driven task system: when a proposal is accepted, the task starts automatically or is queued and starts when resources allow; the minion spawn can be automated (time, id, author, session id and as many fields as possible added by code, not by the AI). The mastermind settles the proposal, the plan is reviewed, then the work begins and spawns itself. As much node-driven as possible.
5. **The task system needs checking,** including its views. Tasks are directory-based now: each module has a `tasks/` directory, so past work on a module is easy to find and tasks are managed by topic, not only by session. A session references its tasks by id → the task directory's path and name (logged in two places, by reference).
6. **Was the session directory's `task.jsonl` renamed to `session.jsonl`?** That was asked for.
7. **An overview:** everything figured out so far, what happened, where things stand, the biggest findings: done, needs to happen, in flight.
