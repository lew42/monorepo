# Owner dictation, 2026-10-19 (relayed by the voice agent): /live becomes a session feed

Not a plan, not approved. The ask as relayed (the voice agent's wording, not the raw words, which is the first finding below), what was found in the repo, and what is proposed. The first build is [sessions.md](sessions.md).

## The five asks, and what exists

**1. Are the voice-session prompts written verbatim to a JSONL on every prompt? Partly, and not reliably.**
- The one door is `ask_mastermind` ([`RemoteMCP.ask()`](../../../Servex/ext/remote/RemoteMCP.js)): it appends the question and the reply as `chat` lines to the voice mastermind's `task.jsonl`, and one index line (first 200 characters) to `ai/log.jsonl`. Written by code, not by AI memory, as asked.
- Four gaps. (a) Only the **question the voice model chooses to pass** is logged, a paraphrase, never the owner's raw words; the Claude app has no session file and no hook. (b) The question is cut at 4000 characters, so a long dictation is truncated. (c) Nothing makes the voice model call it: the directives only say "fire ask_mastermind immediately", and a voice agent that spawns or messages agents directly (as this task's own brief did) bypasses the log. (d) I found no `chat` line from `owner (voice)` dated after 2026-10-16, and no `remote_mcp` line in `log.jsonl` (it may have been swept), so it has probably not fired on the recent days; I could not run anything to confirm.
- Already answered once, 2026-10-17: [Servex/ext/remote/doc/remote-tools.md](../../../Servex/ext/remote/doc/remote-tools.md) ("Where an owner prompt from the Claude app lands"). The 2026-10-16 voice session's [owner-words.md](../../framework/ai/sessions/2026/10/16/voice-20261016/owner-words.md) is the voice agent writing the record from memory, which is what this ask wants to replace (its item 12).
- **Proposal:** make it tool-side. In `RemoteMCP.tools()` add an `owner_words` property to every tool's schema, described as "the owner's exact words that led to this call, verbatim, every time"; `RemoteMCP.post()` strips it before dispatch and appends it (once per distinct text) to one `voice-prompts.jsonl` as `{at, words, tool, session}`, with no length cut. Compliance still depends on the model, but the logging, dedupe and storage are code, and the tool descriptions are where the model reads the rule. Takes effect after a Servex restart.

**2. The live page as a session-based idea feed: built, first slice.** [sessions.md](sessions.md): a session is what was on screen between two `clear` lines, computed from `page.jsonl`; `/live/sessions/` lists them, each opens as a page. It uses the existing `JSONL.live` tail, so a line any agent appends reaches the screen with no AI refreshing anything. Not yet seen in a browser. The log carries `by: "voice-app"` on each line, so the feed can later be filtered by author.

**3. Do items attached to a saved parent persist by themselves? Yes, read from the code, not run.** `List.add()` announces a `delta` that bubbles up the `parent` chain; the nearest ancestor with a `store` (`Item.Store.attach`, [core/Item/Store.js](../../framework/core/Item/Store.js)) appends ONE line with the nesting worked out, and replaying it rebuilds the tree. `Item.set()` does the same for a changed field. So a card class that `extends Item` and is added to a saved page's `content` list saves itself, and later `card.set({...})` edits are appended too; no separate save step. Limits: it only writes on the dev backend (`DevBackend`; the static production site is read-only), and the card class must be registered with `Item.register` or it comes back as a plain `Item` ([core/Item/readme.md](../../framework/core/Item/readme.md), [core/Page/doc/storage.md](../../framework/core/Page/doc/storage.md)). `Page` also extends `Item`.

**4. Is the Inbox the right view for this feed? For the list of past sessions yes, for the live feed no.** The Inbox rail (`Inbox.Rail extends Browse`, [core/Page/ext/Inbox](../../framework/core/Page/ext/Inbox/readme.md)) is a list of rows with the picked page beside it, rows from any `source()`, a row opening `<url>/<id>/`. That is exactly "browse past sessions": the sessions list should become a `Browse`/`Inbox.Rail` subclass (rows `{id, title, at, sub}`) instead of the plain list in `sessions/LiveSessions.js`, which is a stand-in. The current-session feed stays `Live`: one narrow column of white cards, newest first, phone first. Nothing in the Inbox needs to change.

**5. Context cards (noted, not built).** Nested, dynamic cards with an AI-written icon, title and content, framing a task, question, project, session or chat on the owner's screen while they dictate. Already designed: [ext/Refine/doc/card-types.md](../../framework/ext/Refine/doc/card-types.md) ("Context cards: the pattern, and what already exists"): a context card wraps any class or page that already has an icon and title, via a mention, and holds the content unique to this instance; each card is an `Item`, so it persists as in item 3. Past work: [ux/Dictate/doc/streaming-ui.md](../../framework/ux/Dictate/doc/streaming-ui.md).
