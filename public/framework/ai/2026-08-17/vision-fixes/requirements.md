# vision-fixes — from "what's wrong" to "how it should be", to CSS, with a quality gate

Laws: less is more · clarity · prioritize. **Deliverable: a precision number for the tool's recommendations, and the prompts that earned it. If the number is bad, the report says why and nothing gets built on top. Final message ≤ 30 lines.**

Mike (2026-08-17 ~18:35), verbatim: *"the one image prompt i read basically was, 'give critique', or 'what's wrong' but not necessarily how each thing could be better? Let's try to capture that with the feedback. and lastly … after we capture the raw opinions, give it the code/page/file to look at, ask it to use/improve (via skill/improvements.md) css and layout skills. at that point, the recommendations become CSS fixes, or css-class additions/removals? … however, let's be sure we're proposing the right fixes. if we get this all setup, and 90% of the recommendations are garbage, it's all for nothing"*

## Do, in this order

1. **`fix` per finding.** `prompts/critique-full-v2.md` (already drafted: every angle a clause + purpose + overview/drill-down): each finding gains `"fix": "<one line: what it should look like instead — no CSS, no selectors>"`. Add one angle: *edges — is anything hard against the viewport edge or the frame?* Keep ≤ 40 lines. Also `checklist-v1` gets the same `fix` key (it catches edge-cramping and unlabelled controls the others skip).
2. **Turn 2 sees the code.** Rewrite `prompts/css-v1.md` → `css-v2.md`: the runner passes (a) the page URL and the region's DOM outline (already), (b) **the CSS files that actually cascade onto it** — the model may `Read` `public/framework/framework.css`, `core/Page/Page.css`, the module's own `.css`, `styles/doc/layout-system.md`, and the text of `.claude/skills/css/SKILL.md` + `.claude/skills/layout/SKILL.md` (paths in the prompt; `--allowedTools Read` already). It answers per finding: `{sel, decl, why, class, ladder_rung}` — where `ladder_rung` is the css skill's rung (nothing · utility · layout word · component class · module css · site css) — **and** may return `"skill_notes": [{"skill": "css|layout", "note": "<one evidence line>"}]` for anything that misled it. The runner appends each skill note to `.claude/skills/<skill>/improvements.md` in the skill's one-line format, tagged `(vision, <shot hash>)`. Log turn-2 tokens separately (they will be higher — reads).
3. **Run**: the 6 pilot pages, page-level, 1280 only, Sonnet, `critique-full-v2` + `--turn2 css-v2` → `--out public/framework/ai/2026-08-17/vision-fixes` (~6 asks + 6 turn-2s ≈ $2; `--dry` first; ceiling $4).
4. **Quality gate — an Opus referee (you).** For every finding with a `fix` and a `decl` (expect 20–35): open the png, read the finding, judge (a) is the *finding* real (visible in the image, not taste, not invented) (b) is the `fix` an improvement (c) would the `decl` do it, at the right rung, without a new branch. Score each `right | taste | wrong`. Report **precision** = right ÷ all, for findings, fixes, decls, and separately for `broken` vs `maybe`. Two numbers that must agree: the count of decls you judged and the count in `vision.jsonl`. Write the table to `quality.md` here (≤ 50 lines) with the three worst and three best, quoted. **If decl precision < 0.6, stop here**: say which failure dominates (invented finding · taste as broken · wrong selector · wrong rung · new branch) and what prompt change would fix it; do not build previews.
5. **If ≥ 0.6**: apply nothing; write `proposal.md` (≤ 40 lines): the preview mechanism to build next — `ext/DesignTool/audit/twin.js` (two iframes, injected decls, Accept RPC — exists) vs a devbar "proposals" toggle on the live page — pick one with a reason, and the smallest wiring for Accept/Reject → `verdicts.jsonl` beside the run.

## Rules

- Files: `ext/DesignTool/vision/{run.mjs,prompts/*,readme.md}`, `.claude/skills/{css,layout}/improvements.md` (append only, via the runner), this dir. Not `browse.js`/`page.js`; not any site CSS. `code` skill once; `finish-task`. Log in `task.jsonl` (bash `printf`; timestamps from `date -Iseconds`); bump step. Never Mike's live tabs.

> imagine the same screenshot passed to N different model/prompt minions. each with similar feedback/process, producing specific CSS adjustments. could we get consistent recommendations? if 50%+ recommend a specific change, in a specific direction, that sounds like signal rather than noise. if the other 50% recommend in the other direction, maybe that's a problem :D

**4b. Consensus, alongside the referee.** For the same 6 page shots @1280, run **three independent asks each** (Sonnet `critique-full-v2` in two fresh sessions + Opus `critique-full-v2` once, all with `--turn2 css-v2`; the runner's key is hash|prompt|model, so give the second Sonnet pass a `--tag` or a copied prompt id `critique-full-v2b` — say how). Cluster findings across the three by meaning **and direction** (e.g. "more space above the h1" vs "less"). Report per page: findings with ≥2/3 agreement (signal) · 1/3 (noise) · **contradictory directions** (the problem Mike names). Then the number that decides the design: **does agreement predict the referee's `right`?** (precision of ≥2/3-agreed decls vs 1/3 decls). If it does, consensus becomes the gate and the referee is spot-check only. Extra cost ≈ $5; ceiling for the whole task **$9**.
