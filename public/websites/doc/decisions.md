# Decisions

The record for `/websites/`. Every entry is a choice that could reasonably have gone the
other way, with the reason it did not.

## Why a manifest, and not the directory

`site/index.json` is generated by `tools/index.mjs`, and the pages read it exclusively.

Production is static: there is no server to answer "what files are in `site/`?", and nothing
on this site crawls the filesystem — a page exists once something names it. `blog/posts.js`
made the same call for the same reason, and `blog/meta.mjs` is the same shape of generator.

The cost is real and worth naming: **forget to run `index.mjs` and a freshly shot site is
invisible.** That is the trade for a corpus that deploys as files with no tooling at all.
The manifest also carries only what a *card* needs, so the front lists forty sites without
fetching forty records.

## Why jpeg, and why these five shots

Four viewport shots plus one long one, jpeg at quality 70. A site costs about 1.5 MB, so
forty sites stay under 60 MB in git — png at these dimensions is roughly ten times that, for
photographs of screens where the difference is invisible.

The four widths are a phone, a laptop, a desktop and an ultrawide. **Rendered side by side at
one common height, the difference in their widths IS the responsive story** — that comparison
is the reason the strip exists and the reason all four are kept rather than a "mobile" and a
"desktop".

`long.jpg` is one 1280 × 4000 viewport, never `fullPage: true`. A full-page shot of a tall
site at a 3440 viewport is a 100 MB image.

## Why the CSS is not read from the CSSOM

`document.styleSheets[n].cssRules` throws a `SecurityError` for every cross-origin
stylesheet — measured on stripe.com: five of five sheets blocked. A tool built on the CSSOM
would report that real sites have no media queries, and would look like it was working.

So the stylesheets are captured from the network instead (`page.on("response")` filtered on
`content-type: text/css`), plus the inline `<style>` text, and the queries are read out of
that. `getComputedStyle` needs no such workaround: it works cross-origin and it *is* the
result of the cascade, which is why every per-element measurement uses it.

## Why the viewer SCALES the frame rather than resizing the page

To see a site at 3440 you need a 3440-pixel-wide window, which nobody has. The viewer makes
a real one — an iframe genuinely laid out at 3440 CSS pixels — and then applies
`transform: scale()` so the whole thing fits in the room the page has.

A transform does not affect layout, so the page inside believes it is on an ultrawide monitor
and lays out accordingly, while the reader sees it shrunk. Resizing the frame element
instead would just be a small window, which is a different measurement.

`transform` does not change the element's layout box either, so JS has to write the stage's
width and height from the scaled numbers. Two traps came out of building it:

- **Measure the container, never the stage.** The stage is what we resize, so reading the
  available room off it feeds its own output back in and ratchets the frame to nothing.
- **`max-width: none` on the frame is load-bearing.** framework.css's base layer sets
  `iframe { max-width: 100% }`, which silently held a frame told to be 3440px wide to its
  container's 1766px and then scaled *that* down. The viewer rendered the site at 1766 with
  "3440 px" written beside it, and nothing threw. Caught by reading the painted box back:
  907px where 1766 was expected.

## Why the screenshots are the primary evidence and the frame is the bonus

Roughly half the interesting web refuses to be framed. Of the three seed sites, two do:
MDN sends `x-frame-options: DENY`, Stripe sends `SAMEORIGIN`; only Wikipedia allows it.

So `embed` is read from the response headers at capture time and stored, and a blocked site
says so in one sentence where the viewer would be. Detecting it by *trying* would mean an
empty box with an error only in the console — an invisible failure. The header is the site's
own answer, given before we ask.

## Why layout ids are `N-name` and CSS is a separate tag

The owner's decision (2026-09-08): N is the number of columns at the widest, the name says
how the room is divided, and a number is used only when no name can be found. The names are
deliberately CSS-agnostic, because flex and grid routinely produce identical results and a
vocabulary that splits them would file the same layout in two places.

The technique is a tag instead (`2 column grid`, `float infobox`), so you can ask either
question: "what does this look like" and "how was it done".

Wikipedia is the argument for the split. Its three columns are **two mechanisms at once** —
the article and the appearance rail are one CSS grid, and the contents list is a separate
element positioned beside them. The screenshot cannot tell you that and the id should not
try to; `3-holy-grail` plus `3 column grid` says both things without either lying.

## Why a layout link goes through the standard's alias table

The encyclopedia is allowed to rename and to alias, and it did: the seed word `N-cards`
became `n-wall`, `3-cards` is now an alias of `3-equal`, and `bento` is an alias of `4-1`.

The corpus could have been rewritten to the canonical ids every time that happens. Instead
`Site.js` reads `/layouts/layouts.json` once and builds an alias map, so a record may write
whichever word reads best about that site and the chip still links to the entry that defines
it. Verified live: `3-cards` on stripe's bento resolves to `/layouts/3-equal/`, and
`2-sidebar right` on wikipedia's infobox resolves to `/layouts/2-sidebar/`.

It degrades to the literal id when the table has not arrived, so a missing or half-built
`/layouts/` costs one 404 link, never a broken page.

## Why tags are flat and free text

The owner: "maybe I just want to be able to click through these tags, and see other layouts
that fit that tag." A closed vocabulary would need a decision every time something new turned
up, and the useful tags — `hamburger`, `max-width`, `layout switcher` — are exactly the ones
nobody would have thought to allow in advance.

Free text is not the same as no rule. Forty-seven records grew 107 tags, and half of them were
a number (`max-width 1232`), a note about the capture (`bot wall`) or a second spelling of a
word already there (`3-cards`, `centred at 1920`). One pass on 2026-09-08 folded them to 52.
The rule that decides, and the whole vocabulary: [`tags.md`](./tags.md).

The front's filter row shows only tags that actually narrow the wall — carried by **more than
one** site and by **fewer than four fifths** of them. The first version showed all 26: on a
400-wide screen that stood 400px tall and pushed every site card below the fold, on the page
whose only job is to show them. A tag one site carries filters the wall down to a card that is
already on screen; `1-flow` at the other end is carried by 45 of 47, so clicking it removes two
cards and looks broken. Both are still real tags with real pages — they are just not filters,
and the full list is one click away at `/websites/tag/`.

## Why section layouts get their own index, beside `tags`

A tag page already lists every site whose *global* layout or free-text tags match; it said
nothing about a layout used only inside one section of a page — Wikipedia's infobox is
`2-sidebar right` without the whole page being a sidebar layout. `sections[].layout` was
always in the record, so `index.mjs` (2026-09-08) now also writes a `sections` key beside
`tags`: `{ "<layout id>": ["<site name>", …] }`, one entry per id that appears as a section
somewhere. `/websites/tag/<id>/` and `/layouts/<id>/` both draw a second list from it, "as a
section, on:", under the first. A section's own `layout` may carry a modifier (`2-sidebar
right`) — the index keys on the bare id, the same word a layout chip already splits off.

## Why the live viewer waits for a button

Fifteen of the forty-seven records say `embed: allowed`, and their pages used to write
`<iframe src="https://en.wikipedia.org/…">` straight into the markup. A browser fetches an
iframe's `src` the instant it parses the tag, so **opening one of these pages was itself a
visit to somebody else's website** — their servers, their logs, their cookies — bought by a
reader who came for four photographs and never asked for the live thing.

Measured headless on 2026-09-08 against `/websites/wikipedia-css/`, with every non-`localhost`
request aborted at the wire so the measurement itself cost nobody a page view:

| | hosts requested when the page opens | frames in the DOM |
|---|---|---|
| before | `localhost:8123`, `fonts.gstatic.com`, **`en.wikipedia.org`** | 1 |
| after | `localhost:8123`, `fonts.gstatic.com` | 0 |
| after, once the button is pressed | + `en.wikipedia.org` | 1 |

So the page now costs this server and nothing else. `fonts.gstatic.com` is the two webfont
files `framework/core/App/Font.js` loads on **every** page of this site — it is not this
module's, and it is not a third-party *site* being rendered.

The button says what it is about to do in one sentence, naming the host it will fetch, because
a reader should be able to decide before the request rather than notice it afterwards. The
four screenshots are the evidence; the live frame is the bonus, so making the bonus opt-in
costs the page nothing.

⚠ Do not put the frame back on parse to save a click. If a future viewer needs to load
something before the press, it loads it from here.

## Why a verdict on `/patterns/best/` is a two-track grid

That page is eight judgments, and every judgment is one paragraph about one website with a
photograph of that website beside it. It rendered in the 40em reading track, which at 3440
meant a column hard left, 2,700px of empty screen, an 11,000px scroll, and each 1920-wide
screenshot squeezed to about 700px — the evidence was on the page and unreadable.

The page now claims `wide` and each verdict is wrapped in `site-best-verdict`: above 76em the
words take the measure on the left and the picture takes the rest on the right, never grown
past the 1920px it was actually photographed at. Below 76em it is one column, with the picture
directly under the heading — so a phone meets the evidence before it meets a wall of prose,
which it did not before.

Two mechanics worth knowing. The wrapper is raw `<div>` inside `best.md`: markdown inside a raw
HTML block still parses, as long as there is a blank line after the opening tag and before the
closing one. And the grid's rows are `auto auto 1fr` — the picture spans all three, and a
spanning item hands its extra height to the rows it crosses, so without the `1fr` the heading,
the judgment and the link were dealt 300px of white between them.
